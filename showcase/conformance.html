Tested against somebody else's tests

Our own tests can only tell us that the code does what we meant. The OpenID Foundation publishes a conformance suite that asks the questions the specifications ask, including the awkward ones. What the suite's words mean

Only FAILED means the server got something wrong. The other three outcomes are the suite being careful, and each one here has a known cause.

WARNING, on discovery. PingFederate publishes vendor metadata the suite does not recognise. Every module of both federation plans warns about this once, which is why those plans show warnings and no passes.
WARNING, on authorisation-code reuse. PingFederate refuses the second use, as required, but does not also revoke the token the first use produced, which the profile says it should rather than must.
REVIEW, on three request_uri modules. PingFederate answers a reused, expired or foreign request_uri with an HTTP 400 error page rather than a redirect. The suite takes a picture and asks a person to look at it. A fourth module was REVIEW on 13.0.3 and now passes on 13.1.3.
SKIPPED, on the claims-parameter module. Not supported, not advertised, so not tested.

The federation plans' earlier runs did fail, and each failure was a real defect that has since been fixed: five deployed-entity modules failed because the Entity Configuration was missing OpenID Connect Discovery parameters, and a relying party that had already registered went unchecked on later requests.

Two rules PingFederate cannot be told to apply

FAPI 2.0 says a client assertion's audience is the authorisation server's issuer, alone, as a string, and that a DPoP proof is signed with PS256, ES256 or EdDSA. PingFederate 13.0.3 has no setting for either. 13.1 adds one switch for the audience, but it applies to the whole server and still accepts a one-element array. Its DPoP algorithm list is compiled in.

So this repository ships a filter that enforces both, in front of PingFederate. It can only refuse: a request it lets through is exactly the request that arrived, and the worst a defect in it can do is turn away a request that should have been served.

It applies per client, and that is the point. The suite's own Shared Signals client is an ordinary OAuth client that addresses its assertion to the token endpoint, as OpenID Connect Core says to. An early version applied the rules to every client, and the Shared Signals plan went from 19 of 19 to 1 of 19.

# the two FAPI clients, and nobody else
OIDF_FAPI2_CLIENTS=conformance-fapi2-client1,conformance-fapi2-client2

# the DPoP rule, compiled in
ALLOWED_ALGORITHMS =
  Set.of("PS256", "ES256", "EdDSA");

Two smaller filters sit beside it: one meets FAPI 1.0 Baseline at the UserInfo endpoint for the same listed clients and the FAPI 1.0 clients OIDF_FAPI_RESOURCE_CLIENTS adds, echoing an x-fapi-interaction-id and refusing an access token in the query string; the other keeps an error's error_description inside the character set RFC 6749 allows, which PingFederate's own message breaks by quoting a Java date. None of the three is registered by an annotation: the image build maps them over PingFederate's endpoints when it assembles the runtime.

Where it stops: CIBA

Three of the FAPI-CIBA plan's 35 modules fail, and no configuration and no filter can turn them. They are all the same product gap.

FAPI-CIBA profiles CIBA over FAPI 1.0 Advanced, whose resource servers shall only support sender-constrained access tokens via mutual TLS: certificate-bound tokens, RFC 8705 §3, cnf.x5t#S256. PingFederate 13.0.3 does not have them, and neither does 13.1.3. Every jar of both was searched for the claim, for mtls_endpoint_aliases and for tls_client_certificate_bound_access_tokens, and none of them is there. DPoP is the one sender-constraint the product implements.

  • discovery-end-point-verification fails on the missing metadata flag.
  • ensure-mtls-holder-of-key-required fails on a token issued without a certificate.
  • fapi-ciba-id1, the happy path, fails on its step that presents one client's certificate with another client's access token and expects a refusal the server cannot make.

A certification of this plan is therefore not available on PingFederate 13.x. The other 32 modules say the rest of CIBA is right.

A rig is not a deployment

Some of these results sit on configuration chosen to satisfy one suite. Copying it into production would be a mistake, so the repository says which choices those are and what to do instead.

The rig does thisWhyIn production
Turns off the server-wide client-assertion audience check (Rfc7523bisCompliantAudienceVerification) A fresh 13.1 archive accepts only its issuer, and the suite's ordinary clients address their assertions to the token endpoint, as OpenID Connect Core says to. Without the overlay the Shared Signals plan failed 18 of its 19 modules. Leave the check on. The FAPI clients are held to the stricter rule by the filter either way.
Runs federation and attestation inert and closed The image carries every module, and two of them refuse to boot without a trust anchor and a trust controller. The rig names PingFederate as both and leaves the anchor keys unset. Configure the anchor keys, or leave the modules out of the image.
Serves a self-signed certificate, and the federation profile disables TLS checking Local containers talking to each other. Neither is appropriate anywhere else.

Run it yourself

The rig is in the repository. One script turns a clone into a running PingFederate 13.1.3 with every module in it, configured for the suite, in about five minutes the first time.

You need Docker, Terraform, Maven, Node, and your own Ping DevOps licence details: the image bakes no licence, and nothing licensed ever lands in git. The scripts generate the suite's eight key pairs, author a stock PingFederate through its admin API with Terraform, export the configuration archive, build the image from this repository's own modules, and start it.

Configuration is code the whole way: terraform/ is the source, the archive is the artefact the image imports at boot. There is no volume, so a change made in the console is gone at the next start.

./up.sh

# PingFederate on https://localhost:9031
# discovery   /.well-known/openid-configuration
# transmitter /.well-known/ssf-configuration

What runs without anyone asking

One plan, weekly

A workflow builds a PingFederate from the clone and runs the OpenID Federation deployed-entity plan against it, on Mondays and on demand. It keeps the plan's output either way, and the server log when anything failed.

conformance-federation.yml:12-15

It needs a licence first

The workflow stops at its first step unless the repository secrets PING_IDENTITY_DEVOPS_USER and PING_IDENTITY_DEVOPS_KEY are set. Nothing in the repository can say whether they are, so this page does not claim a passing weekly run.

conformance-federation.yml:44-54

The other five are run by hand

The OP plan needs the suite hosting a relying party and an anchor that PingFederate fetches from. FAPI 2.0, Shared Signals, CAEP and FAPI-CIBA are run by a person against a local suite.

conformance/README.md:246-249

Mutation testing, weekly

A second workflow plants small bugs in the federation decisions and the PingFederate integration and fails if the tests do not notice, below 85% killed.

What has not been tested

Read this before repeating any number above. Nothing here has been certified by the OpenID Foundation. Both OpenID Federation plans are alpha. Shared Signals push delivery has never been run: it needs a suite PingFederate can call back, and a suite on localhost is one the servlet's outbound policy rightly refuses. CIBA's ping mode has never been run, for the same reason. The CAEP result spans two targets, a local replica on 2026-09-23 and the public rig on 2026-09-24, not one run on one system. The suite's third federation plan tests relying parties, which PingFederate is not, so it does not apply.

Our own tests, and what they are worth

535 methods held at 100%

Every method that decides something - verifies a signature, accepts or refuses a credential, enforces a ceiling - is gated at 100% line and branch coverage by the build. Plumbing sits outside the gate on purpose.

209 of 216 claims pinned

Each test that pins a requirement names the clause it pins, and a generated dashboard shows any row nothing pins. Seven rows are pinned by nothing, and the dashboard calls that the work queue.

Not a conformance score

The repository is explicit: a matrix row is one line of prose somebody wrote, not a count of the clauses behind it. It measures whether what this repository claims is also executed, and nothing more.
