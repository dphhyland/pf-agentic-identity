Results requiring qualification

The suite reports failures separately from warnings, manual reviews and skipped tests. The following results need qualification.

WARNING, on discovery. PingFederate publishes vendor metadata the suite does not recognise. Every module of both federation plans warns about this once, which is why those plans show warnings and no passes.
WARNING, on authorisation-code reuse. PingFederate refuses the second use, as required, but does not also revoke the token the first use produced, which the profile says it should rather than must.
REVIEW, on three request_uri modules. PingFederate answers a reused, expired or foreign request_uri with an HTTP 400 error page rather than a redirect. The suite captures the response for manual review. A fourth module was REVIEW on 13.0.3 and now passes on 13.1.3.
SKIPPED, on the claims-parameter module. The server does not advertise support, so the suite skips this test.

Earlier federation failures identified missing OpenID Connect Discovery metadata and missing checks on requests from registered relying parties. Both defects have been fixed.

FAPI 2.0 enforcement

FAPI 2.0 requires a client assertion’s audience to be the authorisation server’s issuer, expressed as a string. It limits DPoP proof signatures to PS256, ES256 or EdDSA. PingFederate 13.0.3 has no settings for these rules. Version 13.1 adds a server-wide audience setting that still accepts a one-element array; the DPoP algorithm list remains compiled in.

The repository’s FAPI 2.0 filter applies both checks before PingFederate processes the request. It rejects requests that fail and forwards accepted requests unchanged.

The filter applies to named clients. The suite’s Shared Signals client addresses assertions to the token endpoint. Applying the FAPI rules to every client caused 18 of its 19 modules to fail.

# Apply the filter to the two FAPI clients
OIDF_FAPI2_CLIENTS=conformance-fapi2-client1,conformance-fapi2-client2

# Permitted DPoP signature algorithms
ALLOWED_ALGORITHMS =
  Set.of("PS256", "ES256", "EdDSA");

A UserInfo filter returns x-fapi-interaction-id and rejects access tokens in query strings, as required by FAPI 1.0 Baseline. An OAuth error filter restricts error_description to RFC 6749’s permitted characters. The image build registers all three filters on PingFederate endpoints.

FAPI-CIBA limitation

Three of 35 FAPI-CIBA modules fail because the tested PingFederate versions lack mutual-TLS certificate-bound access tokens. Configuration changes and the repository’s filters do not resolve this limitation.

FAPI-CIBA requires certificate-bound access tokens under RFC 8705 §3, identified by cnf.x5t#S256. The repository’s investigation of PingFederate 13.0.3 and 13.1.3 found no support for this claim or the related metadata. These versions support DPoP sender-constrained tokens.

  • discovery-end-point-verification fails on the missing metadata flag.
  • ensure-mtls-holder-of-key-required fails on a token issued without a certificate.
  • fapi-ciba-id1, the happy path, fails on its step that presents one client's certificate with another client's access token and expects a refusal the server cannot make.

The tested configurations cannot pass this plan. The other 32 modules passed.

Production configuration differences

The test environment uses settings specific to the suite. Production configuration requires the changes listed below.

Test configurationWhyIn production
Turns off the server-wide client-assertion audience check (Rfc7523bisCompliantAudienceVerification) A fresh 13.1 archive accepts only its issuer, and the suite's ordinary clients address their assertions to the token endpoint, as OpenID Connect Core says to. Without the overlay the Shared Signals plan failed 18 of its 19 modules. Leave the check on. The FAPI clients are held to the stricter rule by the filter either way.
Starts federation and attestation with requests blocked The image carries every module, and two of them refuse to boot without a trust anchor and a trust controller. The rig names PingFederate as both and leaves the anchor keys unset. Configure the anchor keys, or leave the modules out of the image.
Serves a self-signed certificate, and the federation profile disables TLS checking Communication between local test containers. Use trusted certificates and enable TLS verification.

Reproduce the tests

The repository includes a script that builds and starts PingFederate 13.1.3 with the modules and configuration required by the suite.

The build requires Docker, Terraform, Maven and Node, plus Ping DevOps licence credentials. Scripts generate eight key pairs and use Terraform to configure PingFederate through its admin API. They export the configuration and build the image. Licence material is supplied separately.

terraform/ holds the configuration source. The image imports its exported archive at startup. Console changes are lost at the next start because the environment has no persistent volume.

./up.sh

# PingFederate on https://localhost:9031
# discovery   /.well-known/openid-configuration
# transmitter /.well-known/ssf-configuration

Weekly federation tests

A workflow builds PingFederate and runs the OpenID Federation deployed-entity plan on Mondays or on demand. It retains test output and collects the server log after a failure.

Manual conformance runs

The OpenID Provider plan requires the suite to host a relying party and trust anchor. Operators run this plan and the FAPI 2.0, Shared Signals, CAEP and FAPI-CIBA plans against a local suite.

Mutation testing, weekly

A weekly mutation-testing workflow checks the federation library and PingFederate integration. The workflow fails when tests detect fewer than 85% of introduced mutations.

Untested scenarios

Shared Signals push delivery and CIBA ping mode remain untested because the local suite cannot receive permitted callbacks.
