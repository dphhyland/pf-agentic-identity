OpenID Federation 1.0 on PingFederate

Trust without a phone call

Organisations that want to trust each other's servers usually swap details by hand. That works for ten partners, not for ten thousand AI agents that exist for an afternoon. OpenID Federation replaces the phone call with signed statements, and this repo makes PingFederate a full member of a federation: it checks who an agent is, registers it on its first request, gives it only what its federation allows, and lets it go when its federation stops vouching for it.

Who is who

A federation is a tree. At the top is a trust anchor, whose keys everyone configures by hand. Below it, organisations vouch for the organisations and servers below them. PingFederate can play every part.

An OpenID Provider that registers clients

Relying parties and agents from other organisations register without an administrator: on their first request, or by posting their statement to /federation/register.

A trust anchor, or an intermediate

PingFederate vouches for the entities below it, answers the federation's fetch and list endpoints, and can limit what those entities may be.

A home for agents

An agent that lives for an afternoon shouldn't need its own web server. PingFederate publishes and signs its statement for it, and an operator can suspend, revoke or re-key it.

A Trust Mark issuer

A Trust Mark is a signed badge - "certified", "passed our checks". PingFederate issues them, says whether one is still active, and can require them.

A resolver

Anyone can ask PingFederate to build and check an entity's chain to a named anchor and hand back the result, signed.

A careful consumer

The same checks decide whether PingFederate trusts a client attestation's issuer and a wallet provider.

A chain, step by step

An entity proves who it is with a trust chain: its own signed statement, a statement about it from each organisation above it, and the anchor's statement at the top. PingFederate follows the chain up and checks every link.

The agentsays who it is and which keys it uses
→
Its organisationvouches for those keys
→
The federationvouches for the organisation
→
Trust anchorits keys pinned by hand
  1. Every statement is what it says it is - signed, with an algorithm that isn't a shared secret, naming exactly one key.
  2. Every statement is current - issued in the past, not yet expired.
  3. The entity signed its own statement with a key it publishes.
  4. Each link is signed with the key the one above vouched for, all the way up.
  5. The top is signed with a key you pinned - never one fetched from the anchor's own website.
  6. The rules the organisations above set still hold - how deep the tree goes, which domain names are allowed.
  7. Their policies agree, and what the entity may do is what's left when they're applied.
  8. Nothing marked critical is unknown.

A chain lasts as long as its shortest-lived statement, and nothing built on it lasts longer. Working one out is bounded - at most 24 fetches, over https, never to a private address - so a stranger can't make PingFederate crawl the internet for them.

Keys you pin, not keys you fetch

Everything rests on the trust anchor's public keys, and those are the one thing configured by hand - captured once, out of band, and set in OIDF_FEDERATION_TRUST_ANCHOR_JWKS. PingFederate can trust several anchors at once. It never takes an anchor's keys from the anchor's website: whoever controls that website could otherwise put any keys there.

PingFederate can also be an anchor itself. Then chains that end at it are checked with the key it signs with, read from its own key store, so the key can rotate and nobody has to pin it again.

OIDF_FEDERATION_TRUST_ANCHOR_JWKS={
  "https://federation.example.org": {"keys": [ ... ]},
  "https://partners.example.net":   {"keys": [ ... ]}
}
OIDF_FEDERATION_SELF_ANCHOR=https://pf.example.com

What an agent may ask for

An agent describes itself: the scopes it wants, how it signs in. The organisations above it can narrow that with a metadata policy, and can set constraints on everything below them. What PingFederate registers is what's left.

For example, a domain that lets its agents have at most read and write, and always audit. An agent that asks for read write admin audit is registered with read write audit. One that leaves out audit isn't registered at all.

If two organisations' policies contradict each other, the chain fails: nothing is guessed. And by default PingFederate refuses a chain whose organisations set no policy at all, rather than let an agent grant itself whatever it asks for.

"metadata_policy": {
  "oauth_client": {
    "scope": {
      "subset_of":   ["read", "write", "audit"],
      "superset_of": ["audit"]
    }
  }
}

Badges

A Trust Mark is a signed badge: an issuer says an entity passed something. It's only worth what the issuer is worth, so PingFederate counts one only when the federation's trust anchor names that issuer for that kind of mark, the issuer's own chain reaches the same anchor, and the signature checks out - and, if you ask it to, when the issuer still says the mark is active. A mark that fails is simply ignored. A deployment can require marks before it registers anyone; PingFederate can issue them too, to the entities an operator grants them to.

Arriving with a chain

Agents, at the token endpoint

An agent asks for a token with a signed client assertion that can carry its chain. PingFederate checks the chain, registers the agent, and lets the same request through to authenticate it as normal.

TokenEndpointAutoRegistrationFilter.java:142-186

Relying parties, at sign-in

A relying party sends a signed request to the authorization or PAR endpoint. The signature proves it holds its keys; PingFederate checks the request's claims before it fetches anything, then the chain, then registers it.

FrontChannelAutoRegistrationFilter.java:120-162

And every time after

A relying party proves itself on every request, not just the first: each one signed with a key it registered, with an identifier it hasn't used before. A request PingFederate can't trust gets an error page - never a redirect to an address it can't vouch for.

Registering first

A relying party can also register before it asks for anything, by posting its signed statement - or its whole chain - to /federation/register. PingFederate checks it the same way and answers with a signed registration: what it may do, its own keys, and when the registration ends.

RegistrationService.java:205-257

How long it lasts, and how it ends

Every registration ends: when its chain expires, or after a day, whichever comes first. An agent's registration renews itself on its next request, if its federation still vouches for it. A background sweep disables the ones that have lapsed, and never deletes anything.

Asking a policy engine

A federation says what an entity may be. It can't say what your organisation wants to let in today. So PingFederate can ask a policy engine - PingAuthorize, or anything that speaks AuthZEN 1.0 - before it registers a client, enrols an agent or issues a token.

The engine answers yes or no, and a yes can narrow what's granted: fewer scopes, a shorter registration, a badge the client must hold. It can never widen anything. No answer - the engine down, slow, or saying something that isn't a decision - means no, unless you choose otherwise.

{
  "subject":  {"type": "federation_entity",
               "id": "https://agents.example.com/a1"},
  "action":   {"name": "federation.register.automatic"},
  "resource": {"type": "openid_provider",
               "id": "https://pf.example.com"},
  "context":  {"scope": "read write", ...}
}

Knowing who's asking

By default anyone may call a federation's endpoints. A federation can decide that some of them are for members only. PingFederate can then require the caller to sign its request with its own federation key - and since it finds that key by checking the caller's chain, only a member of the federation gets in.

EndpointClientAuthentication.java:68-127

What the logs say

Registrations and refusals, renewals and expiries, the policy engine's answers and every change an operator makes are written as one line each - who, what and why - and the ones that matter for security go to PingFederate's audit log as well. No token reaches those lines: anything that looks like one is replaced with a fingerprint of it.

Proof

The OpenID Foundation's own tests

Against a PingFederate built from this repo: the deployed-entity plan 5 of 5 and the OP plan 20 of 20, with a warning on each about PingFederate's own vendor metadata and no failures. The OP plan registers a relying party thirteen wrong ways; each is refused.

Our own tests

Each test that pins a requirement names it, and a dashboard shows any requirement nothing pins. Every method that makes a decision is held at 100% line and branch coverage by the build.

Tests that are tested

Mutation testing plants small bugs in the decision code - a condition turned round, a boundary moved - and checks a test fails. The tests catch 95% of them in the federation library, 93% in PingFederate's side.

What it doesn't do

Worth knowing before you promise a partner something. PingFederate checks other entities' chains with the keys they publish now, not their retired ones. Client authentication at the federation endpoints is private_key_jwt only. The policy engine is asked at registration, enrolment and token issuance, with one set of settings for the whole deployment. Where the specification leaves room, it errs towards refusing. And a run against a suite you host is evidence, not a certification.
