Authenticating workloads to PingFederate with platform identity instead of secrets

A workload authenticates to PingFederate using an identity token its platform already issues it, rather than a provisioned per-workload credential. This is running on live Google infrastructure across four platforms: SPIRE on GKE, GKE workload identity, Gemini Enterprise Agent Platform service accounts, and a workload on Railway.

The problem it solves

An OAuth client normally authenticates with a static credential: a client secret or a private key in config. For workloads and agents that are created and destroyed continuously, that credential is duplicated across instances, outlives the workloads that used it, and carries no information about where the caller is running. The alternative used here is to derive a short-lived credential from the platform's own attestation of the workload, on each enrolment.

Three parties are involved:

Platform attestor – SPIRE, GKE, or Google's SA signer Client Attester – servlet inside PF's war PingFederate – the authorization server

These colours are used in the diagrams: blue for evidence issued by the platform, teal for the attestation the attester mints, red for what PingFederate verifies at the token endpoint.

The flow, in five steps

The workload is configured with one value: the attester's base URL. It learns the rest from the discovery document, and it is never told which OAuth client it is.

  1. 1

    Discover

    GET /.well-known/client-attester returns a static, parameterless document (RFC 8615). It carries the endpoints, the evidence audience the workload must mint into its identity token, and the proof requirements. It carries no client_id. The workload does not know which OAuth client it is, and does not need to.

  2. 2

    Prove what you are

    The workload fetches identity evidence from the platform: a token only something actually running in that pod could obtain. That is a SPIRE JWT-SVID from the Workload API socket, a Kubernetes service-account token Google signs and projects into the pod, or a Google service-account ID token.

  3. 3

    Bind a key

    The workload generates a fresh P-256 instance key, fetches a one-time challenge, and signs a proof-of-possession over it. The eventual credential is cryptographically bound to this key, and the key never leaves the pod.

  4. 4

    Mint the Client Attestation

    POST /federation/attestation with the evidence, the instance key, and the proof, and no client_id. The attester validates the evidence against a trust bundle. It then reverse-maps the identity onto the client it belongs to (see resolver plugins below), optionally introspects the workload further, and enforces that client's entitlement ceiling. It mints a 5-minute Client Attestation JWT (draft-ietf-oauth-attestation-based-client-auth) whose sub is the client it selected.

  5. 5

    Authenticate to the AS

    The workload calls PF's token endpoint with two headers, OAuth-Client-Attestation (the minted JWT) and OAuth-Client-Attestation-PoP (a fresh proof signed with the instance key), and no client_id or client_secret. A filter over the token endpoint verifies both and authenticates the client to PF with a private_key_jwt the workload never holds; PF then issues a JWT access token. The attestation is the only credential the workload sends (see "How the token call carries no secret" below).

What the platform evidence in step 2 actually is

The evidence is a token the platform issues to the pod, not something the workload can write itself. Take the GKE case, which is the /var/run/secrets/tokens/… file the SDK reads. You declare a projected service-account token on the pod and set its audience to the attester: 

volumes:
  - name: attester-token
    projected:
      sources:
        - serviceAccountToken:
            audience: "https://attester.example.com"   # who the token is for
            expirationSeconds: 3600                     # short-lived
            path: attester-token                        # → /var/run/secrets/tokens/attester-token

The kubelet, not the container, asks the Kubernetes API server for a JWT identifying the pod's service account, and writes it to that file. The token is signed by the cluster's OIDC key, so the attester verifies it against the cluster's public JWKS; its sub is system:serviceaccount:demo:payment-agent; and its aud is the attester, so it cannot be replayed against anything else. The kubelet rotates it before it expires, which is why the SDK reads the file on each call rather than caching it. The workload only reads the file. It cannot mint or alter the token, and that is what makes presenting it proof of what the workload is.

The other two evidence types work the same way, from a different issuer: a SPIRE JWT-SVID comes from the SPIRE agent over the Workload API socket, and a Google service-account ID token comes from generateIdToken. In every case the workload holds no signing key; it only fetches a token a trusted platform component produced for it.

The SDK runs the five steps for you

A workload uses one call. The polyglot SDK (client-attestation-sdk-polyglot, in Java, Python, TypeScript, and Go) runs discovery, evidence, mint, and the token call, and caches the token until it nears expiry: 

from client_attestation_sdk import ClientAttestation

ca = ClientAttestation("pf.example.com")   # finds the workload's platform identity itself
token = ca.token()                          # access token, no secret, no client_id

The PingFederate host is the only required configuration. The attester's /.well-known/client-attester advertises the token endpoint and the PoP audience, so the SDK resolves the rest. It finds the platform identity by checking the runtime in order: an environment token, a projected token file (/var/run/secrets/tokens/…), a SPIRE socket, then the GCP metadata server. You can override that with an explicit source.

For an agent, take the Authorization header the SDK gives you and attach it to a tool's HTTP call, or hand the SDK's adapter to your HTTP client (a requests/httpx auth in Python, a fetch wrapper in TypeScript, an http.RoundTripper in Go, a java.net.http helper in Java). In Gemini/ADK, that adapter is an ADK header_provider or before_tool_callback; the agent's tool call then carries an attestation-derived token with no secret and no extra code.

The workload is not configured with a client_id

The issuance request contains only instance_key, svid and proof. The attester determines which OAuth client the evidence identity maps to and writes that into the attestation's sub; the workload reads it back from there when it calls the token endpoint.

Two consequences follow. A workload cannot request a client it was not mapped to, because it has no way to name one. And re-mapping a workload to a different client is a change in the attester's configuration alone; the workload is not redeployed and its config does not change.

Resolver plugins: where the mapping comes from

The identity-to-client mapping comes from a resolver plugin. At mint time the attester tries each configured plugin against the presented evidence. The plugin whose trust bundle verifies the evidence, and whose bindings contain the resulting SPIFFE ID, supplies the client id and the entitlement ceiling applied to the attestation. Plugins can be chained; the supported and active sets are published in the discovery document.

PluginMapping lives inWhy you'd pick it
pf-client-metadata Each client's attestation_* extended properties in PingFederate No external document; the mapping is config-as-code beside the client itself
cimd A hosted Client ID Metadata Document fetched by URL Mapping in git or a static host, changed without touching the AS – this demo's cimd.json
openid-federation A signed federation entity statement's spiffe_client_bindings claim Governed by a federation you already trust, and tamper-evident by signature

Chaining order is precedence: the first plugin to declare a client id wins, so an external source overrides local config. Two different clients claiming the same SPIFFE ID is a configuration error and is rejected rather than resolved arbitrarily.

Introspecting the workload: SPIRE selectors as policy input

An SVID carries a SPIFFE ID and little else. After validating it, the attester can query SPIRE for the registration selectors behind that identity (k8s:ns:demo, k8s:sa:payment-agent, unix:uid:0, docker:image:…) and add them to the attestation's workload.attributes, where the issuance policy can read them.

Selectors are recorded by SPIRE when it attests the workload, so they are not self-asserted. That makes them usable for conditioning the grant; for example, only granting EMEA to a workload whose selectors include k8s:ns:demo. The lookup is best-effort. If it fails, the attestation is not enriched and issuance continues.

The requests, in full

Four HTTP calls. The live consoles show each one as a runnable curl with the real values filled in (the show the exact request toggle under each step); runbook-curl.md has the annotated version. 

# 1. Discovery: static, no parameters, no client_id
curl -s -X GET '$PF/.well-known/client-attester'

# 2. Evidence from the platform. aud = the evidence_audience the document named
cat /var/run/secrets/tokens/attester-token          # GKE projects it into the pod

# 3. Challenge, then mint. No client_id in the body.
curl -s -X POST '$PF/federation/attestation-challenge'
curl -s -X POST '$PF/federation/attestation' \
  -H 'Content-Type: application/json' \
  -d '{
  "instance_key": {"kty":"EC","crv":"P-256","x":"…","y":"…","kid":"…"},
  "svid":  "eyJhbGciOiJSUzI1NiIs…",
  "proof": "eyJhbGciOiJFUzI1NiIs…",
  "authorization_details": [{"type":"sales_agent","sales_regions":["EMEA"]}]
}'
# → {"attestation":"eyJhbGciOiJFUzI1NiIs…","expires_in":300}

# 4. Token. Only the two attestation headers, no client_id, no client_secret.
curl -s -X POST '$PF/as/token.oauth2' \
  -H 'OAuth-Client-Attestation: eyJhbGciOiJFUzI1NiIs…' \
  -H 'OAuth-Client-Attestation-PoP: eyJhbGciOiJFUzI1NiIs…' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=client_credentials'

The access token that comes back is a JWT (typ: at+jwt) whose sub is the attested workload: 

{
 "sub": "spiffe://<project>.svc.id.goog/ns/demo/sa/payment-agent",
 "act": {"sub": "demo-attest-gke-native", "attested_by": "spiffe"},
 "client_id": "demo-attest-gke-native",
 "jti": "9WU8ePqjpVVuJjxZVly9js", "iat": 1784951215, "exp": 1784994415
}

A resource server holding this token can see which workload the call came from, and act records the client and the platform that attested it.

How the token call carries no secret

PingFederate has no native support for attest_jwt_client_auth (draft-ietf-oauth-attestation-based-client-auth) and no SDK extension point to add a token-endpoint authentication method. Its native methods are client secret, mTLS certificate, and private_key_jwt. Left alone, PF would demand one of those in addition to the attestation.

So a servlet filter, ClientAttestationAuthFilter, is registered over /as/token.oauth2 in pf-runtime.war, the same mechanism this project already uses to register a logout-signal filter. When the two attestation headers are present it verifies them with the same code as the issuance criterion, resolves the client from the attestation's sub, and rewrites the request to authenticate to PF with private_key_jwt: a client_assertion signed by a deployment-held bridge key whose public half is registered in each client's JWKS. The workload never holds that key. PF sees a client authenticating with a method it supports; the workload sends only the draft's two headers.

RequestResult
Two attestation headers, no secret, no client_id200, token issued
No attestation headerspassed through; PF rejects the credential-less request
Attestation without a PoP401 invalid_client, rejected at the filter
Tampered attestation, or PoP with wrong aud401 invalid_client, PF never reached
Requested access above the attested ceiling403 access_denied at mint

The attestation is now the workload's only credential. Nothing shared or reusable is provisioned to the workload; the bridge key lives only in the PingFederate deployment and authenticates on the workload's behalf once its attestation has been verified. The issuance criterion runs independently on the token, so the attestation is checked twice: at the filter and inside PF.

Two caveats are worth stating. This registers a filter in PingFederate's own web application, which Ping does not document as an extension point, so it carries an upgrade-time re-validation cost. And the bridge key is a component the deployment holds on the workload's behalf; it is not a workload secret, but it is a key that must be protected like one. The design point stands: no per-workload credential is provisioned, and the workload authenticates with a platform-attested identity alone.

The three tokens that matter

Three JWTs are involved, each signed by a different party:

1 · Platform evidence
{
 "iss": "https://container.googleapis
         .com/v1/projects/…/clusters/…",
 "sub": "system:serviceaccount:
         demo:payment-agent",
 "aud": ["https://attester.example.com"],
 "exp": …
}
Signed by SPIRE, the GKE control plane, or Google's service-account signer. The workload holds no signing key for it.
2 · Client Attestation
{
 "iss": "https://attester.example.com",
 "sub": "demo-attest-gke",
 "cnf": { "jwk": { …instance key… } },
 "workload": {
   "spiffe_id": "spiffe://….svc.id.goog
                 /ns/demo/sa/payment-agent",
   "attributes": { "region": "EMEA", … }
 },
 "authorization_details": [ …granted… ]
}
Minted by the attester, 5-minute TTL. Binds the client id, workload identity, instance key and entitlement ceiling in one signed statement.
3 · Proof of possession
{
 "iss": "demo-attest-gke",
 "aud": "https://localhost:9031",
 "jti": "…one-time…",
 "iat": …now…
}
Signed with the instance key from cnf, fresh per request. An attestation replayed without that key fails verification.

Four platforms, one issuance flow

Each deployment runs the same five steps against the same servlet. What changes is which system attests the workload, and how much infrastructure you run yourself.

SPIRE on GKE GKE workload identity Vertex AI Agent Engine
Attestor SPIRE you operate in-cluster The GKE control plane Google's SA token signer (managed agent, no cluster at all)
Evidence SPIFFE JWT-SVID from the Workload API Projected service-account token (pod volume) Google-signed SA ID token (generateIdToken)
Trust bundle SPIRE's JWKS, pasted in Cluster's public OIDC JWKS, fetched by URL Google's public JWKS (oauth2/v3/certs)
SPIFFE identity …/ns/demo/sa/payment-agent under gke.banking.demo …/ns/demo/sa/payment-agent under <project>.svc.id.goog /sa/<sa-email> under a deployment trust domain
Runs where a GKE pod a GKE pod Gemini Enterprise Agent Platform (also Cloud Run / GCE)

A fourth deployment runs outside Google. The Railway workload has neither SPIFFE infrastructure nor a Google identity, so it acts as its own trust domain: it signs a spiffe://railway.demo/… JWT-SVID with a key whose public half is published in the CIMD. The issuance path is unchanged. The attester's requirement is that the evidence verifies against a trust bundle it is configured with, not that it came from any particular platform.

The same flow works with no SPIRE at all: GKE's own workload identity provides the evidence. It also works with no cluster at all. A Gemini Enterprise Agent Platform agent cannot export its managed Agent Identity credentials, but its runtime service account can mint a Google-signed ID token scoped to the attester's audience. That token is the evidence; its email claim maps to spiffe://<trust-domain>/sa/<sa-email>, and the same binding and ceiling checks apply.

The Google evidence paths, and the servlet support they need

SPIRE hands the attester a real SVID it can verify against a SPIFFE trust bundle. Google's two platforms do not issue SVIDs, so the attester cannot treat their tokens generically. Each Google path needs a dedicated validator in the issuance servlet that knows the token's shape: it verifies the Google-issued token, then synthesises a SPIFFE ID from its claims. Both validators implement the same EvidenceValidator interface, and the servlet selects one from the client's attestation_evidence setting. After validation every path produces a SPIFFE ID, so the resolver plugins and the entitlement ceiling downstream are identical.

GKE workload identity (gke-sa-token)

The evidence is the projected service-account token from step 2, signed by the GKE cluster's OIDC issuer. GkeTokenValidator checks the signature against the cluster's public JWKS (fetched by URL, key selected by kid), requires exp present and unexpired, requires aud to include the attester, and, when pinned, requires iss to equal the cluster issuer URL. The sub must be Kubernetes-shaped, system:serviceaccount:<ns>:<sa>. From that it builds the SPIFFE ID Google itself uses for GKE workload identity: 

attestation_evidence         = gke-sa-token
attestation_trust_domain     = <project>.svc.id.goog
attestation_bundle_url       = <cluster OIDC JWKS URL>
attestation_evidence_issuer  = <cluster issuer URL>         # optional, pins iss

# sub system:serviceaccount:demo:payment-agent
#   → spiffe://<project>.svc.id.goog/ns/demo/sa/payment-agent

Google service-account ID token (gcp-id-token): Agent Engine, Cloud Run, GCE

The evidence is a Google-signed OIDC ID token for the runtime service account, obtained from the metadata server's identity endpoint or from IAM Credentials generateIdToken, with the attester as audience. This is the evidence a workload has when its platform identity is a service account rather than a Kubernetes one, which is the Gemini Enterprise Agent Platform case. GcpSaTokenValidator checks the signature against Google's rotating JWKS, requires iss to equal https://accounts.google.com when pinned, requires aud to include the attester, requires exp present and unexpired, and requires an email claim. The sub is the account's opaque numeric id, so the stable identifier is email, and the mapped SPIFFE ID uses it. Google defines no canonical SPIFFE mapping for a bare service account, so the trust domain here is a deployment convention: 

attestation_evidence         = gcp-id-token
attestation_trust_domain     = <project>.gcp.example        # deployment convention
attestation_bundle_url       = https://www.googleapis.com/oauth2/v3/certs
attestation_evidence_issuer  = https://accounts.google.com   # optional, pins iss

# email payment-agent@<project>.iam.gserviceaccount.com
#   → spiffe://<project>.gcp.example/sa/payment-agent@<project>.iam.gserviceaccount.com

So each client declares which path it uses through four attestation settings: the evidence type, the trust domain that names the SPIFFE-ID space, the JWKS to verify against, and optionally the exact iss to require. The SPIRE path differs only in that its bundle is an inline JWKS rather than a URL. Adding a new platform means adding one more EvidenceValidator: verify that platform's token, then produce a SPIFFE ID.

AWS is supported the same way, by two more validators. EksTokenValidator (eks-sa-token) takes an EKS IRSA projected token, the direct analogue of the GKE path. AwsStsWebIdentityValidator (aws-sts-web-identity) takes the AWS-signed OIDC token from sts:GetWebIdentityToken (AWS Outbound Identity Federation), which gives any AWS workload, including a Bedrock AgentCore agent, a JWKS-verifiable JWT whose sub is the IAM role ARN. Both validators are built and tested; the AWS demo (PingFederate on EKS, an EKS workload, and a Bedrock AgentCore agent) deploys separately in deploy/aws-bedrock-demo.

What makes this more than authentication

Agent Identity establishes which agent is calling. The attestation adds an entitlement ceiling: an RFC 9396 authorization_details array stating the maximum this workload instance may request. At mint time the attester checks requested ⊆ attested and rejects anything above the ceiling, so no token is issued for it.

How this uses Google's agentic identity stack

This plugs directly into the identity model behind Gemini Enterprise Agent Platform. Google's Agent Identity gives every managed agent a lifecycle-bound SPIFFE ID and auto-managed X.509, with no developer-held long-lived keys. Its Agent Gateway authorizes agent-and-tool traffic at runtime through an ext_proc hook into PingAuthorize (the Ping integration).

Neither covers how an agent authenticates to an authorization server outside Google to obtain that token in the first place. That is what this implements: Google attests the agent, the attester converts that attestation into an OAuth Client Attestation carrying an entitlement ceiling, and PingFederate issues the token. It uses Google's own primitives: the spiffe://… naming, GKE workload identity, and the runtime service account's ID token for a managed agent. The last of these is needed because the managed Agent Identity X.509 credentials are not exportable to third parties.

How a Gemini Enterprise agent actually uses this

Concretely: a user asks a Gemini Enterprise agent to do something that needs a protected downstream resource, such as reading an account or submitting a quote. The agent has a Google Agent Identity (a SPIFFE ID) but no client secret for your authorization server. This is the moment the demo fills: the agent turns its platform identity into a scoped token, then calls the resource.

When agents call other agents (A2A)

When one agent delegates to another, the second agent has its own Agent Identity and runs its own attestation rather than reusing the first agent's token. Each agent authenticates as itself and gets its own entitlement ceiling, and the delegation chain is carried in actor claims. A compromised downstream agent holds only the ceiling it was attested for.

Standards it stands on

The components are all specified:

  • draft-ietf-oauth-attestation-based-client-auth – the two-header client authentication scheme (attestation + PoP)
  • SPIFFE – workload identity: JWT-SVIDs, trust domains, the spiffe://…/ns/…/sa/… naming Google adopted for GKE
  • RFC 9396 (Rich Authorization Requests) – the entitlement-ceiling vocabulary
  • OAuth client credentials – the grant type used

draft-ietf-oauth-spiffe-client-auth profiles this pattern directly, with SPIFFE credentials used as attestation-based client authentication, and Google's Agent Gateway assigns every managed agent a SPIFFE ID. The structure here (platform attests, attester converts, AS verifies) sits between the two. The Google service-account ID token covers the Gemini Enterprise Agent Platform case without that platform exporting any key material.

Implementation note: the classloader split. PingFederate evaluates token-endpoint OGNL criteria on its engine classloader, which cannot see classes inside pf-runtime.war's WEB-INF/lib. The module jar must also sit in server/default/deploy/, or the verification hook fails as an opaque OGNL "Method failed" with no stack trace. The webapp copy (servlets) and engine copy (OGNL hook) communicate only through request attributes keyed by plain strings, a deliberate cross-classloader contract.
