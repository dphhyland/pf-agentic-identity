How a Google workload becomes an OAuth client with no secret worth stealing

This demo answers one question: can a workload running in Google Cloud authenticate to PingFederate using what it is — its platform-attested identity — instead of a client secret someone provisioned and could leak? The answer, verified end-to-end on live Google infrastructure, is yes — three different ways, from a self-run SPIRE deployment all the way up to a managed Gemini Enterprise Agent Platform agent.

github.com/dphhyland/pf-agentic-identity  ·  demo: deploy/gke-spiffe-demo  ·  live explainer: gke-spiffe-demo-production.up.railway.app

The problem it solves

OAuth clients traditionally authenticate with a static credential — a client secret or a private key baked into config. For human-operated apps that's tolerable. For agents and workloads that are created and destroyed by the hundreds, it's the weakest link: secrets are duplicated across instances, outlive the workloads that used them, and say nothing about where the caller is actually running. Ping and Google's shared answer — the "runtime identity" model behind Google's Agent Gateway integration — is to derive the credential from the platform's own attestation of the workload, freshly, on every enrolment.

This demo implements that model with three cooperating parties:

Platform attestor — SPIRE, GKE, or Google's SA signer Client Attester — servlet inside PF's war PingFederate — the authorization server

The colors above carry through every diagram: blue is evidence issued by the platform, teal is the attestation the Client Attester mints, red is what PingFederate verifies at the token endpoint.

The flow, in five steps

The agent pod knows exactly two things at boot: a base URL and its client_id. Everything else it learns from the attester's discovery document.

  1. 1

    Discover

    GET /.well-known/client-attester?client_id=demo-attest-gke returns the issuance contract: the endpoints, the evidence audience the workload must mint into its identity token, the evidence type expected, proof requirements, and which RAR types it may request.

  2. 2

    Prove what you are

    The workload fetches identity evidence from the platform — a token only something actually running in that pod could obtain. Phase 1: a SPIRE JWT-SVID from the Workload API socket. Phase 2: a Kubernetes service-account token Google signs and projects into the pod.

  3. 3

    Bind a key

    The workload generates a fresh P-256 instance key, fetches a one-time challenge, and signs a proof-of-possession over it. This is the key the eventual credential will be cryptographically bound to — it never leaves the pod.

  4. 4

    Mint the Client Attestation

    POST /federation/attestation with evidence + instance key + proof. The attester validates the evidence against the platform's trust bundle, checks the SPIFFE ID is bound to this client, enforces the entitlement ceiling, and mints a short-lived (5-minute) Client Attestation JWT (draft-ietf-oauth-attestation-based-client-auth).

  5. 5

    Authenticate to the AS

    The workload calls PF's token endpoint carrying two headers — OAuth-Client-Attestation (the minted JWT) and OAuth-Client-Attestation-PoP (a fresh proof signed with the instance key). An issuance criterion verifies both, and PF issues the access token.

The three tokens that matter

The security of the whole scheme lives in how these three JWTs chain together:

1 · Platform evidence
{
 "iss": "https://container.googleapis
         .com/v1/projects/…/clusters/…",
 "sub": "system:serviceaccount:
         demo:payment-agent",
 "aud": ["https://attester.example.com"],
 "exp": …
}
Signed by SPIRE (Phase 1), the GKE control plane (Phase 2), or Google's SA signer (Phase 3). Proves what the caller is. The workload cannot forge it.
2 · Client Attestation
{
 "iss": "https://attester.example.com",
 "sub": "demo-attest-gke",
 "cnf": { "jwk": { …instance key… } },
 "workload": {
   "spiffe_id": "spiffe://….svc.id.goog
                 /ns/demo/sa/payment-agent",
   "attributes": { "region": "EMEA", … }
 },
 "authorization_details": [ …granted… ]
}
Minted by the attester, 5-minute TTL. Binds client, workload identity, instance key, and the entitlement ceiling into one vouched statement.
3 · Proof of possession
{
 "iss": "demo-attest-gke",
 "aud": "https://localhost:9031",
 "jti": "…one-time…",
 "iat": …now…
}
Signed with the instance key from cnf, fresh per request. A stolen attestation is useless without the key that never left the pod.

Three phases — climbing away from SPIRE, up to a managed agent

All three phases run the identical five steps against the identical servlet. The only thing that changes is who vouches for the workload — and each phase needs less of your own infrastructure than the last.

Attestor SPIRE you operate in-cluster The GKE control plane Google's SA token signer — managed agent, no cluster at all
Evidence SPIFFE JWT-SVID from the Workload API Projected service-account token (pod volume) Google-signed SA ID token (generateIdToken)
Trust bundle SPIRE's JWKS, pasted in Cluster's public OIDC JWKS, fetched by URL Google's public JWKS (oauth2/v3/certs)
SPIFFE identity …/ns/demo/sa/payment-agent under gke.banking.demo …/ns/demo/sa/payment-agent under <project>.svc.id.goog /sa/<sa-email> under a deployment trust domain
Runs where a GKE pod a GKE pod Gemini Enterprise Agent Platform (also Cloud Run / GCE)

Phase 2 was the first punchline: SPIRE was uninstalled before the run and the chain still completed, because GKE's own workload identity supplied everything a SPIFFE attestor would. Phase 3 goes further still — there is no cluster the workload controls at all. A Gemini Enterprise Agent Platform agent can't hand out its managed Agent Identity credentials, but its runtime service account can mint a Google-signed ID token scoped to the attester's audience. That token is the evidence; its email claim maps to spiffe://<trust-domain>/sa/<sa-email>, and the attester enforces the same binding and ceiling as before. Same servlet, same five steps, a third kind of platform.

What makes this more than authentication

Google's Agent Identity binds who the agent is. This design goes one step further: the attestation carries an entitlement ceiling — an RFC 9396 authorization_details array declaring the most this workload instance may ever request. At mint time the attester enforces requested ⊆ attested; anything over the ceiling dies before a token ever exists.

Standards it stands on

Nothing here is proprietary protocol:

  • draft-ietf-oauth-attestation-based-client-auth — the two-header client authentication scheme (attestation + PoP)
  • SPIFFE — workload identity: JWT-SVIDs, trust domains, the spiffe://…/ns/…/sa/… naming Google adopted for GKE
  • RFC 9396 (Rich Authorization Requests) — the entitlement-ceiling vocabulary
  • OAuth client credentials — the grant itself is boring on purpose

It also tracks where the standards are heading: draft-ietf-oauth-spiffe-client-auth profiles exactly this pattern (SPIFFE credentials as attestation-based client auth), and Google's Agent Gateway assigns every managed agent a SPIFFE ID. The demo's architecture — platform attests, attester converts, AS verifies — is the connective tissue between those two worlds, and Phase 3 shows it reaching all the way into the Gemini Enterprise Agent Platform without that platform having to expose a single key.

Field note — the bug worth remembering. PingFederate evaluates token-endpoint OGNL criteria on its engine classloader, which cannot see classes inside pf-runtime.war's WEB-INF/lib. The module jar must also sit in server/default/deploy/, or the verification hook fails as an opaque OGNL "Method failed" with no stack trace. The webapp copy (servlets) and engine copy (OGNL hook) communicate only through request attributes keyed by plain strings — a cross-classloader contract that now makes sense.
