Client Attestation on Google Cloud — the components

A workload proves what it is with a platform-signed token, an attester converts that into a short-lived Client Attestation bound to a key the workload holds, and PingFederate issues a token against it. Colour marks the role: platform evidence, the attester, PingFederate.

The request flow

  1. 1Discover. The workload GETs /.well-known/client-attester (static), follows it to /federation/attester-configuration?client_id=…, and learns the endpoints, the evidence audience it must use, and the RAR types it may request.
  2. 2Get evidence. It fetches a platform-signed identity token — SPIRE JWT-SVID (P1), GKE projected SA token (P2), or Google SA ID token (P3) — with aud set to the attester. The workload can't forge it.
  3. 3Mint. It POSTs the evidence + its instance public key + a challenge-bound proof to /federation/attestation. The attester validates the evidence against the trust bundle, checks the SPIFFE ID is bound to the client, enforces the entitlement ceiling, and returns a 5-minute Client Attestation.
  4. 4Authenticate. It calls /as/token.oauth2 with OAuth-Client-Attestation + -PoP headers. PingFederate verifies the attester signature, the PoP against cnf, and freshness — then issues the access token.

Where this sits in Google's agentic identity stack

This is not a parallel invention — it plugs into the identity model Google has built for Gemini Enterprise Agent Platform, and reuses its primitives:

Google building blockWhat it providesHow this demo uses it
Agent Identity platform Every managed agent gets a lifecycle-bound SPIFFE ID + auto-managed X.509, attested by the platform — no developer-held long-lived keys. (docs) We speak the same spiffe://… naming and treat the platform as the attestor. The managed X.509 isn't exportable to third parties yet, so Phase 3 uses the agent's runtime service-account ID token (which is exposable) as the evidence.
Agent Gateway runtime authz An ext_proc hook calls an external PDP (PingAuthorize) to authorize agent & tool traffic at execution time. (Google · Ping) Complementary leg. The gateway authorizes traffic between agents; this demo is the upstream leg — how the agent first proves itself to an external authorization server (PingFederate) to obtain the token it then carries through the gateway.
Workload Identity Federation for GKE platform Binds GKE pods to spiffe://<project>.svc.id.goog/ns/…/sa/… identities with a public OIDC issuer. (docs) Phase 2 evidence: the projected SA token is validated against that public JWKS and mapped onto Google's own canonical SPIFFE identifier.
The one-line relationship. Google attests the agent (Agent Identity) and authorizes its traffic (Agent Gateway → PingAuthorize). This demo fills the gap between: it converts Google's platform attestation into an OAuth Client Attestation carrying an entitlement ceiling, so the agent can authenticate to PingFederate and obtain a scoped token — with no shared secret and no key the agent has to hold.

Resolver plugins — how the attester maps identity → client

The workload never names a client. At mint time the attester tries each of its configured resolver plugins against the presented evidence: the plugin whose trust bundle verifies it and whose bindings contain the resulting SPIFFE ID supplies both the client identity and the entitlement ceiling (downscoping) the attestation carries. Plugins chain — several can be active at once — and the deployment's supported/active set is advertised in the discovery document.

PluginSource of the mappingUsed for
pf-client-metadata Each client's attestation_* extended properties in the PingFederate client store The default — no external document; config-as-code alongside the client itself
cimd A hosted Client ID Metadata Document the attester fetches by URL The mapping lives in git / a static host, independent of PF; this demo's cimd.json
openid-federation A signed OpenID Federation entity statement's spiffe_client_bindings claim Governance by a federation the attester already trusts, not a flat file

Workload introspection — SPIRE selectors feed the issuance policy

A bare SVID only proves a SPIFFE ID. After validation, the attester can introspect the workload further: look up the SPIRE registration selectors that produced that identity — k8s:ns:demo, k8s:sa:payment-agent, unix:uid:0, docker:image:… — and fold them into the attestation's workload.attributes. Selectors describe how SPIRE attested the workload, which is a stronger basis for policy than anything the workload asserts about itself, so they're available to condition the granted entitlement (downscope unless a specific namespace/service-account selector is present) before the ceiling is applied.

Two trust checks, two directions. The attester trusts the platform by verifying evidence against a trust bundle (SPIRE's JWKS inline, or Google's public JWKS fetched by URL). Separately, PingFederate trusts the attester by verifying the attestation's signature against a configured attester key. Neither trust relationship uses a secret the workload ever holds.
