Authenticating AWS workloads to PingFederate with platform identity instead of secrets

A workload on AWS authenticates to PingFederate using an identity token AWS already issues it, rather than a provisioned client secret. This is running on live AWS infrastructure: PingFederate on EKS, an EKS workload, and a Bedrock AgentCore agent in the managed runtime. The same attester also serves the Google demo; only the evidence validators differ.

The problem it solves

An OAuth client normally authenticates with a static credential: a client secret or a private key in config. For workloads and agents created and destroyed continuously, that credential is duplicated across instances, outlives the workloads that used it, and says nothing about where the caller runs. The alternative here is to derive a short-lived credential from AWS's own attestation of the workload, on each call. AWS gives a workload two shapes of verifiable identity; both work.

AWS identity provider – EKS cluster OIDC, or the account STS issuer Client Attester – servlet inside PF on EKS PingFederate – the authorization server

The flow, in five steps

The workload is configured with one value: the attester's base URL. It learns the rest from the discovery document, and it is never told which OAuth client it is.

  1. 1

    Discover

    GET /.well-known/client-attester returns a static document (RFC 8615) carrying the endpoints, the evidence audience, and the proof requirements. It carries no client_id.

  2. 2

    Prove what you are

    The workload obtains an AWS-issued identity token with the attester as its audience. On EKS that is the pod's projected service-account token. On Bedrock AgentCore (or Lambda, ECS, EC2) it is the token from sts:GetWebIdentityToken. Neither can be forged by the workload.

  3. 3

    Bind a key

    The workload generates a fresh P-256 instance key, fetches a one-time challenge, and signs a proof-of-possession over it. The credential is bound to this key, and the key never leaves the workload.

  4. 4

    Mint the Client Attestation

    POST /federation/attestation with the evidence, the instance key, and the proof, and no client_id. The attester validates the AWS token against the AWS JWKS, maps the identity to the client it belongs to, enforces that client's entitlement ceiling, and mints a 5-minute Client Attestation whose sub is the client it selected.

  5. 5

    Authenticate to the AS

    The workload calls PF's token endpoint with two headers, OAuth-Client-Attestation and OAuth-Client-Attestation-PoP, and no client_id or client_secret. A filter over the token endpoint authenticates the client to PF and a JWT access token is issued.

The two AWS evidence paths

AWS does not issue SVIDs, so each path needs a validator in the issuance servlet that knows the token's shape: it verifies the AWS-signed token against the relevant public JWKS, then synthesises a SPIFFE ID from its claims. Both implement the same EvidenceValidator interface the Google paths use.

EKS workload identity (eks-sa-token)

An EKS pod projects a service-account token with the attester as its audience, signed by the cluster's OIDC issuer. EksTokenValidator verifies it against the cluster JWKS, requires the Kubernetes sub, and maps it to a SPIFFE ID. The one place EKS differs from GKE is the JWKS location: <issuer>/keys, not /.well-known/jwks.json. 

attestation_evidence         = eks-sa-token
attestation_trust_domain     = eks.demo.aws
attestation_bundle_url       = https://oidc.eks.ap-southeast-2.amazonaws.com/id/<id>/keys
attestation_evidence_issuer  = https://oidc.eks.ap-southeast-2.amazonaws.com/id/<id>

# sub system:serviceaccount:demo:payment-agent
#   → spiffe://eks.demo.aws/ns/demo/sa/payment-agent

AWS Outbound Identity Federation (aws-sts-web-identity): the Bedrock AgentCore path

A Bedrock AgentCore agent has no JWT of its own that an external server could verify. Its workload access token is opaque and first-party only, in AWS's own words it "cannot be used for external services". But an AgentCore agent runs under an IAM execution role, so it calls sts:GetWebIdentityToken (AWS Outbound Identity Federation, GA re:Invent 2025) and gets an AWS-signed OIDC token with an account-specific public JWKS. AwsStsWebIdentityValidator verifies it, reads the IAM role ARN from sub, and maps it. The same call works for any AWS workload with an IAM role. 

attestation_evidence         = aws-sts-web-identity
attestation_trust_domain     = <account>.aws.demo
attestation_bundle_url       = https://<uuid>.tokens.sts.global.api.aws/.well-known/jwks.json
attestation_evidence_issuer  = https://<uuid>.tokens.sts.global.api.aws

# sub arn:aws:iam::<account>:role/agentcore-attest-demo
#   → spiffe://<account>.aws.demo/aws/<account>/role/agentcore-attest-demo

Bedrock AgentCore, in the real managed runtime

The AgentCore path is not simulated. The agent is packaged as an ARM64 container implementing the AgentCore Runtime contract (GET /ping, POST /invocations on port 8080) and deployed to Bedrock AgentCore Runtime with a PUBLIC network and the HTTP protocol. Its IAM execution role carries sts:GetWebIdentityToken. On InvokeAgentRuntime the agent obtains its web-identity token, runs the chain against PingFederate over the cluster's load balancer, and receives a JWT access token. The token's sub is the agent's role identity and act records the client and that it was attested. Nothing shared or reusable is provisioned to the agent.

The AgentCore identity model. Google gives a managed agent a SPIFFE identity it cannot export; AWS gives an AgentCore agent an IAM role and an opaque first-party token. Neither hands the agent a JWT to present to a third party directly. On both clouds the agent reaches a verifiable identity through a platform call: generateIdToken on Google, sts:GetWebIdentityToken on AWS. The attester turns that into an OAuth Client Attestation carrying an entitlement ceiling.

How the token call carries no secret

PingFederate has no native support for attest_jwt_client_auth and no SDK extension point to add a token-endpoint authentication method. So a servlet filter, ClientAttestationAuthFilter, is registered over /as/token.oauth2 in pf-runtime.war. When the two attestation headers are present it verifies them, resolves the client from the attestation's sub, and rewrites the request to authenticate to PF with private_key_jwt: a client_assertion signed by a deployment-held bridge key whose public half is registered in each client's JWKS. The workload never holds that key. PF sees a client authenticating with a method it supports; the workload sends only the draft's two headers.

RequestResult
Two attestation headers, no secret, no client_id200, token issued
Requested access above the attested ceiling403 access_denied at mint
Tampered attestation, or PoP with wrong aud401 invalid_client, PF never reached

The architecture

The AgentCore agent in a cross-cloud chain

Everything above gets an AWS workload a token from the AWS Authorization Server. The AgentCore agent also does the harder job: it takes a token issued by the Google Authorization Server, and exchanges it there, using nothing but its AWS-attested identity.

That works because the attestation is portable. The agent proves what it is to its own attester on EKS, with sts:GetWebIdentityToken as before, and gets a Client Attestation that names no particular Authorization Server. To use it against Google's AS it mints one extra artefact – a proof-of-possession whose aud is the audience that AS advertises. Nothing about the agent is pre-registered in Google Cloud beyond a client record; the trust in the AWS attester is resolved through an OpenID Federation chain, where each Authorization Server publishes its attester's signing keys under metadata.oauth_client_attester.jwks and a trust anchor vouches for each member's own keys.

The chain runs Google → AWS → Google → AWS: agent A on GKE gets a token for itself, the AgentCore agent exchanges it at the Google AS, a second GKE agent exchanges that at the AWS AS, and a mock resource in AWS decides. Each exchange is RFC 8693 delegation, so the token keeps the original sub and nests one actor per hop – arriving as {delivery, {agentcore, {payment}}}. The resource can name the workload the request started from and everyone who has handled it since.

A PoP minted for one Authorization Server is refused by the other, so a captured attestation and proof cannot be replayed sideways. And a valid, correctly-signed, unexpired token is still refused 403 by the resource when the party presenting it is not the delegate it was issued to – which bearer semantics alone cannot detect.

Standards it stands on

  • draft-ietf-oauth-attestation-based-client-auth – the two-header client authentication scheme
  • AWS IAM Outbound Identity Federation – sts:GetWebIdentityToken, the AWS-signed OIDC token for a workload's IAM role
  • EKS IRSA – projected service-account tokens with a public cluster OIDC issuer
  • SPIFFE – the spiffe://… naming the attester maps every identity onto
  • RFC 9396 – the entitlement-ceiling vocabulary
  • RFC 8693 (Token Exchange) – each cross-cloud hop, carrying the actor chain in act
  • OpenID Federation 1.0 – entity statements and trust chains, so each Authorization Server can resolve the other's attester
