# The sample app

A minimal SwiftUI app for iOS 17 that drives [AgentIdentityKit](../AgentIdentityKit/README.md) against an enrolment
service you name, with the real implementations: App Attest through DeviceCheck, the instance key in the Secure
Enclave, the owner's sign-in at PingOne through `ASWebAuthenticationSession`. It enrols, re-mints, refreshes the
user verification and forgets, shows the instance and a log, and captures App Attest vectors for
[U-0063](../../../docs/findings/U-0063.yaml). It holds no secrets and names no real tenant: every setting is a
placeholder you replace on the settings form, and the form's values stay on the phone.

App Attest and the Secure Enclave exist only on a physical device: in the simulator `DCAppAttestService.isSupported`
is false, and enrolment stops there with "App Attest is not supported on this device".

## What you supply

1. **An Apple Developer team and an App ID with the App Attest capability.** Set `DEVELOPMENT_TEAM` and
   `PRODUCT_BUNDLE_IDENTIFIER` in [project.yml](project.yml) and run `xcodegen generate` here, or set them in
   Xcode's Signing & Capabilities. The entitlement `com.apple.developer.devicecheck.appattest-environment` is
   `development`: Apple's sandbox, which the service accepts only with `APPLE_ALLOW_DEVELOPMENT=true`. A
   TestFlight, App Store or Enterprise build ignores the entitlement and uses production (Apple, "App Attest
   Environment", read 2026-09-27).
2. **A physical iPhone** on iOS 17 or later, with a passcode (the instance key is created behind `.userPresence`,
   so each key proof asks for Face ID, Touch ID or the passcode).
3. **An enrolment service the phone can reach**, [services/device-enrolment](../../../services/device-enrolment/README.md),
   started with:
   - `APPLE_TEAM_ID` and `APPLE_BUNDLE_ID` - your team and the bundle id above;
   - `APPLE_ALLOW_DEVELOPMENT=true` for a development build;
   - `ENROLMENT_ISSUER` - what you type as the audience on the form;
   - `PINGONE_ISSUER`, `PINGONE_CLIENT_ID` and `PINGONE_ACR_AAL2` - the application below and its passkey
     sign-on policy's name;
   - `REQUIRE_COMPLIANT_DEVICE=false`. With the default, every re-mint answers `device_not_compliant`: a new
     device starts `UNKNOWN`, and nothing sends a compliance signal until X-A15 and X-A17 (F-0004);
   - `REGISTRY=memory`, or `IDM_DATABASE_URL`, and `ENROLMENT_SIGNING_JWK`.
4. **A PingOne application**: a public native client with PKCE `S256`, the form's redirect URI registered on it
   (a custom scheme: `ASWebAuthenticationSession`'s browser hands the redirect to the session, and Apple's page on
   it names no scheme for the app to declare, so the sample declares none; not yet tried on a phone), and a
   sign-on policy that ends in a passkey. The user signing in must already have a passkey: the environment the
   service README names blocks a user with none.
5. **Later, an Entra app registration.** Nothing sends the Entra device token yet: the kit's
   `DeviceTokenProvider` throws until the `deviceid` spike on an Intune-managed iPhone
   ([U-0064](../../../docs/findings/U-0064.yaml)) and X-A17, and MSAL is not a dependency
   ([U-0065](../../../docs/findings/U-0065.yaml)).

## Capturing App Attest vectors

"Capture App Attest vectors" makes one App Attest key, attests it over the kit's commitment to a fixed thumbprint
(RFC 7515 Appendix A.3.1's key, the kit's vector) and a timestamped challenge, and makes three assertions over the
client data `renewal key proof`. The JSON it shares carries the key identifier exactly as `generateKey` returned
it, the same bytes as base64url, the attestation object and the assertions: the fields of
`libs/app-attest/src/test/resources/fixtures/macos-27.2-*.json`. The attested key's SPKI, which the assertion test
reads, comes from the attestation's credential certificate when the fixture is written. Run it in a development
build and in a production one; the aaguid in the authenticator data says which each was. It needs no enrolment
and no service.

## Build

```sh
xcodebuild -project clients/ios/SampleApp/SampleApp.xcodeproj -scheme SampleApp \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

That is what [.github/workflows/ios.yml](../../../.github/workflows/ios.yml) runs, and it succeeded on
2026-09-27 with Xcode 27.0; the build then launched in the iOS 27.0 simulator and showed its form. For a phone,
open the project in Xcode with your team set. The app has not been run on a device: that is David's step, with
the items above.

`SampleApp.xcodeproj` is generated by XcodeGen 2.45.4 from [project.yml](project.yml) and committed, so building it
needs only Xcode.
