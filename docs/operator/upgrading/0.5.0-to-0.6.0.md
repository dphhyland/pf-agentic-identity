# Upgrading from v0.5.0 to v0.6.0

For whoever runs a PingFederate built from this repository's artefacts and is on v0.5.0. v0.6.0 is Phase 3 of the
production programme, "secure by default": the production profile is enforced, and an unset
`OIDF_DEPLOYMENT_PROFILE` is production, so v0.6.0 is the release where a deployment that never set the profile first
meets refusals. [The release notes](../../releases/0.6.0.md) say what changed, package by package, and number every
"Before you deploy" item in package order; this page puts those items in the order to do them, says what to check
after the first boot, how to roll back, and what each consumer of this repository changes. The notes' own first item,
**Follow the upgrade guide, which puts these items in the order to do them.**, points here.

PingFederate does not move: v0.6.0 is built and tested against 13.1.3, the image `build/pf-version.env` records, as
v0.5.0 was. One PingFederate node only, as in v0.5.0 ([deployment-limits.md](../deployment-limits.md), F-0007, until
0.7.0).

## Before anything: run the preflight

Take `oidf-preflight.jar` and `SHA256SUMS` from the assets of the v0.6.0 release, check the jar, and run it on each
environment's settings - the container's environment, with the JVM's `-D` options and PingFederate's `run.properties`
system properties in one `JAVA_OPTS` line:

```
sha256sum --ignore-missing -c SHA256SUMS      # in the directory holding the downloaded assets
java -jar oidf-preflight.jar --env-file <your env file> --profile production
```

Java 17 or later runs it. [preflight.md](../preflight.md) gives the lines for a Docker env file, a Kubernetes
ConfigMap and `run.properties`, and what each line of output means.

- **Exit 0**: nothing the start-up sweep judges would be refused.
- **Exit 1**: a component would be refused. Each `REFUSED:` line names the setting, the fix and the components it
  refuses. Fix it, accept its risk in `OIDF_ACCEPTED_RISKS` (try that first with `--accepted-risks`), or switch the
  component off with `OIDF_<COMPONENT>_ENABLED=false`.
- **Exit 2**: the file or the arguments could not be read; the output names the line.

What it cannot see: anything only a running node knows (whether a database, Redis, a PDP, a key store or a trust
anchor answers); PingFederate's own configuration (data stores, OAuth clients and their extended properties, plugin
fields, access-token mappings, the licence); certificates; the stores refused in code (an in-memory store without the
`in-memory-state` risk, a database that is not PostgreSQL); and a setting the server refuses only when it reads it -
a removed name, a value that does not parse where the profile governs nothing, a secret set beside its `_FILE`
variant ([F-0427](../../findings/F-0427.yaml)). In a Docker env file, write values without quotes: Docker passes the
quotes to the process and the preflight removes them ([F-0426](../../findings/F-0426.yaml)). It holds every catalogue
of the release, so a line about a component the process you are checking does not run can be ignored
([F-0425](../../findings/F-0425.yaml)). The checklist below covers what it cannot see. An example from the release's
own rig (2026-10-01): the preflight passed a production environment that named no Redis and no SSF data store, and
the server then refused `SSF` and `ATTESTATION_ISSUER` (on by inference, since none of its settings was set) for
keeping state in memory, until `in-memory-state` was accepted. Switch off what you do not run, and give what you run
a store.

## Decide the profile

`OIDF_DEPLOYMENT_PROFILE` chooses it: `development` (trimmed, in any case) is development; unset, blank, `production`
and anything else are production (Phase 3 plan decision 3, which David has not confirmed). Production is what every
real deployment runs. `development` is for the conformance rig and the demos: nothing is refused there, the refusals
are logged as warnings, and each item below names what else development relaxes. Set it explicitly either way, so
that a reader of the environment knows which one you meant.

## The move, step by step

1. **Keep what you run now.** The v0.5.0 artefacts, the image you built from them, and PingFederate's configuration
   archive exported from the running node. Rolling back needs all three (Rollback, below).
2. **Run the preflight** on every environment's settings, as above, and fix each `REFUSED:` line.
3. **Work through the checklist below**, group by group; it is in the order to do things, and each line says whether
   the development profile relaxes it.
4. **Pull the v0.6.0 release and record it.** The assets: the 13 module jars the production image stages, with their
   `MANIFEST` (`build/pingfederate/stage-modules.sh`: v0.5.0 staged 12; `rs-validation` is the new one), `oidf.war`,
   `pf.plugins.pf-rar-paz-plugin.jar`, `pf.plugins.instance-registry-datasource.jar`, `gm-api.war`,
   `oidf-preflight.jar`, `PROVENANCE.txt` and `SHA256SUMS`. Check them against `SHA256SUMS` and record the tag.
5. **Build the image, or copy the jars.** With this repository's Dockerfile, the image stages what it needs. A build
   context you compose yourself also copies `pf-healthcheck.sh`; a deployment that copies jars into PingFederate
   itself deploys all 13, `rs-validation` beside `platform-pf`.
6. **Set the run-time environment**: `PING_IDENTITY_ACCEPT_EULA=YES`, `OIDF_DEPLOYMENT_PROFILE`, the nine component
   switches, `OIDF_ACCEPTED_RISKS`, `OIDF_TRUSTED_PROXIES`, the operator settings and whatever the checklist adds, and
   remove `OIDF_AUTHORITY_ADMIN_TOKEN`, `OIDF_SSF_BASE_PATH` and the JVM-wide hostname flag. Run the preflight once
   more on the result.
7. **Change PingFederate's configuration**, through your usual config-as-code path: the operator scopes and clients,
   the issued-details criterion on every access-token mapping an attested client uses, the RAR plugin's development
   switches off, the instance registry's data store, and ID-JAG left off where the RAR plugin's types may arrive.
8. **Deploy, then check the first boot** (After the first boot, below) before sending traffic to it.

## Before you deploy - the checklist

Every "Before you deploy" item of the v0.6.0 notes, by its bold title, grouped in the order to do them. Each link is
to the notes' numbered list, where the item says why, how to tell and what to change; the number is the item's
number there. "Development" says what `OIDF_DEPLOYMENT_PROFILE=development` relaxes, and "no escape" that nothing does.

- **Run the preflight against your environment before you upgrade.** ([item 43](../../releases/0.6.0.md#before-you-deploy), PR5) The class-path form of the same check; the jar supersedes it. Development: the list is a warning.

## After the first boot

1. **The start-up banner** in server.log lists each component with its state and how its switch was read, every
   violation of the profile, and the "code refusals" (a store in memory, a database that is not PostgreSQL). Nothing
   should say `REFUSED` or `FAILED_CONFIG` that you did not mean ([startup-audit.md](../startup-audit.md)).
2. **Ready**: `GET /agentic-identity/health/ready` on the runtime port answers 200 only when every enabled component is
   `READY` or `DEGRADED` ([health.md](../health.md)). Route the load balancer on it; the image's HEALTHCHECK checks live,
   not ready. Its 503 body is `{"status": "DOWN"}` and names no component: the banner and the health detail say which.
3. **The health detail**: `GET /agentic-identity/health` with a DPoP-bound PingFederate access token carrying
   `oidf.health.read` lists each component, its parts, their states and reasons, and `"graced": true` beside a
   component ready is counting as degraded ([operator-authentication.md](../operator-authentication.md)). It answers
   even while `OPERATOR_API` is refused: it is platform-pf's servlet behind the operator authenticator, not part of
   that component.
4. **The fail-soft rules**: a failed or disabled component closes only its own surfaces, each by its own rule
   ([components.md](../components.md#each-surfaces-rule)); PingFederate's own endpoints keep serving. A component
   that failed on a dependency is retried by the supervisor; one that failed on its configuration or was refused
   waits for a restart.
5. **A token for an attested client**, with the issued-details criterion on its mapping: server.log should carry no
   `attestation.issued.refused` you did not expect ([issued-details.md](../issued-details.md)).

## Rollback to v0.5.0

Roll back by deploying the v0.5.0 artefacts or image you kept, with PingFederate's configuration archive from before
the upgrade. What v0.6.0 wrote that v0.5.0 reads differently, read in the code on 2026-10-01 (v0.5.0 at 0d049d79,
v0.6.0's code at 600fa6b5):

- **SSF push headers encrypted at rest** (HSSF3). With `OIDF_SSF_SECRET_KEY` set, v0.6.0 stores a push stream's
  `authorization_header` as `ssfenc:v1:<kid>:<ciphertext>` (`PushHeaderCipher`). v0.5.0 has no cipher: it sends the
  stored value as it is (`PushDeliveryService`), so each such stream's receiver gets the sealed text as its
  Authorization header and refuses every push. After rolling back, have each push stream's receiver set its
  `authorization_header` again (a stream update), or delete and recreate the stream; nothing here decrypts headers
  back.
- **SSF stream columns and the SCIM table** (HSSF2). v0.6.0 adds `description`, `min_verification_interval` and
  `inactivity_timeout` to `ssf_streams` at run time (`ADD COLUMN IF NOT EXISTS`, nullable) and creates
  `ssf_scim_users`. v0.5.0 inserts by column name and reads rows by name, so it ignores both; the three stream members
  and the SCIM user records are simply not reported. Nothing needs removing.
- **The authority's tables** (HFEDL's conditional writes, Trust Marks, hosted entities). No `.sql` file or table
  changed between v0.5.0 and 600fa6b5: the conditional writes compare the status column that was already there
  (`UPDATE hosted_entity SET status = ? WHERE entity_id = ? AND status = ?`), so v0.5.0 reads every row v0.6.0 wrote.
- **PingFederate's configuration.** Remove the issued-details criterion from your access-token mappings before
  rolling back: `IssuedDetailsCriterion` does not exist in v0.5.0, and a criterion that fails denies every token its
  mapping issues. An operator client, scopes and a JWT access token manager added for v0.6.0 do no harm to v0.5.0.
  Clients registered explicitly under v0.6.0 keep "Require PKCE" and the defaults HFEDR gave them.
- **Settings v0.5.0 needs back.** `OIDF_AUTHORITY_ADMIN_TOKEN` (and device-enrolment's `PF_AUTHORITY_ADMIN_TOKEN`)
  for v0.5.0's operator API and health detail, which know no other credential; `OIDF_ATTESTATION_REQUIRE_BRIDGE_KEY`
  if you replaced it with `OIDF_ATTESTATION_AUTH_ENABLED` (v0.5.0 does not read the switches); the SSF receiver's
  `OIDF_SSF_RECEIVER_POLL_TOKEN` if it now uses a client; `OIDF_SSF_BASE_PATH` only if you had set it. v0.6.0's new
  names (`OIDF_*_ENABLED`, `OIDF_TRUSTED_PROXIES`, `OIDF_OPERATOR_*` and the rest) can stay: v0.5.0 lists unknown
  `OIDF_` names in its banner and refuses nothing.
- **The image.** v0.5.0's image accepts the EULA, opens 9080 and logs at DEBUG itself, as it did before the upgrade.
