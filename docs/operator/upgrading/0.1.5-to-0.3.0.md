# Upgrading from v0.1.5 to v0.3.0

For whoever runs a PingFederate built from this repo's artefacts and is on v0.1.5 or older. v0.1.5 is the last
release for PingFederate 13.0.x; v0.3.0 is the first for 13.1.3, and upgrades are supported from it onward.
[The release notes](../../releases/0.3.0.md) say what changed; this page says how to move, what to check before
you deploy, how to roll back, and what each consumer repository must change.

## The rule: PingFederate and the artefacts move as a pair

PingFederate 13.1 moved its servlet container from `javax.servlet` to `jakarta.servlet` (Jetty ee9). Every
servlet, filter and war in v0.3.0 is compiled against `jakarta.servlet` and the 13.1.3 SDK; every v0.1.x
artefact is compiled against `javax.servlet`. Neither loads on the other line: a `javax` filter fails the merged
`pf-runtime.war` on 13.1 with a 503, a `javax` `@WebServlet` is never mapped, and the v0.3.0 RAR plugin does not
link on 13.0 at all (it reads `AuthorizationDetailContext.getJakartaRequest()`, which 13.0 lacks).

So in one commit, never two:

- the image's `FROM` goes from `pingidentity/pingfederate:13.0.3-alpine_3.23.4-al21-latest` (v0.1.5's
  `build/pingfederate/Dockerfile`) to the tag and digest `build/pf-version.env` records -
  `pingidentity/pingfederate:13.1.3-alpine_3.24.1-al21-latest@sha256:0d559261d658222179b07de8b2c84a8aea3cb30c7be107970686f58ea9dd3a4a`
  (recorded 2026-09-26);
- every artefact you carry changes from the v0.1.5 set to the v0.3.0 set;
- `pf-runtime.war` is re-assembled against the 13.1.3 stock war with v0.3.0's `assemble-pf-runtime-war.sh`.

A repo's PingFederate tag and the line of the artefacts it consumes change together, or not at all.

## The move, step by step

1. **Pull the v0.3.0 release and record it.** The assets are the module set (`modules/`: nine jars named in
   `MANIFEST`), `oidf.war`, `pf.plugins.pf-rar-paz-plugin.jar`, `pf.plugins.instance-registry-datasource.jar`,
   `gm-api.war`, `SHA256SUMS` and `PROVENANCE.txt` - the same shape as v0.1.5's. Check the sums and keep the
   `commit:` and `tag:` lines, as [build/pingfederate/README.md](../../../build/pingfederate/README.md#consuming-a-release-rather-than-copying-jars)
   shows. `PROVENANCE.txt` says `PingFederate line: 13.1.x (jakarta.servlet)`; a set that says 13.0.x is the
   wrong set. Do not copy jars from a sibling checkout: the migration plan found a `modules/` directory holding
   jars staged on 30 August beside a `HEAD` of 15 September, and the MANIFEST guard passes such a directory
   because it checks the directory against its own manifest.
2. **Re-stage and re-assemble.** Delete any `modules/` you staged before, stage the v0.3.0 set, and run v0.3.0's
   `build/pingfederate/assemble-pf-runtime-war.sh` against the stock `pf-runtime.war` from the 13.1.3 image
   (the Dockerfile finds it in the base image and does exactly this). The script reads the stock war's
   namespace and refuses a jar compiled for the other one, and it maps seven filters where v0.1.5's mapped four:
   `FapiResourceServer`, `OAuthErrorDescription` and `OidfFrontChannelAutoRegistration` are new. A war assembled
   by the old script registers nobody at the authorization or PAR endpoints. The same jars go on the engine
   classpath (`server/default/deploy`) as before; the OGNL criteria's class names are unchanged.
3. **Change `FROM` in the same commit**, build, and boot with the archive you have. The image imports it through
   PingFederate's drop-in deployer at boot (`overlay/config-store/…DataDeployer.xml`: `ForceImport`,
   `ForceUnsupportedImport`). The migration plan records a 13.0.3 archive importing into 13.1.3; the archive is
   upgraded in memory as it is imported, and the file you staged is untouched.
4. **Read the first boot's log** against the checklist below. The refusals that stop a component are logged at
   start-up: a trust controller named with no anchor keys, a receiver enabled without its audience and token, a
   provisioner scope equal to the receiver scope, a switch that is neither `true` nor `false`, an attester JWKS
   with a private key in it, the old and new name of a setting holding different values.
5. **Re-export the archive on 13.1.3** once the first boot is right, from the admin API
   (`GET /pf-admin-api/v1/configArchive/export`, as `conformance/export.sh` does), and make that export the
   environment's archive from now on. An archive exported on 13.1.3 carries 13.1's settings - among them
   `Rfc7523bisCompliantAudienceVerification`, which an archive upgraded from 13.0 arrives with **off** and a
   production PingFederate should have **on** ([the audience switch](../../../servlets/pf-integration/README.md#the-pingfederate-audience-switch)).
   Keep the last archive exported on 13.0.3 as well: it is the rollback artefact, and nothing re-exports over it.
6. **Move the settings** in the checklist, then deploy.

## Rollback

Rollback is the 13.0.3 image with the v0.1.5 artefacts and **the last archive exported on 13.0.3** - the pair
that ran before, in one commit again. Never a 13.1.3-exported archive on 13.0.3: the tracked overlay sets
`ForceUnsupportedImport=true`, so a 13.0.3 image would attempt the import, and what happens then is untested
(migration plan, "What is not verified"). What v0.3.0 wrote while it ran is left behind: the extended
properties it stamped on clients, the `owner_client_id` column in `ssf_streams`, the `V101`-`V103` tables. The
v0.1.5 code ignores the properties and the tables; the column is nullable and the ownership rule it serves is
in v0.1.4 and later anyway, so v0.1.5 reads it. Nothing here has been rehearsed on a real environment.

## Before you deploy - the checklist

Each item says which version it arrived in. An operator on v0.1.5 has the v0.1.4 and v0.1.5 items already;
the consumers below had not moved past the 30 August jars when the migration plan last checked their trees
(2026-09-26), so for them every item is new.

1. **Declare the extended properties** (0.3.0). PingFederate drops an extended property it hasn't been told
   about, without a word, and this release relies on ten of them
   ([docs/extended-properties.json](../../extended-properties.json)). A registration whose client comes back
   without `status` is refused and the client disabled. The rig declares them in
   `conformance/terraform/extended-properties.tf`.
2. **Apply the migrations** (0.3.0) to the authority's database if hosted agents, Trust Mark grants or the key
   history live in one: `V101__hosted_entity_actor.sql` (without it every enrolment and status change fails),
   `V102__trust_mark.sql`, `V103__federation_key_history.sql`. There is no migration runner; apply them by hand
   and record it.
3. **Decide what happens to clients registered before 0.3.0** (0.3.0). They have no recorded expiry and count as
   expired: an automatic one renews on its next request, an explicit one is refused until its RP registers
   again. `OIDF_REGISTRATION_EXPIRY_ENFORCEMENT=log` for the migration records expiries and enforces nothing,
   the sweeper included; set it back afterwards.
4. **Re-assemble `pf-runtime.war`** (0.3.0) - step 2 above.
5. **The token filter admits every client, and fails closed** (0.3.0, `35780e9`).
   `RegistrationService.automaticRegister` is gone: `TokenEndpointAutoRegistrationFilter` looks at every token
   request that names a client (the assertion's `sub`, else `client_id`) and `RegistrationService.admit`
   decides - register from the presented chain or by discovery, renew, or refuse with 401 `invalid_client` or
   503 `temporarily_unavailable` (with `Retry-After`). Clients this module didn't register are never touched.
   `OIDF_AUTO_REGISTRATION_FAIL_CLOSED=false` restores the pass-through on failure, which v0.1.5 had; a value
   that is neither `true` nor `false` stops the filter starting.
6. **Relying parties register at the authorization and PAR endpoints** (0.3.0, `041ebfe`), through the new
   `OidfFrontChannelAutoRegistration` filter, from a signed request object or a PAR client assertion.
   `OIDF_AUTO_REGISTRATION_FRONT_CHANNEL=false` turns it off. Its refusals at the authorization endpoint are an
   error page, never a redirect; `OIDF_FEDERATION_ERROR_PAGE` names your own.
7. **Check every stored RAR plugin instance's switches** (0.3.0, PR #7 `554e688`). Every switch is read with its
   secure default when the stored configuration lacks the field: "Deny unless PERMIT" and "Prefix Attributes
   with Type" read as `true`; "Fail open on error", "Allow client-asserted principal", "Trust agent marker" and
   "Insecure TLS" as `false`. The one-argument read v0.1.5 used turned a missing "Deny unless PERMIT" **off**.
   An instance saved through the admin API or an archive that left a field out now refuses a PDP answer other
   than PERMIT, and sends its attributes prefixed with the type - a policy written against unprefixed names
   stops matching. Open each instance in the console and save it with every field present.
8. **The bridge assertion's `aud` is the issuer, as one string** (0.3.0, PR #6, pinned in PR #7 `621336e`; it
   was `[issuer, request URL]`). Nothing to configure. Turn `Rfc7523bisCompliantAudienceVerification` on in
   production - step 5 above - and check your other clients first: one that addresses its assertion to the token
   endpoint, as OpenID Connect Core §9 says to, is refused once the switch is on.
9. **Bind each attesting client to its attesters** (v0.1.4, `faa0cdc`, 2026-09-15). A client's entry in
   `OIDF_BRIDGE_SIGNING_KEYS` names the attesters that may vouch for it. The token endpoint answers 401 to an
   attestation from a trusted attester the client is not bound to, and - by default - to a client whose entry
   names none. `OIDF_ATTESTATION_REQUIRE_ATTESTER_BINDING=false` relaxes only the unbound case.
10. **Pin the trust anchor's keys** (v0.1.4, `7d05d71`, 2026-09-15). No chain validates without
    `OIDF_FEDERATION_TRUST_ANCHOR_JWKS`, required whenever a trust controller is named - public keys only, each
    with its own `kid`. A missing key does not stop PingFederate booting: the token-endpoint filters log it at
    start-up and refuse every request that needs a chain, and the registration servlet fails to initialise.
    `tools/pin-trust-anchor.py` captures the keys and prints their thumbprints. The old name
    `OIDF_TRUST_ANCHOR_JWKS` is still read, with a warning; the two names holding different values stop
    PingFederate starting ([configuration](../../federation/configuration.md)).
11. **Name the owner of the SSF streams that exist already** (v0.1.4, `07e1979`, 2026-09-22). A stream belongs
    to the client that created it, and streams created before this have no owner: nobody is admitted to them,
    so a poll stream answers its receiver 404 until `OIDF_SSF_UNOWNED_STREAM_OWNER` names that receiver or the
    owner is set in the store ([ssf README](../../../servlets/ssf/README.md#stream-ownership) has the SQL). The
    `tables` store adds `owner_client_id` to `ssf_streams` at boot; upgrade every node that shares a store
    together, because an old node writes streams with no owner.
12. **Expect the SET backlog to go** (v0.1.4, `daf63ea`, 2026-09-22). `setTtlSeconds` is enforced: the first
    tick after the upgrade deletes every undelivered SET older than the TTL (7 days by default) in one
    statement, poll and push streams alike. An unowned poll stream loses anything older than the TTL while it
    waits for an owner - name the owner before the TTL passes.
13. **Give provisioning its own scope, and the receiver its audience and token** (v0.1.5, `639c678`,
    2026-09-23). `/ssf/scim/v2/Users` takes `OIDF_SSF_PROVISIONER_SCOPE` (for example `ssf.provision`) and
    nothing else: unset, every SCIM call is 403; equal to the receiver scope, the transmitter doesn't start. A
    body `aud` must be the caller's client id or one `OIDF_SSF_ALLOWED_AUDIENCES` lists for it. An enabled
    receiver refuses to start without `OIDF_SSF_RECEIVER_AUDIENCE` and `OIDF_SSF_RECEIVER_ENDPOINT_AUTH_TOKEN`.
14. **The switches that guard something are strict** (0.3.0). `OIDF_REQUIRE_METADATA_POLICY`,
    `OIDF_ATTESTATION_REQUIRE_BRIDGE_KEY` and `OIDF_ATTESTATION_REQUIRE_ATTESTER_BINDING` are `true` or `false`,
    or PingFederate doesn't start. `OIDF_FEDERATION_ATTESTER_JWKS` must hold public keys. The federation
    settings and the registration filters' init-params are parsed strictly. `OIDF_TRUST_CONTROLLER_HOST`,
    `OIDF_TRUST_ANCHOR_JWKS` and `OIDF_TRUST_CONTROLLER_IGNORE_SSL` are superseded by their `OIDF_FEDERATION_`
    names. `token_endpoint_auth_method` is no longer written as an extended property.
15. **A criterion that throws denies the token** (verified 2026-09-26 on the rig, PingFederate 13.1.3.0). An
    access token mapping's OGNL issuance criterion whose expression throws - `1/0 == 1`, and a method call
    that throws, `@java.lang.Integer@parseInt('not-a-number') == 1` - answered a client-credentials request
    that had succeeded a moment before with 400 `invalid_grant` and the criterion's Error Result as
    `error_description`; `server.log` recorded `ERROR [TokenAuthorizationIssuanceCriteriaChecker] Exception
    occurred while trying to resolve ognl expression` and `Actual Value(s): false (Exception)`, and `audit.log`
    a `failure`. So an issuance criterion fails **closed**: a deployment whose only token-endpoint gate is
    `ClientAttestationUtils.validateClientAttestation(#this)` or `OIDFederationUtils.validateTrustChain(#this, …)`
    refuses every gated token if the engine-classpath jar is missing, is the wrong line (the v0.1.5 jar throws
    `ClassCastException` on 13.1), or the criterion throws for any other reason - loudly, in the log above, not
    by issuing tokens. An expression that names an attribute the context lacks is refused when it is saved
    (422 `ognl_expression_invalid_attribute`) and never reaches a request. Detail:
    [docs/unverified.md](../../unverified.md).

## The consumers

Three repositories consume this one, named in `.github/workflows/release.yml`'s header; the facts below are
what this repository's documents recorded ([the migration plan](../../pf-13_1-jakarta-migration-plan.md#the-consumers),
read on 2026-09-24 and its step 7 re-checked on 2026-09-26) and what commit `639c678` recorded about SCIM. None
of the three repositories was opened for this guide, so whether any has moved since is not known.

**idp-agentic-demo** vendors `oidf.war`, `gm-api.war`, the plugin jar and the legacy single
`pf-oidf-modules.jar` in its tree, on its own 13.0.3 `Dockerfile`, without the assemble script, and on
2026-09-26 its `Dockerfile` still named 13.0.3. It must bump its `FROM` to the 13.1.3 tag and digest and
re-vendor the v0.3.0 set in one commit - the hazard there is doing either without the other - and it needs
`pf-runtime.war` assembled by v0.3.0's script, because the filters are what the file it vendors does not carry.
It runs the OGNL criterion as its only token-endpoint gate, so with the v0.1.5 jar on a 13.1.3 engine
classpath every gated token is refused (item 15), not issued. It also bakes the PingOne MFA integration kit, a
third-party `javax`-era SDK plugin, which has not been tested on 13.1. Not checked: whether its `FROM`, its
vendored artefacts or the kit have moved since 2026-09-26.

**pf-oidf-modules** takes delivery two ways. Its deploy workflow checks this repo out with no `ref:` and pins
its own `PF_IMAGE` for the compile classpath, and was deliberately disabled (an unconditional `exit 1` in its
secrets step). The path that runs is by hand: `compose-context.sh` against a sibling checkout, then a deploy.
That sibling must be at `v0.3.0`, `modules/` deleted and re-staged first (the script re-stages only when
`MANIFEST` is absent), and its export helper - which still named 13.0.3 on 2026-09-26 - moved to 13.1.3. Its
bootstrap and probe drive SCIM with the `ssf.manage` token and the probe sends its own `aud`; both break until
`OIDF_SSF_PROVISIONER_SCOPE` and `OIDF_SSF_ALLOWED_AUDIENCES` are configured (item 13). Its Terraform names the
OGNL criteria by class; those names are unchanged. The `Automatically registered federation client` log line
the demo reads is unchanged. Not checked: whether the workflow is still disabled, and what the helper names now.

**pf-agentic-identity-domain-authority** builds from a sibling checkout and pins no image tag of its own, so it
inherits this repo's `FROM`; its `REBUILD.md` called `build-module-jar.sh`, superseded and hard-coded to
`*-0.1.0.jar` names. Pin the sibling at `v0.3.0`, record it in `REBUILD.md`, re-stage with
`stage-modules.sh`, and rebuild its images from the 13.1.3 base. Its phone-simulator builds against
`device-enrolment` and `app-attest` from GitHub Packages, which now publish as `0.3.0`. Its rigs use the
attestation filter and the federation chain, so items 9 and 10 apply to their variables. Not checked: any of
its files.

## What this page rests on

The image tags: `git show v0.1.5:build/pingfederate/Dockerfile` and `build/pf-version.env` at v0.3.0. The
filters: `assemble-pf-runtime-war.sh` at each tag. The import flags: `build/pingfederate/overlay/config-store/`.
The export: `conformance/export.sh`. Which version each item arrived in: `git tag --contains` on the commit
named, run 2026-09-26. The probe: run 2026-09-26 on the rig, recorded in
[docs/unverified.md](../../unverified.md). The consumers: the migration plan and commit `639c678`.
