# 0.5.0 (2026-09-29) - Phase 2: foundations, the platform the rest is built on

0.5.0 is Phase 2 of the production programme. Every shipped module now stands on two shared libraries,
`libs/platform` and `libs/platform-pf`: one reading of the deployment profile, one trust-all TLS context, strict
settings parsers, a settings catalogue per component, events catalogued with a PII class per field, bounded
metrics, health endpoints, managed background threads, a pooled Redis client, an outbound HTTP client that connects
only to the address it checked, and a lifecycle listener that audits every war at start-up and closes what it
opened at undeploy. The configuration reference is generated from the catalogues and held to the code both ways;
every store's tests run on PostgreSQL, which is now the only database the stores accept; the image is built,
tested and scanned in CI and required for a release. Each package has its own section below; the "Before you
deploy" list is the union of what they ask of a consumer.

**Read "Before you deploy" first.** Several changes stop things working until something is done: four jars a
consumer that copies jars must now ship, two federation settings read as strict JSON, H2 and HSQLDB refused,
`filters.xml` and the assembler in a composed build context, federation fetches that refuse more addresses and
ignore a JVM proxy, and a stricter SSF receiver.

## Before you deploy

1. **If you build or deploy `gm-api.war`, expect its new coordinates underneath and two jars inside it** (F-3,
   X-C01, F-2). gm-api keeps its own coordinates, `au.com.idpartners:gm-api`, and is still not published to
   GitHub Packages; the release asset `gm-api.war` is where it comes from. What changed: its pom imports this
   repository's BOM and compiles against the real coordinates of what PingFederate provides
   (`com.pingidentity.pingfederate:pingfederate-sdk`, `jakarta.servlet:jakarta.servlet-api`, `jose4j`,
   `jackson-databind`, `jackson-core`, all `provided`), so a build of it needs only the two jars the
   `pf-provided-jars` action installs (`pf-protocolengine` and `pingfederate-sdk`) and nothing under
   `local.pingfederate`; a script that installed the old `local.pingfederate:*` jars to build it can drop those
   steps. And `gm-api.war` now carries `platform-<version>.jar` and `platform-pf-<version>.jar` in its
   `WEB-INF/lib`, which give it its own start-up banner and its own health under
   `/gm-api/agentic-identity/health/{live,ready}`. Deploy the war as it comes; do not strip those jars out of it,
   or its servlets fail with `NoClassDefFoundError: com/pingidentity/ps/oidf/platform/...`. How to tell: `unzip -l
   gm-api.war` lists both under `WEB-INF/lib`.
2. **Give the Redis pool room if a node sends Redis more than eight commands at once.** (C2) 0.4.0 opened a new
   connection whenever every pooled one was busy, and kept four; 0.5.0 opens at most `OIDF_REDIS_POOL_SIZE`
   (default 8), and a command that waits more than `OIDF_REDIS_BORROW_TIMEOUT_MS` (default 1000) for one fails as
   Redis unavailable - a 503 at the token, challenge and attester endpoints. An attested request sends a few
   commands (a challenge's `DEL`, a proof's `SET NX`) and holds a connection only for each one's round trip, so
   what counts is how many commands are in flight at once: a node that keeps more than eight busy - many
   attested requests at once, or a Redis far away - raises `OIDF_REDIS_POOL_SIZE` (up to 256). Nothing else about
   Redis changes: no setting was renamed, and the URL, the CA file and the plaintext rule mean what they meant.
3. **Update anything that looks for the old thread names.** (C3) A thread dump, a JVM monitoring rule or a log
   pattern that names `oidf-registration-sweeper`, `oidf-subordinate-refresh`, `ssf-push-delivery`,
   `ssf-poll-receiver`, `ssf-boot-retry` or `oidf-platform-close-<resource>` will not find them: the Notes give
   the new names. Nothing else changes: no setting, no endpoint, no log line of the jobs' own.
4. **Move an H2 or HSQLDB store to PostgreSQL.** (DB1) A deployment whose authority store URL
   (`OIDF_AUTHORITY_JDBC_URL`, the `oidf.authority.jdbc.url` system property or the `jdbcUrl` init parameter)
   or SSF store URL (`OIDF_SSF_JDBC_URL`) begins `jdbc:h2:` or `jdbc:hsqldb:`, in any case, no longer starts
   that store. The SSF transmitter logs an ERROR and retries every 30 s, and stays down. `HostedEntityServlet`
   fails its init; `FederationAdminServlet` logs that hosting could not be configured, and fails its init too
   when the URL comes from the environment or a system property. Where Trust Mark issuing or the key history is
   enabled as well, `OpenIdFederationServlet`'s init fails, and because it loads at start-up that fails the whole
   `pf-runtime.war` (seen on the rig 2026-09-27 for a throwing init, commit 053a264). A PingFederate data store
   id (`OIDF_AUTHORITY_DATA_STORE_ID`, `OIDF_SSF_DATA_STORE_ID`) that names an H2 or HSQLDB data store - such as
   PingFederate's own bundled HSQLDB - is refused too, on the store's first connection: every use of that store
   fails with a message naming PostgreSQL, and the `tables` SSF store, which takes a connection at boot to create
   its tables, does not start. The check reads the product name the driver reports (`HSQL Database Engine` and
   `H2`, read with the image's own java 21 from the image's `hsqldb.jar` 2.7.1 and `h2.jar` 2.2.224,
   2026-09-28). Point the URL, or the data store, at PostgreSQL.

   Both databases were offered before this release. Up to 0.4.0 the showcase's settings reference said the
   authority store URL needed "the driver class (postgresql, hsqldb or h2 by URL prefix)", listed the driver
   setting as `org.postgresql.Driver | org.hsqldb.jdbc.JDBCDriver | org.h2.Driver`, and said the SSF store URL
   loads `org.postgresql.Driver` or `org.hsqldb.jdbc.JDBCDriver`. The SSF README and the 0.4.0 release notes
   record the `tables` store's push selection run on the HSQLDB 2.7.1 the PingFederate 13.1.3 image ships
   (U-0078, 2026-09-27), and `JdbcSsfStore`'s class comment says its SQL is kept to what "HSQLDB (PF's bundled
   DB)" accepts. The code accepted `jdbc:hsqldb:` for the SSF store from commit b00fe2e (2026-07-19) and both
   prefixes for the authority store from commit 01fbc20, and the image ships both drivers in
   `server/default/lib`, so a deployment may well have used either.
5. **Name the test database with OIDF_TEST_JDBC_URL.** (DB1) Developers and any CI that builds this repository set
   `OIDF_TEST_JDBC_URL`, `OIDF_TEST_JDBC_USER` and `OIDF_TEST_JDBC_PASSWORD`, or leave Docker running for
   Testcontainers. The user must be allowed `CREATE DATABASE`, because each test class creates and drops a
   database of its own. `IDM_TEST_JDBC_*` still work in 0.5.x, with a warning, and go after it. A CI job with
   `CI=true` and no Postgres now fails the store suites rather than skipping them. See CONTRIBUTING.md,
   "Tests that need Postgres".
6. **Deploy `platform-<version>.jar` and `platform-pf-<version>.jar` wherever you deploy `oidf-jose` and
   `pf-integration` today.** (F1) A consumer that builds its image from this repository's
   `build/pingfederate/Dockerfile` and `stage-modules.sh` gets them with nothing to do. A consumer that copies
   jars itself - pf-oidf-modules stages them, idp-agentic-demo commits built artefacts - must put both jars in
   both places PingFederate loads the modules from: the `pf-runtime.war` merge (`WEB-INF/lib`) and
   `server/default/deploy`, the engine's classpath where the OGNL criteria run. At 0.5.0 neither is optional.
   oidf-jose and rar-model depend on platform, and every staged module reaches it through them: the deployment
   profile, `InsecureTls`, the settings parsers, events, the Redis client, the managed executors and the
   outbound HTTP client are all platform's. pf-integration and attestation-issuer depend on platform-pf:
   `PfInternals`, the audit sink, health and the lifecycle listener. Without them the first class that calls one
   fails with `NoClassDefFoundError: com/pingidentity/ps/oidf/platform/...` - a filter or load-on-startup servlet
   at deploy, an OGNL criterion on the first token request that evaluates it - and the war assembler refuses to
   build `pf-runtime.war` when no staged jar holds the lifecycle listener `filters.xml` registers, which is
   platform-pf's. The RAR plugin and ciba-sim carry their own relocated copy of platform and need neither jar.
   device-enrolment, a service of its own, needs `platform-<version>.jar` on its classpath (its build copies it
   to `target/dependency`). Compare your deployed jars with the release's `MANIFEST`, which names every one.
7. **Give PingFederate ten seconds or more to stop.** (F2) At a stop each war's listener now closes what that war opened -
   background jobs, its metrics MXBean, its Redis connections - and waits up to five seconds for them, before
   PingFederate's own shutdown. Wherever PingFederate runs, set a stop grace period of ten seconds or more (Docker's
   `stop_grace_period` or `docker stop -t`, Kubernetes' `terminationGracePeriodSeconds`). The rig's container was
   created with a one-second stop timeout, so a plain `docker stop` killed PingFederate (exit 137), while
   `docker stop -t 30` stopped it cleanly in about five seconds (F-0211).
8. **Expect `Client Attestation`, not `OpenID Federation`, in the `protocol` column of the attester's evidence
   conflict records.** (O1) `attestation.evidence.conflict` - the attester refusing instance evidence already bound to
   another key or client - is an attestation event, and its audit record now says so. Nothing else in the audit
   log changes: every federation record keeps `OpenID Federation`, and the event, status, subject, connection,
   role, `ip` and description columns are written as before. If you find these records by filtering `audit.log`
   on the protocol, add `Client Attestation` to the filter. Deploy the attester's jar from the same release as
   `pf-integration`: its catalogue ships in that jar, and without it the conflict record keeps its code, status
   and subject but loses its fields (a WARN line in server.log says so).
9. **Look for three configuration lines under a new logger name.** (O1) The warnings that `OIDF_EVENTS_AUDIT` is neither
   `true` nor `false` and that `OIDF_EVENTS_MAX_VALUE_LENGTH` is not a number, and the DEBUG line saying an audit
   write was skipped, keep their text and are now written by
   `com.pingidentity.ps.oidf.platform.pf.audit.PfAuditSink` instead of `com.pingidentity.ps.oidf.pf.PfAuditEventSink`.
   The DEBUG line saying a second event sink was ignored now reads "The event sink is already configured; a second
   configuration was ignored", on `com.pingidentity.ps.oidf.platform.events.Events`. Event lines themselves - their
   text, their logger (`com.pingidentity.ps.oidf.federation.event.<family>`) and their level - are unchanged. A
   log4j2 filter or alert on the old logger names needs the new ones.
10. **`OIDF_ACCEPTED_RISKS` is new, and its format is checked.** (PR1) It lists the risks a production deployment
    accepts, as ids from a fixed registry (`no-metadata-policy`, `attester-binding-off`, `registration-fail-open`,
    `expiry-log-mode`, `pdp-fail-open`, `pkce-off`, `resolve-any`, `audit-off`, `in-memory-state`), each alone or
    as `id@YYYY-MM-DD`, the last day it holds; `expiry-log-mode` must carry a date. An unknown id, a date that is
    not one, an expired date and an id named twice are refused, each with a message naming the entry. In this
    release nothing reads the list to refuse anything: PR-2 and PR-5 (0.6.0) make the production profile refuse a
    risky switch whose risk is not accepted. Leave it unset for now, or write it in the checked format; the
    start-up audit banner (F-2, in this release) counts the entries it did not accept and logs each at WARN,
    naming it.
11. **Copy `filters.xml` and `assembler/` into a build context you compose yourself.** (RI5) A consumer that builds with
    `docker build build/pingfederate` after `mvn package` and `stage-modules.sh` has nothing to do. A consumer that
    copies files out of `build/pingfederate` into its own context (pf-oidf-modules' `compose-context.sh` copies
    `Dockerfile`, `assemble-pf-runtime-war.sh`, `pf-entrypoint.sh`, `modules/` and `overlay/config-store/`) must
    also copy `filters.xml` and the `assembler/` directory `stage-modules.sh` now writes beside `modules/`, and
    must build this repository's whole reactor first, which it already does. Without them `docker build` stops at
    the assembler's `COPY` with `"/assembler/war-assembler.jar": not found` (checked 2026-09-28), so no image is
    built without its filters.
12. **Give the script Java 17 or later where you run it outside Docker.** (RI5) The command line is unchanged:
    `assemble-pf-runtime-war.sh STOCK_WAR MODULES JOSE4J_JAR OUT_WAR [PROFILE]`. It now runs
    `$JAVA_HOME/bin/java` (or `java` on the `PATH`) with the staged `assembler/war-assembler.jar` and the
    `filters.xml` beside it (`WAR_ASSEMBLER_JAR` and `WAR_FILTERS_XML` move them). With no Java or no jar it
    refuses with exit 1 and deletes `OUT_WAR`, as any other refusal does. The image build uses the base image's
    own Java 21, so the Dockerfile needs nothing more.
13. **Expect a refusal where the script used to leave a registration alone.** (RI5) The script skipped any filter whose
    name was already in the stock `web.xml`. The assembler keeps one only if it is exactly as declared - the same
    class, one mapping, the same paths, no servlet-name or dispatcher - and refuses the war otherwise, naming what
    differs. A stock war from the base image has none of these names, so this bites only a war that was
    hand-edited or assembled by something else. Re-assembling the assembler's own output is accepted and writes
    the same war.
14. **Check whether federation fetches go through a proxy set for the JVM.** (S5AR) `OutboundHttp` connects directly to
    the checked address and ignores `https.proxyHost`, `http.proxyHost` and `socksProxyHost`; the JDK client used
    the JVM's default proxy selector, which reads them. A PingFederate that reaches federation peers, JWKS URIs or
    an AuthZEN PDP only through such a proxy will find those fetches fail to connect. Neither pf-oidf-modules nor
    idp-agentic-demo sets one (read 2026-09-28). If yours does, allow direct egress to those peers before upgrading.
15. **Check that certificates name the hosts you fetch from, even with OIDF_FEDERATION_IGNORE_SSL_ERRORS on.** (S5AR) The
    JVM-wide `-Djdk.internal.httpclient.disableHostnameVerification=true` governs the JDK client only, and nothing
    here turns host name checking off. idp-agentic-demo's `pingfederate/Dockerfile:73` sets that property (finding
    F-0035), so a federation peer, trust controller or PDP whose certificate does not name the host in the URL it is
    fetched by - an IP address, or an internal name the certificate lacks - worked there before and is now refused
    as a TLS failure. Fix the certificate or the URL.
16. **Check that no peer is served from a newly refused address.** (S5AR) Federation fetches now refuse the ranges listed
    in the Changelog. A name that resolves to both a public and a private address was refused before as well, and
    still is. A trust controller or other operator-configured endpoint on such an address still passes when it is
    exempted by `trusting()` or named in `OIDF_FETCH_HOST_ALLOWLIST`.
17. **Check that no single peer needs more than 32 requests from one node at once.** (S5AR) Only a peer that is slow as well
    as busy can fill the 32 places: a request waits for a place up to its own 15 s deadline before it fails. A
    trust controller answering in a few hundred milliseconds serves about a hundred requests a second from each
    node before anything waits.
18. **Check that `OIDF_AUTHORITY_METADATA_POLICY` and `OIDF_FEDERATION_SUBORDINATE_CONSTRAINTS` are each one
    well-formed JSON object.** (ST12) They are now read by `platform.json`, which refuses what Jackson read without
    complaint: a member name used twice in one object (Jackson kept the last), anything after the object (Jackson
    ignored it), nesting deeper than 32, a number written with more than 128 characters, and a string holding half
    a surrogate pair. Either setting holding one of these now stops PingFederate starting, with
    `OIDF_AUTHORITY_METADATA_POLICY: not a JSON object` (or the other name) in the log. Everything Jackson read
    otherwise reads the same values; numbers are now `BigDecimal`, which the metadata policy and the constraints
    already compare by value, and an exponent past a double's range, such as `1e400`, is kept exactly where
    Jackson read it as infinity. To check a value for the first two before you upgrade, pipe it into
    `python3 -c 'import json,sys; json.loads(sys.stdin.read(), object_pairs_hook=lambda p: dict(p) if len({k for
    k, _ in p}) == len(p) else sys.exit("duplicate member name"))'`, which refuses both.
19. **An SSF JDBC store on a database that is not PostgreSQL.** (ST3C) `JdbcSsfStore`'s two reads of pending SETs now say
    `COLLATE "C"`, which is PostgreSQL's syntax: on MySQL 8.4 it fails with `Unknown collation: 'C'` (checked
    2026-09-28), so on a MySQL data store every `peek` and `dueForPush` fails where the old ORDER BY ran. H2 and
    HSQLDB are already refused at boot, and 0.5.0 supports PostgreSQL only.
    If `jdbcUrl` or `dataStoreId` points the transmitter at another engine, move it to PostgreSQL before upgrading.
20. **Declare the new extended properties.** (ST4) A deployment that diffs its extended-properties Terraform against
    `docs/extended-properties.json` sees 24 names it has not seen: 21 `attestation_*` names and the three
    `trust_chain_*` limits. Declare every one of them, as `conformance/terraform/extended-properties.tf` does.
    PingFederate drops an extended property it has not been told about without a word, so a per-client attestation
    policy, chain limit or issuance setting written to a client is simply not applied (F-0041).
21. **Deploy `shared-signals-<version>.jar` wherever you deploy `ssf-<version>.jar`.** (XA14) A consumer that builds its
    image from this repository's `build/pingfederate/Dockerfile` and `stage-modules.sh` gets it with nothing to do.
    A consumer that copies jars itself must put it beside `ssf`'s in both places PingFederate loads the modules
    from: the `pf-runtime.war` merge (`WEB-INF/lib`) and `server/default/deploy`. pf-oidf-modules stages jars this
    way (its `deploy/pingfederate/.context/modules/MANIFEST` lists `ssf-0.1.3.jar`, read 2026-09-28). Without the
    jar the SSF servlets fail with `NoClassDefFoundError: com/pingidentity/ps/oidf/signals/...`. Compare your
    deployed jars with the release's `MANIFEST`.
22. **Check that the transmitters your SSF receiver listens to send SETs the stricter verifier accepts.** (XA14) Only a
    deployment with `receiverExpectedIssuer` set is affected. A SET the receiver took before and refuses now - a
    `typ` other than `secevent+jwt` or `application/secevent+jwt`, a missing or non-numeric `iat`, an `exp` more
    than 60 seconds past, an empty `events` or an event that is not an object, an `HS256` or `none` signature, a
    `sub_id` that is not an object - is answered `400` with `invalid_request` on push; on poll it is logged as
    rejected and acknowledged, so the transmitter does not send it again.
    RFC 8417 and SSF 1.0 require all of these of a transmitter (see Notes), and this repository's transmitter meets
    them. If a transmitter of yours does not, fix it before upgrading.
23. **Depend on `rs-validation`, not `demo-rs`.** (XD01) The relocation resolves the old coordinates for you, with a Maven
    warning naming the new ones; change the dependency to `com.pingidentity.ps.oidf:rs-validation` to silence it.
    Nothing in this repository's image or release assets changes: neither module was staged or copied to `dist/`.
24. **Give the validator a replay store.** (XD01) Replay protection is now required, so an embedding application must
    supply one: the constructors are gone, and `DelegatedTokenValidator.builder(issuer, audience).keys(...)
    .replayStore(...).build()` refuses to build without it. Use `RedisReplayStore` on a `RedisClient` from
    `platform.redis` when more than one node serves the resource, since every node must see the same store, and
    `InMemoryReplayStore` only for one node.
25. **Check the `typ` your access tokens carry.** (XD01) The validator now requires RFC 9068's `at+jwt` (or
    `application/at+jwt`). PingFederate's JWT access token manager sends no `typ` unless its "Type Header Value"
    field is set; set it to `at+jwt`, as the conformance rig does, or build the validator with
    `accessTokenType(AccessTokenType.ABSENT)`. Tokens without a `kid` are refused too; PingFederate includes it
    unless "Include Key ID Header Parameter" was turned off.
26. **Stop sending `act` as a string.** (XD01) A token whose `act` is a string holding JSON is refused in production. A
    development rig that still mints them can call `allowLegacyStringAct()`, which reads the process's own
    profile; `build()` then throws unless it is development (unset counts as production). `services/gm-api` still accepts the string form (F-0228).

## What is new for integrators

## Package C2: The platform Redis client: a bounded pool, deadlines, key prefixes, lease and rate-limit commands, Sentinel

What changed. The client and its S3a rules moved from client-attestation to `libs/platform`, which every module
already deploys beside it (PR1). The URL's userinfo is still decoded twice, as 0.4.0 did, so a `+` in a password
is a space ([F-0180](../findings/F-0180.yaml)); a bad escape there is now refused with a message that quotes
nothing, where URLDecoder's own message quoted two characters of the password. The plan's X-A02, which it names
only as absorbed by C-2, is taken as absorbed here. The
[platform README](../../libs/platform/README.md#redis) has the pool, the deadlines, the Sentinel rules and the
settings.

Sentinel and TLS. A sentinel reports the master by address unless `announce-hostnames` is on; an address cannot be
checked against a name, so the master's certificate is then checked against the URL's host, which every node's
certificate must carry. Whether C-6's reference cluster issues certificates that way is
[U-0190](../findings/U-0190.yaml).

How it was verified, on 2026-09-28. The platform tests run against an in-process RESP server that plays a master,
a replica and a sentinel, and stages silence, dropped connections and cut-off or malformed replies; the TLS tests
use certificates `keytool` makes for the run. Against real servers (redis:7-alpine, JDK 17.0.11): the commands and
the three scripts, including after `SCRIPT FLUSH`; the TLS half with a CA and a `localhost` certificate from
`tools/ci/start-tls-redis.sh`; and a master, a replica and one sentinel, where the test asked for a failover and
the client followed the master to its new port in 11.5 s. client-attestation's `RedisLiveTest` passed both halves
on the new client, and a key written the 0.4.0 way is found by the 0.5.0 stores. The in-process tests also passed
on the pinned PingFederate image's JDK, OpenJDK 21.0.12.1, the TLS ones included. CI runs the live tests against
its Redis services; it starts no Sentinel, so the real failover is not repeated there.

Residual risk. A command's bytes are written untimed: they fit a socket's send buffer, so only a peer that has
stopped reading can hold a write past the deadline ([F-0181](../findings/F-0181.yaml)). A command that fails
on a reused connection is retried once, as 0.4.0's was, and when the first attempt ran and only its reply was lost
the retry answers with a verdict (a spent proof, an unknown challenge) rather than an outage - 0.4.0 had the same
exposure, and Sentinel adds none: a new connection lost after the command was sent is not retried. CI's guard
against skipped live tests reads client-attestation's report and not platform's, which runs the lease and
rate-limit scripts against its Redis ([F-0182](../findings/F-0182.yaml)). Two documents C2 did not own still
describe `MiniRedisClient` ([F-0183](../findings/F-0183.yaml)).

The adversarial review (2026-09-28) found that all the sentinels shared one deadline, so a first sentinel that
accepted and never answered - or a host that dropped packets - used all of it and the healthy ones after it were
never asked. Each sentinel now gets an equal share of what is left and the one that answered is asked first next
time; `RedisSentinelTest` stages a silent first sentinel and the command succeeds in about half the deadline.
Against real servers the same day (redis:7-alpine master, replica and sentinel), with a listener that accepts and
never answers named first, the live Sentinel test passed in 1.55 s, and with the real sentinel alone it followed a
`SENTINEL FAILOVER` to the new master in 11.5 s.

## Package C3: Managed executors: every background job on a named, counted, stoppable thread

Thread names, for an operator reading a thread dump. Each is a daemon; `-1` is the executor's first thread, and a
higher number means its thread was replaced.

| Job | Before | Now |
|---|---|---|
| Registration expiry sweep | `oidf-registration-sweeper` | `oidf-registration-sweeper-1` |
| Subordinate entity-configuration refresh | `oidf-subordinate-refresh` | `oidf-subordinate-refresh-1` |
| SSF push delivery and SET expiry | `ssf-push-delivery` | `oidf-ssf-push-delivery-1` |
| SSF receiver poll | `ssf-poll-receiver` | `oidf-ssf-poll-receiver-1` |
| SSF boot retry | `ssf-boot-retry` | `oidf-ssf-boot-retry-1` |
| Lifecycle closes, at shutdown | `oidf-platform-close-<resource name>` | `oidf-platform-close-<n>` |

What stays the same: when each job first runs and how often (the sweeper and the SSF loops one interval from
start and then one interval after each run ends; the refresher at once and then every 240 s), every log line the
jobs write, and each job's own catch. Three things change, each on purpose:

- **One of each job per JVM.** Each executor's name is claimed in the System property `oidf.exec.owner.<name>`
  and given back when it closes, so a second start - a servlet initialised twice, or the same servlets in
  `oidf.war` and `pf-runtime.war` - starts nothing and logs why. The subordinate refresher had no such guard:
  each `init` started another thread. Because it warms only its own instance's cache, a second instance whose
  refresher is refused fetches a subordinate's keys on its first request and serves them stale after that
  (F-0202); production's single servlet in `pf-runtime.war` is not affected. The sweeper keeps its own owner property as well, and now gives it back
  when it stops.
- **An `Error` no longer ends a job.** The jobs catch their exceptions as before; what gets past those catches -
  a `NoClassDefFoundError`, say - used to end the sweeper's thread and silently stop the SSF loops' later ticks.
  Now it is logged at WARN with its stack, counted in `oidf_executor_failures_total`, and the next run happens.
- **Shutdown stops them.** When F-2's lifecycle listener (in this release) runs the lifecycle's shutdown at
  undeploy, each executor is interrupted and waited for up to five seconds; a run interrupted that way is logged
  at INFO, not as a failure. The refresher stops at the next subordinate instead of logging each remaining one as
  not reachable. Before 0.5.0 nothing stopped these threads.

Only the webapp's copy is meant to start threads (docs/development/classloaders.md, rule 2). Until F-2 marks it,
that holds because every start is in a servlet's or filter's `init`, which the engine's loader never runs;
refusing every unmarked copy once F-2 exists is F-0200. The Kafka producer's own I/O thread, when the SSF Kafka
publisher is on, is started by the Kafka client and never closed in production (F-0201). Left for C-4 (Phase 4):

## Package RCI5: The coverage gate and the ratchet in CI

Nothing here changes what is deployed; it changes what a pull request can merge with.

What the gate refuses (`--gate`, each line on stderr and in the step summary starts `gate:`):

- a jacoco check that includes no method;
- an `<include>` pattern that names no method in the jacoco report. jacoco passes a rule that selects nothing,
  so a renamed method or a typo in a pom left the method ungated and the build green. Fix the pattern;
- an `@Requirement` id whose prefix `Requirement.java` does not declare. Declare the prefix once the document
  behind it has been read, or fix the id.

An id naming a section no conformance-matrix row declares is printed as a `gate warning:` and counted, not
refused. Measured on 2026-09-28 (origin/main 982e4cd, `mvn -B clean verify` on JDK 17): 65 of the 500 ids, under
21 prefixes, seven of which no matrix has a row for, and the repository has no spec index to declare them
instead. Refusing them would fail every build until the matrices catch up; F-0145 records the gap and the
one-line change that turns the warning into a refusal.

What the ratchet refuses (`--baseline`, lines start `ratchet:`), against the `coverage-dashboard.json` of an
earlier build:

- a jacoco check the baseline had is gone, or includes fewer methods - the line names the methods it no
  longer includes;
- a gated method below 100% line or branch coverage;
- fewer pinned matrix rows - the line names the rows.

A new module, check or method passes, so Phase 2's new modules need no edit to the tool. A reduction that is the
point of a change - dead code deleted with its `<include>`, a check renamed, a module moved, a matrix row
retired - needs a line in `tools/coverage-ratchet-allow.txt` in the same pull request (`method <module>
<method>`, `check <module> <execution id>` or `row <matrix row>`, copied from the `ratchet:` line). The pull
request's run and the push to main after it both read the file, so a reviewed reduction does not leave main
red, and a red merge is cleared by adding the line rather than by editing the tool. Nothing in the file excuses
a gated method below 100%. A line whose item the baseline no longer has allows nothing and is listed in the step
summary, ready to delete.

CI's baseline is the JSON of the newest successful push Build on main that the commit under test descends from:
a pull request's merge commit, a push, or a dispatched branch, which may be behind main (so a release dry run
on an older branch is not compared with a newer main). Runs from pull requests never supply it, even from a
fork's branch called `main`. No baseline - the first run after this merges, which finds artefacts without the
JSON, or an artefact past its 90 days - passes with a notice in the step summary, and so does a baseline in

## Package XB01: Verified evidence selectors on the instance identity

Plan item X-B01 prepares X-B09's selector-conditioned ceilings. `InstanceIdentity.selectors()` is an immutable,
sorted multimap from `<source>:<name>` to a sorted set of values; `source` is the evidence type id and `name` comes
from the validator's fixed list. The [attestation-issuer README](../../servlets/attestation-issuer/README.md#evidence-selectors)
tables what each validator verifies, what it copies into the identity, and which selectors it proves from which
claim: the SPIFFE ID and trust domain of an SVID; the cluster issuer, namespace and service account of a GKE, EKS
or AKS token; the issuer and email of a GCP ID token; the issuer, account and role of an AWS
STS token; the issuer, tenant and object id of an Azure managed-identity token; the provider and instance of a
wallet WIA. Values are kept as the evidence states them, compared exactly, as the binding match compares subjects.

A selector is built only inside a validator, from a claim of evidence whose signature it verified, after every
check. Request parameters, binding metadata, the SPIRE introspector's attributes and the caller-asserted context
cannot reach it: `InstanceIdentity` cannot be changed once built, and only the issuer package can build a non-empty
set. Evidence with more than 32 values, or a value over 2048 UTF-8 bytes (the SPIFFE ID's limit, SPIFFE-ID §2.3), is
refused with `invalid_svid` or `invalid_instance_attestation` rather than truncated. The built-in lists have at
most three names with one value each, so the count bound is for SPIRE's selectors to come. The value bound refuses
a SPIFFE ID longer than the SPIFFE specification requires implementations to support; it would also refuse a
wallet instance id, an issuer or an email over 2048 bytes, which no specification this module follows bounds.

Nothing changes on the wire. `AttestationMinter` does not read the selectors, and `EvidenceSelectorsTest` mints the
same identity with and without them and compares the payloads. It also gives each validator a real-shaped token
and, for every validator, extra and unknown claims, an oversized value, and a forged or expired token refused for
that fault before any selector is built; non-string claims; and 200
random seeds of binding metadata, asserted context and SPIRE answers that leave the selectors as they were. The
methods that build and read the selectors are in attestation-issuer's 100% METHOD gate. Verified on 2026-09-28 with
`mvn verify` on the module under JDK 17 and JDK 20, and on the whole reactor under JDK 17 with Postgres and Redis.

The SPIRE introspector's selectors are not evidence: a plain HTTP read of an operator-configured endpoint, merged
into `workload.attributes` of every attestation as before. F-0140 records that anything reading those attributes
reads what the endpoint said; X-B07 and X-B08 (Phase 5) replace the read with an mTLS reader, which is to add
`spire:` selectors through the same bounds.
