# The RAR plugin refuses a detail where it arrives, and the JWT-bearer grant no longer carries its types

## Changelog

- The RAR plugin's `validate` holds each `authorization_details` entry to its type's model, the two bookkeeping
  markers stripped: an unmodelled type (in development the common-fields model stands in, as it does for `enrich`),
  an undeclared field, a value of the wrong JSON type or a detail over the size limits is refused with the model's
  reason, which names the field and never a value. PingFederate calls `validate` at PAR, the authorization endpoint,
  CIBA's backchannel request, the device authorization endpoint, token exchange and the token endpoint, so such a
  request now fails there with `invalid_authorization_details` rather than later at the resume or the token endpoint
  (RFC 9396 section 5, F-0108). The exception is a token exchange that requests an ID-JAG
  (`requested_token_type=urn:ietf:params:oauth:token-type:id-jag`): PingFederate 13.1.3 calls neither `validate` nor
  `enrich` there and copies the request's `authorization_details` into the ID-JAG it signs (F-0325). A models document that did not load, and an instance whose configure threw, refuse
  every detail there too. `validate` asks no PDP and resolves no principal; each refusal is logged at INFO as
  `RAR validate: refusing type=... flow=... path=...`.
- On the JWT-bearer grant (`grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`), where PingFederate calls
  `validate` and never `enrich`, the plugin refuses a detail of its types with "authorization_details of this type
  are not accepted on the JWT-bearer grant" unless the new field "Types allowed on the JWT-bearer grant" lists the
  type. The field defaults to none. A listed type passes `validate`'s model check and is issued without a PDP
  decision. The field refuses, on save and at configure, a type that "Types requiring an authenticated principal"
  lists (F-0108, U-0017).

## Before you deploy

1. **The JWT-bearer grant no longer carries the RAR plugin's types.** From 0.6.0 a JWT-bearer token request whose
   `authorization_details` - the request's parameter, or the claim in an ID-JAG assertion (`typ`
   `oauth-id-jag+jwt`) - holds a type bound to the "Attestation-aware RAR to PingAuthorize" processor is answered
   400 `invalid_authorization_details`, "authorization_details of this type are not accepted on the JWT-bearer
   grant", and no token is issued. Why: PingFederate 13.1.3 never calls the processor's `enrich` on that grant, so
   the PDP never decided those details; on the ID-JAG profile the token carried the assertion's details as they
   were. How to tell: a client that used the grant with these types gets that error, and the server log has a
   `RAR validate: refusing type=<type> flow=urn:ietf:params:oauth:grant-type:jwt-bearer` line. What to change: if
   you issue a type on the JWT-bearer grant on purpose, list it in "Types allowed on the JWT-bearer grant", knowing
   that a listed type passes `validate`'s model check and is issued without a PDP decision. A type in "Types
   requiring an authenticated principal" (by default `payment_initiation` and `account_information`) cannot be
   listed; remove it from that field first if you accept that no person is established for it on this grant. On
   the plain RFC 7523 profile PingFederate 13.1.3 issued none of the request's details even before this change, so
   such a client loses nothing but now gets an error instead of a token without the details. There is no
   development-profile escape: the field is the control, in every profile.
2. **Non-conforming details are refused where they arrive.** A PAR, authorization, CIBA, device or token request
   whose `authorization_details` the RAR model does not accept - an undeclared field, a value of the wrong type, an
   unmodelled type in production, a detail over the size limits - used to succeed at PAR or the authorization
   endpoint and fail later, at the resume after the user logged in or at the token endpoint; it now fails at once,
   with `invalid_authorization_details` and the model's reason, for example "authorization_details of type
   'payment_initiation' does not conform to its type's model (UNDECLARED_FIELD): requested authorization_details[0]
   carries 'colour', which type 'payment_initiation' does not declare". Why: RFC 9396 section 5 says "The AS MUST
   refuse to process any unknown authorization details type or authorization details not conforming to the
   respective type definition", and a refusal after the user has logged in wastes their login. How to tell: a client
   that sent such details sees the error at PAR or the first endpoint instead of later; the server log has a `RAR
   validate: refusing` line naming the type, the flow and the reason. What to change: fix the client to send what
   the type's model declares, or declare the field in your models document (`OIDF_RAR_MODELS_FILE`). The
   development profile's escape is the one it had before: an unmodelled type is held to the common-fields model
   (`OIDF_DEPLOYMENT_PROFILE=development`); nothing else is relaxed.
3. **Do not enable ID-JAG issuance for a client that may send the RAR plugin's types.** A token exchange whose
   `requested_token_type` is `urn:ietf:params:oauth:token-type:id-jag` is not covered by this release: PingFederate
   13.1.3 calls neither the processor's `validate` nor its `enrich` on it, and copies the request's
   `authorization_details` into the ID-JAG it signs, so no model and no PDP decides them (F-0325, read with `javap`
   of pf-protocolengine 13.1.3.0 on 2026-09-30, not yet driven on the rig). How to tell: an SP connection whose OAuth
   token exchange settings enable ID-JAG, and a confidential client allowed the token-exchange grant. What to
   change: until F-0325 is fixed, leave ID-JAG off on every SP connection while such a client may send a type bound
   to the "Attestation-aware RAR to PingAuthorize" processor, or give the SP connection's ID-JAG claim mapping an
   `authorization_details` of its own, since PingFederate copies the request's only when the mapping sets none.

## Notes

Package S4D2 (plan item S4d, 2 of 3), 2026-09-30. Route (a) of F-0108 - refusal, the plan's recommended default -
is built; route (b), asking the PDP from `validate` on the JWT-bearer grant with the assertion's `sub` as the
principal, is not, and waits for David's choice.

Verified before any code, 2026-09-30, on the conformance rig on slot 2 (`PF_RIG_NAME=pfai-p3-s4d2`, PingFederate
13.1.3.0), configured by `ONLY_CONFIGURE=1 conformance/verify-rar-principal.sh` with the probe client given the
`EXTENSION` grant and an IdP connection for a test JWT issuer, and a plugin jar that logged each `validate` call:
on both JWT-bearer profiles PingFederate called `validate` and never `enrich` (U-0017). On the plain RFC 7523 profile
`validate` ran before the assertion was verified - a forged assertion still reached it - and the token carried
`"authorization_details": []`; on the ID-JAG profile `JwtGrantProcessor` verified the signature first - a forged
assertion never reached `validate` - and the token carried the assertion's `payment_initiation` detail with no PDP
decision. The bytecode agrees (`javap -c` of pf-protocolengine 13.1.3.0:
`TokenEndpointRequestHandler.validateParametersAgainstClient` skips `checkAuthorizationDetails` for an ID-JAG
assertion, and `JwtGrantProcessor.processJwtRequestUsingNativeProcessor` calls `validateJwt` before
`AuthorizationDetailsUtil.validate`). So route (b) could trust the assertion's `sub` on the ID-JAG profile only.

Then with this jar, the same rig: a JWT-bearer request with a `payment_initiation` detail, plain and ID-JAG, was
answered 400 `invalid_authorization_details` with no token, no `enrich` and no PDP call; a PAR carrying
`payment_initiation` with an undeclared field, or `amount` as a boolean, was refused at PAR; a CIBA backchannel
request with an undeclared field was refused at `/as/bc-auth.ciba`; a conforming client-credentials request was
decided by the PDP as before. Saving the instance with `payment_initiation` in "Types allowed on the JWT-bearer
grant" was refused (422); with `sales_agent` an ID-JAG `sales_agent` detail was issued with no PDP call. The plugin's
tests pass on JDK 17 and on JDK 21 (`maven:3-eclipse-temurin-21`); the plugin itself ran on the image's JDK 21.

Residual: a type listed in the new field is issued on the ID-JAG profile as the assertion's issuer wrote it, held to
the model but never to the PDP or the attestation ceiling; S4D3's issuance criterion (plan item S4d, 3 of 3) is
to bound what an attested client is issued. A bare refresh is still never re-decided (F-0105, S4D3). A token
exchange that requests an ID-JAG reaches neither `validate` nor `enrich` and carries the request's details into the
ID-JAG (F-0325, open, U-0335); nothing in this package or the plan's S4d reaches it, since S4D3's criterion is an
access-token mapping and the ID-JAG is SP-connection output.
