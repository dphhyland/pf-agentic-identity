# Events in platform, catalogued, with a PII class for every field

## Changelog

- Events live in `platform.events` (plan item O-1): the event record, now with a component, the sink interface, the
  per-classloader sink registry, the server-log sink and `LogSafe`, with the rule that an instance's subject is
  never recorded beside its `agent_id`. `FederationEvent`, `FederationEvents`, `FederationEventSink`,
  `LoggingEventSink` and `LogSafe` in openid-federation are delegating façades, deprecated for removal by O-2.
- Every event code and every field it may carry is catalogued as data, in `META-INF/oidf-events/<component>.json`
  of the module that declares it - `federation` in openid-federation, `attestation-issuer` in the attester - with
  one PII class per field (`OPERATIONAL`, `PSEUDONYMOUS_ID`, `DIRECT_ID`, `NETWORK`, `CREDENTIAL_DIGEST`). A field
  its code does not declare is dropped before any log sees it, and counted.
- PingFederate's audit sink is `platform.pf.audit.PfAuditSink` in platform-pf, with the audit log's `protocol`
  column set per component from its catalogue; `PfAuditEventSink` in pf-integration is a delegating shim.
  `OIDF_EVENTS_AUDIT` and `OIDF_EVENTS_MAX_VALUE_LENGTH` are unchanged.
- `EventsCataloguedTest` fails the build on an emitted code or field that is not catalogued, on a catalogued code
  nothing emits unless it is marked `declaredOnly`, and on an emitter whose audit flag or outcome its catalogue
  does not match.

## Before you deploy

1. **Expect `Client Attestation`, not `OpenID Federation`, in the `protocol` column of the attester's evidence
   conflict records.** `attestation.evidence.conflict` - the attester refusing instance evidence already bound to
   another key or client - is an attestation event, and its audit record now says so. Nothing else in the audit
   log changes: every federation record keeps `OpenID Federation`, and the event, status, subject, connection,
   role, `ip` and description columns are written as before. If you find these records by filtering `audit.log`
   on the protocol, add `Client Attestation` to the filter. Deploy the attester's jar from the same release as
   `pf-integration`: its catalogue ships in that jar, and without it the conflict record keeps its code, status
   and subject but loses its fields (a WARN line in server.log says so).
2. **Look for three configuration lines under a new logger name.** The warnings that `OIDF_EVENTS_AUDIT` is neither
   `true` nor `false` and that `OIDF_EVENTS_MAX_VALUE_LENGTH` is not a number, and the DEBUG line saying an audit
   write was skipped, keep their text and are now written by
   `com.pingidentity.ps.oidf.platform.pf.audit.PfAuditSink` instead of `com.pingidentity.ps.oidf.pf.PfAuditEventSink`.
   The DEBUG line saying a second event sink was ignored now reads "The event sink is already configured; a second
   configuration was ignored", on `com.pingidentity.ps.oidf.platform.events.Events`. Event lines themselves - their
   text, their logger (`com.pingidentity.ps.oidf.federation.event.<family>`) and their level - are unchanged. A
   log4j2 filter or alert on the old logger names needs the new ones.

## Notes

The catalogues classify and do not yet change what an event line carries: `PiiPolicy.DEFAULT` keeps every class in
server.log and in the audit log, as before. The one direct identifier, `actor` (whatever name an administrator
sends in `X-Federation-Actor`), still reaches server.log in clear; the policy that could digest it there is in
place and unused, and the decision is plan item D-6's ([F-0165](../../findings/F-0165.yaml)). The catalogues
declare 40 federation codes and one of the attester's, 26 fields and 6; 13 federation codes are declared and not
emitted, `attestation.client.verified` and `.refused` among them, and are marked `declaredOnly` until O-2 emits
them. Two lines can now appear that could not before, and neither is expected: a WARN the first time an event
carries a field its catalogue does not declare (the field's name, never its value), and an ERROR when a catalogue
cannot be read.

`PfAuditSink` keeps `PfAuditEventSink`'s order of `LoggingUtil` calls exactly - `init`, the columns, the protocol
into log4j's `ThreadContext` rather than through `LoggingUtil.setProtocol` (which writes the `ip` column on
PingFederate 13.0 and 13.1), `log`, and `cleanup` in a `finally` - so whether `cleanup` strips PingFederate's own
audit context is still [F-0049](../../findings/F-0049.yaml)'s question (H-FED-7, Phase 3). The umbrella finding
F-0027 stays open.

One line outside the events subpackages: `platform.log.PlatformLog` gains `get(String)`, a logger by name, which the
server-log sink needs to keep writing on each event family's logger.
