# Security Event Tokens without PingFederate: libs/shared-signals

## Changelog

- New module `libs/shared-signals` (`com.pingidentity.ps.oidf:shared-signals`, package
  `com.pingidentity.ps.oidf.signals`; plan item X-A14): the RFC 8417 SET model, minting behind `oidf-jose`'s
  `SigningKeyProvider` or `JwsSigner`, verification against a supplied key set, the subject identifiers, and the
  CAEP and RISC event types. No HTTP and no PingFederate, so a service outside PingFederate can mint and verify SETs
  with the code `servlets/ssf` uses.
- `SecurityEventToken`, `SetMinter`, `SetVerifier`, `ReceivedSet`, `SubjectId` and `CaepRiscEvents` moved from
  `com.pingidentity.ps.oidf.ssf` to `com.pingidentity.ps.oidf.signals`; no class of the old name is left behind,
  because keeping the package in a second jar would split it across two jars again (the 2026-08-15 unwind in
  [PROVENANCE](../../PROVENANCE.md)). `SsfEventTypes` stays in `servlets/ssf` as the list the transmitter
  advertises; its URIs are the new `EventTypes`. What needs PingFederate or the network stays in `servlets/ssf`:
  `PfSetSigningKeys` (PingFederate's signing key, resolved on first use as before) and `JwksHttpSource` (the
  receiver's JWKS fetch, which plan item S5d moves onto platform's HTTP client).
- `SubjectId` parses RFC 9493's `did`, `uri` and `aliases`, SSF 1.0's `jwt_id`, `saml_assertion_id` and
  `ip-addresses`, and SSF 1.0's complex subject, and implements SSF 1.0 §8.1.3.1's subject matching (finding U-0033,
  closed). `servlets/ssf` still accepts only the five formats it handled before (`iss_sub`, `email`,
  `phone_number`, `opaque`, `account`) - in stream subjects, the emit API, SCIM ids and an inbound `sub_id` - until
  plan item H-SSF-1 stores, matches and acts on the others.
- The receiver's SET verification is stricter (finding F-0245, closed): `typ` must be `secevent+jwt` (with or without
  `application/`, in any case), not merely contain `secevent`; `alg` must be an asymmetric signature algorithm;
  `iat` must be present and a number; an `exp` that has passed, less 60 seconds, is refused; `events` must be an
  object with at least one member, each an object; a `sub_id` that is not an object is refused.
- `build/pingfederate/stage-modules.sh` stages `shared-signals-<version>.jar` in both profiles, so the image carries
  it and the `MANIFEST` names it.

## Before you deploy

1. **Deploy `shared-signals-<version>.jar` wherever you deploy `ssf-<version>.jar`.** A consumer that builds its
   image from this repository's `build/pingfederate/Dockerfile` and `stage-modules.sh` gets it with nothing to do.
   A consumer that copies jars itself must put it beside `ssf`'s in both places PingFederate loads the modules
   from: the `pf-runtime.war` merge (`WEB-INF/lib`) and `server/default/deploy`. pf-oidf-modules stages jars this
   way (its `deploy/pingfederate/.context/modules/MANIFEST` lists `ssf-0.1.3.jar`, read 2026-09-28). Without the
   jar the SSF servlets fail with `NoClassDefFoundError: com/pingidentity/ps/oidf/signals/...`. Compare your
   deployed jars with the release's `MANIFEST`.
2. **Check that the transmitters your SSF receiver listens to send SETs the stricter verifier accepts.** Only a
   deployment with `receiverExpectedIssuer` set is affected. A SET the receiver took before and refuses now - a
   `typ` other than `secevent+jwt` or `application/secevent+jwt`, a missing or non-numeric `iat`, an `exp` more
   than 60 seconds past, an empty `events` or an event that is not an object, an `HS256` or `none` signature, a
   `sub_id` that is not an object - is answered `400` with `invalid_request` on push; on poll it is logged as
   rejected and acknowledged, so the transmitter does not send it again.
   RFC 8417 and SSF 1.0 require all of these of a transmitter (see Notes), and this repository's transmitter meets
   them. If a transmitter of yours does not, fix it before upgrading.

## Notes

Who imports the moved classes, read 2026-09-28 in the checkouts on the development Mac: pf-oidf-modules at 55629cc,
idp-agentic-demo at 9eee704 and pf-agentic-identity-domain-authority at 46fdcc3 import none of them (a search for
the six class names and for `com.pingidentity.ps.oidf.ssf` found only prose in pf-oidf-modules' `docs/REPO-MAP.md`
and `docs/ssf-transmitter.md`). So the old package keeps no delegate. Code that compiles against `ssf` and imports one
of them changes `com.pingidentity.ps.oidf.ssf.` to `com.pingidentity.ps.oidf.signals.` and adds the
`shared-signals` dependency (it also arrives with `ssf`); `SsfEventTypes` keeps its name and package.

The texts the verifier is held to, quoted from the primary sources fetched 2026-09-28:

- RFC 8417 §2: "The "events" claim value MUST be a JSON object that contains at least one member." §2.2: `iss`,
  `iat` and `jti` - "This claim is REQUIRED"; `aud` - "This claim is RECOMMENDED"; `exp` - "the time after which the
  JWT MUST NOT be accepted for processing"; for `events`, "For each name present, the corresponding value MUST be a
  JSON object". §2.3: "the "typ" value used SHOULD be "secevent+jwt"".
- SSF 1.0 (Final, 29 August 2025) §4.1.1: "SSF events MUST use explicit typing as defined in Section 2.3 of
  [RFC8417]." §4.1.6: "Receivers MUST validate that this claim matches". §4.1.8: "The "aud" claim can be a single
  string or an array of strings."
- RFC 7515 §4.1.9: media types are case insensitive, and "A recipient using the media type value MUST treat it as
  if "application/" were prepended to any "typ" value not containing a '/'."

SSF 1.0 also says "The "exp" claim MUST NOT be used in SETs" (§4.1.7) and "The JWT "sub" claim MUST NOT be present"
(§4.1.2). Both are written to the transmitter; the verifier honours an `exp` as RFC 8417 does and ignores `sub`.
Whether a receiver should refuse either is finding F-0246, for H-SSF-1.

The complex subject is SSF 1.0 §3.3: "a JSON [RFC7159] object that has a format field, and one or more Simple
Subject Members. The name of the format field is "format", and its value is "complex"." Matching is §8.1.3.1, and
the tests use the section's own three examples. Nothing in `servlets/ssf` uses the new formats or `matches` yet:
H-SSF-1 (Phase 3) wires the receiver's complex, `did`, `uri` and `aliases` subjects, and X-A13, X-A15 and X-A16
(Phase 6) are the services meant to mint and receive SETs without PingFederate.

The subject keys `servlets/ssf`'s stores hold are unchanged for the five formats they can hold, so stored streams,
subjects and pending SETs read back as before. Verified 2026-09-28: the reactor on JDK 20 and 17, `servlets/ssf`'s
Postgres store suites included; the new module's jacoco gate covers the verifier, subject parsing, keys and
matching, and `SetMinter.sign` at 100% line and branch.
