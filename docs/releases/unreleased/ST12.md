# Settings core: strict parsers, the Setting model and the catalogue format

## Changelog

- Plan items ST-1 and ST-2: `platform.settings` holds the strict parsers `FederationRuntimeConfig` used, with
  their messages (`Parsers`), and the settings model - `Setting`, a resolver that returns each value with the
  source and name that supplied it, aliases, removed names, `_FILE` secrets - loaded from one JSON catalogue per
  component at `META-INF/oidf-settings/<component>.json`, read through typed accessors (`Settings`).
  `UnknownKeys.find` lists `OIDF_*` names under a catalogued family that nothing declares; nothing calls it at
  run time yet. `platform-pf` adds `InitParams`, a servlet's or filter's init-params as a source.
- `FederationRuntimeConfig` reads through `Parsers`; its names, precedence, defaults and messages are unchanged.
  `OIDF_AUTHORITY_METADATA_POLICY` and `OIDF_FEDERATION_SUBORDINATE_CONSTRAINTS` are read by `platform.json`
  instead of Jackson, which refuses a few documents Jackson accepted (see the first item below).
- [docs/development/settings-catalogue.md](../../development/settings-catalogue.md) describes the catalogue
  format, with a worked example.

## Before you deploy

1. **Check that `OIDF_AUTHORITY_METADATA_POLICY` and `OIDF_FEDERATION_SUBORDINATE_CONSTRAINTS` are each one
   well-formed JSON object.** They are now read by `platform.json`, which refuses what Jackson read without
   complaint: a member name used twice in one object (Jackson kept the last), anything after the object (Jackson
   ignored it), nesting deeper than 32, a number written with more than 128 characters, and a string holding half
   a surrogate pair. Either setting holding one of these now stops PingFederate starting, with
   `OIDF_AUTHORITY_METADATA_POLICY: not a JSON object` (or the other name) in the log. Everything Jackson read
   otherwise reads the same values; numbers are now `BigDecimal`, which the metadata policy and the constraints
   already compare by value, and an exponent past a double's range, such as `1e400`, is kept exactly where
   Jackson read it as infinity. To check a value for the first two before you upgrade, pipe it into
   `python3 -c 'import json,sys; json.loads(sys.stdin.read(), object_pairs_hook=lambda p: dict(p) if len({k for
   k, _ in p}) == len(p) else sys.exit("duplicate member name"))'`, which refuses both.
2. **Make sure `platform-<version>.jar` is deployed beside `pf-integration`'s jar, in both places.** From this
   package `FederationRuntimeConfig` calls platform, so platform is no longer optional: without it the first
   class to read the federation settings fails with `NoClassDefFoundError: com/pingidentity/ps/oidf/platform/...`.
   A consumer that builds its image from `build/pingfederate` gets it with nothing to do; one that copies jars
   itself follows the item "Deploy `platform-<version>.jar` and `platform-pf-<version>.jar` wherever you deploy
   `oidf-jose` and `pf-integration` today", and compares its deployed jars with the release's `MANIFEST`.

## Notes

What changed, and what did not:

- No setting is read differently apart from the two JSON settings above: the parsers moved with their messages,
  and `FederationRuntimeConfig` keeps its names, its precedence (system property, then environment variable),
  its defaults and its lenient read of `OIDF_FEDERATION_IGNORE_SSL_ERRORS` (`Boolean.parseBoolean`), which
  ST-5 makes strict in Phase 3. Its private helpers the coverage gate names (`strictBoolean`, `strictly`,
  `words`, `jsonObject`) stay, as one-line calls into `Parsers`, so the gate keeps them.
- The catalogue format exists, with a worked example in platform's test resources; no production catalogue
  exists yet (ST3A, ST3B and ST3C write them) and no reader resolves through `Settings` yet (ST-5).
- Unknown `OIDF_*` keys are listed, not refused: refusing one before every module is catalogued would stop working
  deployments. The start-up audit (PR-5) and ST-5 wire it in, in Phase 3. F-0025 stays open.
- The libs/platform README lists every lenient read found on 2026-09-28 across the reactor, from
  `OIDF_FETCH_ALLOW_HTTP` to device-enrolment's `REQUIRE_COMPLIANT_DEVICE`, as ST-5's worklist.
