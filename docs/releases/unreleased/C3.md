# Managed executors: every background job on a named, counted, stoppable thread

## Changelog

- Plan item C-3: `libs/platform` gains `platform.exec`. `ManagedExecutors.every`, `after` and `single` start a
  job on an executor of its own with one daemon thread named `oidf-<name>-<n>`, registered with the copy's
  lifecycle (closed at shutdown within five seconds), listed per classloader, and counted per run in
  `oidf_executor_runs_total`, `oidf_executor_failures_total` and `oidf_executor_run_seconds`. A run that throws
  is logged and counted and the job carries on. A job runs once in the JVM, whichever classloader starts it, and
  a plugin's relocated copy starts none.
- The registration expiry sweeper, the federation subordinate refresher, and the SSF push delivery, receiver
  poll and boot-retry loops run on it, with their timing, log lines and failure handling unchanged. Their threads
  are renamed (see the Notes).
- `Lifecycle` closes each resource on a thread started through `ManagedExecutors.startDaemon`, so platform.exec
  is the one place the repository's shipped PingFederate code starts a thread; closes F-0131. New in the
  register: F-0200, F-0201, U-0210.

## Before you deploy

1. **Update anything that looks for the old thread names.** A thread dump, a JVM monitoring rule or a log
   pattern that names `oidf-registration-sweeper`, `oidf-subordinate-refresh`, `ssf-push-delivery`,
   `ssf-poll-receiver`, `ssf-boot-retry` or `oidf-platform-close-<resource>` will not find them: the Notes give
   the new names. Nothing else changes: no setting, no endpoint, no log line of the jobs' own.

## Notes

Thread names, for an operator reading a thread dump. Each is a daemon; `-1` is the executor's first thread, and a
higher number means its thread was replaced.

| Job | Before | Now |
|---|---|---|
| Registration expiry sweep | `oidf-registration-sweeper` | `oidf-registration-sweeper-1` |
| Subordinate entity-configuration refresh | `oidf-subordinate-refresh` | `oidf-subordinate-refresh-1` |
| SSF push delivery and SET expiry | `ssf-push-delivery` | `oidf-ssf-push-delivery-1` |
| SSF receiver poll | `ssf-poll-receiver` | `oidf-ssf-poll-receiver-1` |
| SSF boot retry | `ssf-boot-retry` | `oidf-ssf-boot-retry-1` |
| Lifecycle closes, at shutdown | `oidf-platform-close-<resource name>` | `oidf-platform-close-<n>` |

What stays the same: when each job first runs and how often (the sweeper and the SSF loops one interval from
start and then one interval after each run ends; the refresher at once and then every 240 s), every log line the
jobs write, and each job's own catch. Three things change, each on purpose:

- **One of each job per JVM.** Each executor's name is claimed in the System property `oidf.exec.owner.<name>`
  and given back when it closes, so a second start - a servlet initialised twice, or the same servlets in
  `oidf.war` and `pf-runtime.war` - starts nothing and logs why. The subordinate refresher had no such guard:
  each `init` started another thread. The sweeper keeps its own owner property as well, and now gives it back
  when it stops.
- **An `Error` no longer ends a job.** The jobs catch their exceptions as before; what gets past those catches -
  a `NoClassDefFoundError`, say - used to end the sweeper's thread and silently stop the SSF loops' later ticks.
  Now it is logged at WARN with its stack, counted in `oidf_executor_failures_total`, and the next run happens.
- **Shutdown stops them.** Once F-2's listener runs the lifecycle's shutdown, each executor is interrupted and
  waited for up to five seconds; a run interrupted that way is logged at INFO, not as a failure. The refresher
  stops at the next subordinate instead of logging each remaining one as not reachable. Until F-2 lands nothing
  calls that shutdown, as nothing stopped these threads before.

Only the webapp's copy is meant to start threads (docs/development/classloaders.md, rule 2). Until F-2 marks it,
that holds because every start is in a servlet's or filter's `init`, which the engine's loader never runs;
refusing every unmarked copy once F-2 exists is F-0200. The Kafka producer's own I/O thread, when the SSF Kafka
publisher is on, is started by the Kafka client and never closed in production (F-0201). Left for C-4 (Phase 4):
the registration sweeper and the SSF poll client must run once per cluster, not once per node, through
`leaderEvery`; the SSF push loop becomes S-10's leased engine. F-0007, the clustering umbrella, stays open.

Verified on 2026-09-28: `mvn verify` of platform, openid-federation, pf-integration and ssf with their
dependencies, on JDK 17 and JDK 20, with the new decision methods in platform's 100% METHOD gate and every
existing gate met. `ExecutorCopiesTest` loads platform twice through two `URLClassLoader`s in one JVM and shows
the second copy starts no second loop while the first runs. Each converted job has a test that runs its loop on
the executor: its thread name, its first run, a failing run followed by the next, one loop in the JVM, and a stop
that interrupts a run in progress and ends it cleanly. Not seen yet: the new thread names in a running
PingFederate (U-0210).
