# gm-api and the plugins on BOM coordinates

## Changelog

- gm-api imports the BOM like every other module and depends on the real coordinates of what PingFederate
  provides (`pingfederate-sdk`, `jakarta.servlet-api`, `jose4j`, `jackson-databind`, `jackson-core`), all
  `provided` and version-less; ciba-sim and instance-registry-datasource take `org.apache.commons:commons-lang3`
  from the BOM. Nothing names `local.pingfederate` any more.
- The `pf-provided-jars` action installs only `pf-protocolengine` and `pingfederate-sdk`; it still extracts
  `pf-lib` and `pf-jetty-lib` for `tools/pf-linkcheck.py` and `tools/pf-provided-versions.py`, which now checks
  `jackson-core` against the image as well.

## Before you deploy

None.

## Notes

Nothing changes at run time. gm-api.war's `WEB-INF` is byte for byte the war main built on 2026-09-28 (the same
classes and `web.xml`, compiled on the same JDK), and its `WEB-INF/lib` is still empty: no PingFederate-provided
jar is bundled. What moved is only where the build finds the jars it compiles against.

- **gm-api.** The pom imports the BOM with the literal-version import every module uses, and keeps its
  coordinates `au.com.idpartners:gm-api`, war packaging, `finalName` gm-api, `maven.deploy.skip` and the
  Implementation-Version manifest entry McpServlet reads. Its build is now the reactor's shape (compiler 3.13.0,
  surefire 3.2.5, release 17); the jacoco gate is unchanged in content. `pingfederate.version` is gone:
  gm-api takes the SDK version from the BOM, and `tools/pf-version-check.py` now fails if the pom carries a
  PingFederate version of its own. `tools/set-version.py` reads gm-api like any other module (its version and
  its BOM import); its tests say so. The old pom also declared `commons-lang3` and `commons-logging`; nothing in
  gm-api reaches either (`mvn dependency:analyze` on 2026-09-28 lists every remaining `provided` dependency as
  used, and the build and 88 tests pass without them), so they are not declared.
- **The servlet API underneath.** gm-api compiled against the image's `jetty-jakarta-servlet-api-5.0.2.jar` and
  now compiles against `jakarta.servlet:jakarta.servlet-api:5.0.0` from Maven Central, as every other servlet
  here already did. `tools/pf-linkcheck.py --lib pf-lib --lib pf-jetty-lib` on the new gm-api.war against the
  13.1.3 image's jars (2026-09-28): 20 own classes, 35 watched member references - 17 of them `jakarta.servlet`
  members - and 0 unresolved; the whole reactor, 0 unresolved.
- **The libraries PingFederate ships.** `tools/pf-provided-versions.py` against the image's `server/default/lib`
  (2026-09-28): jackson-databind and jackson-core 2.21.1, jose4j 0.9.6, commons-lang3 3.18.0, commons-logging
  1.1.1 and log4j-api 2.25.4, each equal to the BOM. The BOM gains one managed entry, `jackson-core` at
  `version.pf.jackson`.
- **Only two jars from the image.** A Maven repository holding nothing but `pf-protocolengine` and
  `pingfederate-sdk`, installed the way the action installs them, then `mvn -B clean verify` of the whole
  reactor, gm-api included, on JDK 17 (2026-09-28): BUILD SUCCESS, and no `local.pingfederate` directory was
  created. instance-registry-datasource's unused `h2` test dependency is gone with it.
- **Dependabot** no longer ignores `local.pingfederate:*`; the PingFederate coordinates and the `version.pf.*`
  libraries stay ignored.

A consumer who built gm-api or the plugins with the `local.pingfederate` installs no longer needs them; an old
`~/.m2` that still holds them is harmless, since nothing reads them.
