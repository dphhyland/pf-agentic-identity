# 0.3.0 - PingFederate 13.1.3, and OpenID Federation complete

0.3.0 is the first release for PingFederate 13.1.3 - the 13.1.3 cut-over that was 0.2.0 is folded in, and
upgrades are supported from here onward (below). It also makes PingFederate a full member of an OpenID Federation 1.0 federation: it checks chains the way the
Final text says, registers relying parties and agents at every endpoint they arrive at, issues and requires
Trust Marks, answers every federation endpoint, can ask a policy engine, logs its decisions the way
PingFederate logs its own, and passes the OpenID Foundation suite's two federation plans that apply to an OP.
[docs/federation](../federation/README.md) explains it all in plain language.

**Read "Before you deploy" first.** Several changes stop things working until something is done.

## PingFederate 13.1.3 and jakarta

The 13.1.3 cut-over was 0.2.0, a version `main` carried from 2026-09-24 (commit `12626ec`) and never tagged;
this release holds all of it. Where a document here says "from 0.2.0" or "upgrading from 0.2.0", it means
this release.

- **The modules speak `jakarta.servlet`.** PingFederate 13.1 moved its container to Jetty ee9, so every
  servlet, filter and war in this repo is compiled against `jakarta.servlet` and the 13.1.3 SDK
  (`pingfederate-sdk` 13.1.3.0, the version `build/pf-version.env` pins). They do not load on 13.0.x: a filter
  fails the merged war with a 503, an annotated servlet is never mapped. `assemble-pf-runtime-war.sh` reads the
  stock war's namespace and refuses a jar built for the other one, and CI's `tools/pf-linkcheck.py` reports
  0 unresolved members against the 13.1.3 image.
- **The RAR plugin is 13.1-native** (PR #7, `554e688`). It reads the request through
  `AuthorizationDetailContext.getJakartaRequest()`, so `javax.servlet-api` is gone from its pom and the BOM,
  and it no longer links on 13.0 at all. Its descriptor now reports the jar's real version - v0.1.1 to v0.1.5
  all said `0.1.0`.
- **`pf-13.0` is frozen.** `v0.1.5` (2026-09-24) is the last `javax.servlet` release, on that branch, and takes
  no backports (decided 2026-09-26). A PingFederate 13.0.x consumer pins there.
- **Upgrades are supported from 0.3.0 onward.** PingFederate 13.1.3 and v0.3.0 move together - next section.
- **One PingFederate version and one project version** (PR #10). `build/pf-version.env` pins the image by tag
  and digest, and every workflow, the composite action, the rig and the Dockerfile's `FROM` are checked
  against it; `tools/set-version.py` keeps twenty poms on one version, with gm-api
  (`au.com.idpartners:gm-api`) in the lockstep from this release.
- **The release publishes what it verified** (PR #10). The tag must equal the poms, a green Build on the
  tagged commit is required, the reactor runs `mvn verify` with tests and coverage gates on and the link check
  against the pinned image, `PROVENANCE.txt` comes from the staged `MANIFEST`, the release is a draft until
  the Maven artefacts have been compared byte for byte with `dist/`, and a `workflow_dispatch` dry run stops
  before anything is published.
- **The docs describe 13.1.3** (PR #8); dated 13.0.3 results are kept as history.

## Moving from 0.1.5

PingFederate and the artefacts move as a pair, in one commit; `pf-runtime.war` is re-assembled against the
13.1.3 stock war; the config archive is re-exported on 13.1.3 after the first boot; rollback is the 13.0.3
archive with the v0.1.5 artefacts, never a 13.1.3 archive on 13.0.3.
[docs/operator/upgrading/0.1.5-to-0.3.0.md](../operator/upgrading/0.1.5-to-0.3.0.md) has the steps, the
pre-deploy checklist and what each consumer repository must change. Every item under "Before you deploy" is
in that checklist, marked with the version it arrived in: four of them came in v0.1.4 and one in v0.1.5, and
they are listed here because no consumer had moved past the 30 August jars when the migration plan last
checked (2026-09-26).

## Before you deploy

1. **Declare the extended properties.** PingFederate drops an extended property it hasn't been told about,
   without a word, and 0.3.0 relies on ten of them
   ([docs/extended-properties.json](../extended-properties.json)). A registration whose client comes back
   without `status` is refused and the client disabled - without it a federation client looks like one an
   administrator made, never expired and never checked. The conformance rig declares them in
   `conformance/terraform/extended-properties.tf`.
2. **Apply the migrations** to the authority's database, if hosted agents, Trust Mark grants or the key history
   live in one: `V101__hosted_entity_actor.sql` (without it every enrolment and status change fails),
   `V102__trust_mark.sql` and `V103__federation_key_history.sql`.
3. **Decide what happens to clients registered before 0.3.0.** They have no recorded expiry, so they count as
   expired. An automatic one renews on its next request and carries on; an explicit one is refused until its
   relying party registers again. To give relying parties time, set `OIDF_REGISTRATION_EXPIRY_ENFORCEMENT=log`
   for the migration - expiries are recorded and nothing is enforced, the background sweeper included - and set
   it back afterwards.
4. **Re-assemble `pf-runtime.war`** with this release's `assemble-pf-runtime-war.sh`. It maps the new
   front-channel registration filter; a war assembled by an older script registers nobody at the authorization
   or PAR endpoints.
5. **The token filter admits every client, and fails closed** (`35780e9`, 2026-09-25).
   `RegistrationService.automaticRegister` is gone: the filter looks at every token request that names a
   client (the assertion's `sub`, else `client_id`) and `RegistrationService.admit` decides - register, renew,
   or refuse with 401 `invalid_client` or 503 `temporarily_unavailable`. Clients this module didn't register
   are never touched. `OIDF_AUTO_REGISTRATION_FAIL_CLOSED=false` restores the pass-through on failure; a value
   that is neither `true` nor `false` stops the filter starting.
6. **Check every stored RAR plugin instance's switches** (PR #7, `554e688`). Each switch is read with its
   secure default when the stored configuration lacks the field: "Deny unless PERMIT" and "Prefix Attributes
   with Type" now read as `true`; "Fail open on engine error", "Trust a client-asserted principal", "Trust the
   PAR-carried agent marker" and "Skip TLS verification (dev only)" as `false` - the labels as the plugin
   declares them. The one-argument read used before turned a missing "Deny unless PERMIT" off. An instance
   saved through the admin API or an archive that left a field out now refuses a PDP answer
   other than PERMIT, and sends its attributes prefixed with the type - a policy written against the
   unprefixed names stops matching.
7. **The bridge assertion's `aud` is the issuer, as one string** (PR #6, pinned in PR #7 `621336e`). It was
   `[issuer, request URL]`. Nothing to configure: PingFederate accepts its issuer whatever
   `Rfc7523bisCompliantAudienceVerification` says, and FAPI 2.0 asks for exactly this. Turn that switch on in
   production - an archive upgraded from 13.0 arrives with it off
   ([the audience switch](../../servlets/pf-integration/README.md#the-pingfederate-audience-switch)).
8. **Bind each attesting client to its attesters** (`faa0cdc`, 2026-09-15; in v0.1.4 and v0.1.5). A client's
   entry in `OIDF_BRIDGE_SIGNING_KEYS` names the attesters that may vouch for it. The token endpoint answers
   401 to an attestation from a trusted attester the client is not bound to, and - by default - to a client
   whose entry names none. `OIDF_ATTESTATION_REQUIRE_ATTESTER_BINDING=false` relaxes only the unbound case.
9. **Pin the trust anchor's keys** (`7d05d71`, 2026-09-15; in v0.1.4 and v0.1.5). No chain validates without
   `OIDF_FEDERATION_TRUST_ANCHOR_JWKS`, required whenever a trust controller is named. A missing key does not
   stop PingFederate booting: the token-endpoint filters log it at start-up and refuse every request that
   needs a chain, and the registration servlet fails to initialise. `tools/pin-trust-anchor.py` captures the
   keys and prints their thumbprints. The old name `OIDF_TRUST_ANCHOR_JWKS` is still read, with a warning; the
   two names holding different values stop PingFederate starting.
10. **Name the owner of the SSF streams that exist already** (`07e1979`, 2026-09-22; in v0.1.4 and v0.1.5).
    A stream belongs to the client that created it, and streams created before this have no owner: nobody is
    admitted to them, so a poll stream answers 404 until `OIDF_SSF_UNOWNED_STREAM_OWNER` names its receiver
    or the owner is set in the store. The `tables` store adds `owner_client_id` to `ssf_streams` at boot;
    upgrade every node that shares a store together.
11. **Expect the SET backlog to go** (`daf63ea`, 2026-09-22; in v0.1.4 and v0.1.5). `setTtlSeconds` is
    enforced: the first tick after the upgrade deletes every undelivered SET older than the TTL (7 days by
    default) in one statement, poll and push streams alike. An unowned poll stream loses anything older than
    the TTL while it waits for an owner, so name the owner before the TTL passes.
12. **Give provisioning its own scope, and the receiver its audience and token** (`639c678`, 2026-09-23; in
    v0.1.5). `/ssf/scim/v2/Users` takes `OIDF_SSF_PROVISIONER_SCOPE` and nothing else: unset, every SCIM call
    is 403; equal to the receiver scope, the transmitter doesn't start. A body `aud` must be the caller's
    client id or one `OIDF_SSF_ALLOWED_AUDIENCES` lists for it. An enabled receiver refuses to start without
    `OIDF_SSF_RECEIVER_AUDIENCE` and `OIDF_SSF_RECEIVER_ENDPOINT_AUTH_TOKEN`. The rig's configuration carries
    the scope and a provisioner client.

## What changes for clients

- **The token endpoint is fail-closed.** A registration that fails, or an expired one that can't be renewed, is
  answered with a 401 or 503 and the reason, instead of being passed on to PingFederate.
  `OIDF_AUTO_REGISTRATION_FAIL_CLOSED=false` restores the old behaviour.
- **Every registration ends** (§12.3): at its chain's expiry or after a day, whichever is sooner. An explicit
  registration now often lasts an hour; its relying party registers again before the response's `exp`.
- **Scopes and response types are restricted** to what was registered. They weren't before: PingFederate's
  restrict flags were never set, so the lists did nothing.
- **Explicit registration answers 200**, not 201, with the relying party's own keys in the response, as §12.2.3
  says.
- **Relying parties can register at the authorization and PAR endpoints**, with a signed request object or a
  PAR client assertion, and prove themselves again on every request after (§12.1.1). A relying party that
  publishes keys for `openid_relying_party` is registered with those keys, at every endpoint, not with its
  Federation Entity Keys.
- **The OGNL criterion refuses an expired registration** before it looks at the chain, so a deployment that
  gates tokens with the criterion alone enforces §12.3 too.
- **A chain a client presents is checked as it stands.** Nothing is fetched on its say-so; a chain that doesn't
  hold together on its own is found by discovery instead.

## What changes for the federation

- **The entity configuration describes the OP as PingFederate's own discovery does**, with federation's and
  attestation's parameters on top. It used to carry a handful of endpoints and none of the parameters OpenID
  Connect Discovery requires, which failed every module of the suite's deployed-entity plan.
- **Fetch takes `sub` alone**, list takes its filters, **resolve returns a signed `resolve-response+jwt`**, and
  every error is §8.9 JSON with its status.
- **Constraints, `crit`, peer chains and several trust anchors** are handled; metadata policy follows the Final
  text's merge rules exactly.
- **Trust Marks** are verified, can be required per role (`OIDF_FEDERATION_REQUIRED_TRUST_MARKS`) and can be
  issued (`OIDF_FEDERATION_TRUST_MARK_TYPES`, grants through `/federation/admin/trust-marks`).
- **Historical keys** are published when `OIDF_FEDERATION_HISTORICAL_KEYS=true`.
- **Hosted agents have a lifecycle**: `/federation/admin/entities` suspends, reactivates, revokes, re-keys and
  updates them, and records who did.
- **A policy engine can decide** registrations, enrolments and token issuance over AuthZEN 1.0
  (`OIDF_PDP_MODE=authzen`). It can refuse or narrow, never widen; no answer is a 503 unless it fails open.
- **Federation endpoints can require client authentication** (`OIDF_FEDERATION_ENDPOINT_AUTH`), off by default.
- **PingFederate can be its own trust anchor** without pinning its own keys (`OIDF_FEDERATION_SELF_ANCHOR`).

## What changes for operators

- **Decisions are logged as events**: registrations, renewals, expiries and refusals, the policy engine's
  answers, changes to hosted agents and Trust Mark grants, key rotation, and client authentication at the
  federation endpoints. Each is one line in `server.log`, and the security-relevant ones go to PingFederate's
  `audit.log` too. No token reaches an event line: anything shaped like one is replaced with a hash of it.
  [Operations](../federation/operations.md#reading-the-logs) lists them. The "Automatically registered federation
  client" line the demo reads is unchanged.
- **The federation settings are parsed strictly.** A value that doesn't parse stops the component starting, where
  it used to mean the default, quietly. `OIDF_EVENTS_AUDIT` fails safe instead: anything but `true` or `false`
  leaves audit logging on, and says so.
- **The switches that guard something are `true` or `false`.** `OIDF_REQUIRE_METADATA_POLICY`,
  `OIDF_ATTESTATION_REQUIRE_BRIDGE_KEY` and `OIDF_ATTESTATION_REQUIRE_ATTESTER_BINDING` used to read a typo like
  `yes` as `false`, switching the protection off; now it stops PingFederate starting.
- **`OIDF_FEDERATION_ATTESTER_JWKS` must hold public keys.** It is published in the Entity Configuration, and a
  private or symmetric key there used to be published with it. Now it stops PingFederate starting.
- **`OIDF_TRUST_CONTROLLER_HOST`, `OIDF_TRUST_ANCHOR_JWKS` and `OIDF_TRUST_CONTROLLER_IGNORE_SSL` are
  deprecated** for their `OIDF_FEDERATION_` names. The old names still work, with a warning in the log at
  start-up; setting both to different values stops PingFederate starting.
- **`token_endpoint_auth_method` is no longer written as an extended property.** PingFederate 13.1 counts it as
  standard client metadata and refuses to declare it.

[configuration](../federation/configuration.md) lists every setting, and the
[pf-integration README](../../servlets/pf-integration/README.md#upgrading-from-020) has each upgrade note in
full.

## If you run the conformance rig

A PingFederate 13.1 archive authored fresh accepts only its issuer as a client assertion's audience; one
upgraded from 13.0 also accepts the token endpoint, which the suites' ordinary clients send. The rig now sets
`Rfc7523bisCompliantAudienceVerification` off in `conformance/config-store/`, and `export.sh` refuses an archive
without it. Without it the SSF plan passes 1 of 19 on a fresh archive.

## Known gaps

The production-readiness review of 2026-09-26 rated the repo beta and found seven blockers. This release
closes part of one; the rest are Phase 1 and later of the production programme. They are listed so nobody
reads a 13.1.3 release as a production one.

- **RAR containment ignores scalars.** `RarEntitlement` and the plugin's `RarContainment` check `type` and
  five array fields; amounts and accounts pass, and a refresh reissues the requested detail when
  `isEqualOrSubset` says so.
- **Attestations carry raw platform evidence** (`workload.svid`, and the cloud validators' tokens), whose
  audience is the attester: anyone who sees an attestation can re-mint for their own key until the evidence
  expires.
- **The RAR plugin has no trusted principal.** `resource_owner_sub` is never set, and 13.1's `getUserKey()` is
  the client id under client credentials and null under token exchange, so it is not one yet.
- **device-enrolment's `POST /compliance` is unauthenticated**, and devices register `UNKNOWN` while re-minting
  needs `COMPLIANT`.
- **SSF push can stall.** One oldest-first batch across all streams starves push, the HTTP client has no
  timeouts on a single-thread loop, and the loop starts only when a management servlet first initialises. Push
  delivery has not been run against the suite at all (it needs a suite PingFederate can call back).
- **Release and CI**, partly closed here: this is the first 13.1 release, the release runs `verify`, and the
  image is pinned by digest - but Build does not build or boot the image, the one workflow that would
  (`conformance-federation.yml`, weekly and on demand) needs licence secrets the repository does not have and
  has never run, and `main` is unprotected.
- **Single node only.** The stores are per node in memory unless a store is configured, push is not leased,
  and replication of the client writes made through `MgmtFactory` is unverified. There is no cluster story
  until Phase 4.
- **No migration runner.** `V101`-`V103` are applied by hand and `owner_client_id` at boot; nothing records
  which migrations an environment has.
- **Not exercised on a booted 13.1.3**: the attestation filter's wrapped request and the webapp-to-engine
  attribute channel (the rig runs attestation inert), `SsfAuditLogSource`, and the client-authentication model
  `ClientAuthenticationModelTest` pins, which is characterised from `javap` (U-0004 in
  [docs/unverified.md](../unverified.md)).
- **The encrypted-archive checks** (the entrypoint failing closed, the layer scan) were made on 13.0.3 on
  2026-08-21 and not repeated on 13.1.3; `age` 1.3.1 is confirmed present in the image.
