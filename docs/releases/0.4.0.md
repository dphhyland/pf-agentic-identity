# 0.4.0 - Phase 1: blockers closed or mitigated, guard rails up

0.4.0 is Phase 1 of the production programme: the review's blockers B1 to B3 closed, B4 and B5 mitigated, B7
documented as a limit (single node until 0.7.0), the findings register seeded, and CI's hygiene done. Each
package has its own section below; the "Before you deploy" list is the union of what they ask of a consumer.

**Read "Before you deploy" first.** Several changes stop things working until something is done.

## Before you deploy

1. **Decide the deployment profile, because unset now means production** (R-I4, X-D02). `OIDF_DEPLOYMENT_PROFILE`
   is read by the image's entrypoint and by the CIBA simulator: `development` means a rig or a demo, and unset,
   `production` or any other value means production. Two things change with it: a plaintext `data.zip` no
   longer boots in production (next item), and the CIBA simulator never runs there. Set
   `OIDF_DEPLOYMENT_PROFILE=development` on a rig - the conformance rig's `vars.env` does - and nothing on a
   production deployment. Plan item PR-1 (Phase 2) centralises the profile; until then this is the whole
   definition.
2. **Ship `data.zip.age`, or say the deployment is `development`** (R-I4). `pf-entrypoint.sh` refuses a plaintext
   archive - baked in or named by `PF_ARCHIVE_FILE` - with `FATAL: a plaintext archive (...) is refused when
   OIDF_DEPLOYMENT_PROFILE is production`, and PingFederate does not start. Every deployment that still boots
   from a plaintext `data.zip` and does not set the profile stops at the next restart on this version. The
   encrypted path is unchanged in what it needs: the archive and one identity
   ([the image build](../../build/pingfederate/README.md#the-archive-at-boot)).
3. **Move the age identity to a file** (R-I4). `PF_ARCHIVE_AGE_KEY_FILE` is preferred over `PF_ARCHIVE_AGE_KEY`:
   when both are set the file is used, and a file that is named but missing is a refusal, not a fall-through to
   the variable. Both are removed from the environment before PingFederate starts, so nothing that reads the
   PingFederate process's environment - a diagnostic, a plugin, a shell in the container - sees the identity
   from this version. The inline variable remains visible in the container's metadata (`docker inspect`), which
   is why the file is preferred. An identity file the entrypoint was given is no longer deleted after use
   (0.3.0's entrypoint removed it when it could, which on a writable mount was the operator's file).
4. **Optionally pin the archive** (R-I4). `PF_ARCHIVE_SHA256=<hex>` makes the boot check the archive - the
   ciphertext, for an encrypted one - before it is decrypted or imported, and stop on a mismatch.
   `PF_ARCHIVE_FILE=<path>` selects a mounted archive over the one baked into the image.
5. **The plaintext path now takes its keys from the archive** (R-I4). On the plaintext path `pf.jwk` and
   `pingfederate-system-keys.xml` are extracted from inside `data.zip`, as the encrypted path always did, and
   overwrite the `overlay/` copies the Dockerfile still stages. For an archive exported the way the rig's
   `export.sh` does they are the same files. A plaintext archive that lacks them is refused
   (`FATAL: pf.jwk is not in the archive`), where 0.3.0 booted with the overlay copies.
6. **Re-stage `modules/` with the new `stage-modules.sh`, choosing a profile** (R-I1). `MANIFEST` is version 2 -
   a header naming the format, the profile, the build time and the commit; a section per module group; a
   sha256 per jar - and `assemble-pf-runtime-war.sh` refuses a v1 `MANIFEST` (bare filenames), a `modules/`
   staged for a profile other than the one the image is built for (`STAGING_PROFILE`, default `production`),
   and a jar whose digest is not the one staged. `stage-modules.sh` with no argument stages the production
   profile: **nine jars**. `--profile conformance` stages ten, the CIBA simulator among them, and is what the
   rig uses. Anything of yours that counted the module set by counting `MANIFEST` lines now counts the header
   and sections too; count the digest lines, `grep -cE '^[0-9a-f]{64}  ' MANIFEST`. From this version a
   release's module set is the production profile, so `pf.plugins.ciba-sim.jar` is not among a release's
   assets - a rig builds it from source, as `conformance/up.sh` does.
7. **The CIBA simulator needs three settings, and a directory that already exists** (X-D02). The decision
   endpoint answers 404 and the authenticator fails every backchannel request unless `OIDF_CIBA_SIM_ENABLED=true`,
   `OIDF_DEPLOYMENT_PROFILE=development` and `OIDF_CIBA_SIM_DIR` names an absolute path to an existing directory
   that is not a symbolic link, is owned by the user PingFederate runs as and is `0700`, on a POSIX filesystem.
   The plugin no longer creates the directory or falls back to the JVM's temp directory; the conformance image
   makes `/opt/ciba-sim` to this shape, and the rig's `vars.env` names it
   ([plugins/ciba-sim](../../plugins/ciba-sim/README.md)). Both halves check before every request and log the
   reason for a refusal at WARN.
8. **An image built from `conformance/compose-context.sh`'s output needs the build arg** (R-I1). `.context/modules`
   is staged for the conformance profile from this version - `up.sh` stages it so, and `compose-context.sh` accepts
   nothing else - so a plain `docker build .context`, which builds for the default profile, stops at the assembler:
   `modules/ was staged for the conformance profile, and this image is being built for production`. Pass
   `--build-arg STAGING_PROFILE=conformance`, or your platform's equivalent, and know what comes out: a conformance
   image, the CIBA simulator in it, gated by item 7's three settings, which `.context/vars.env` carries. For a
   production image, stage again with `stage-modules.sh --profile production` and build without the arg.
9. **A production Redis URL must be `rediss://`** (S3a, `a7911f1`). `MiniRedisClient` refuses `redis://` unless
   `OIDF_DEPLOYMENT_PROFILE=development`, because the password in `AUTH` would otherwise cross the network in
   the clear. If you do nothing and your `OIDF_REDIS_URL` (or `REDIS_URL`) is plaintext, every store accessor
   throws from the first request: the token endpoint answers 500 `server_error` to attested clients, the
   challenge endpoint and the attester answer 500 (a configuration error, not an outage, so not the 503 of
   item 11), and an OGNL issuance criterion built on `ClientAttestationUtils` fails as if the attestation were
   bad. `server.log` carries one ERROR from `AttestationSupport` quoting the refusal, which names `rediss://`
   and `OIDF_DEPLOYMENT_PROFILE` but not the variable that holds the URL, and after it the token endpoint's
   filter logs an ERROR with a stack trace for every attested request. No message quotes the URL's password:
   `MiniRedisClient` replaces the userinfo with `***`. Move to `rediss://`; the server's certificate must chain
   to the JVM's CAs or to the PEM file `OIDF_REDIS_CA_FILE` names, and must name the URL's host (an IP literal
   is checked against the address). Plan item PR-2 makes a refused URL a 503.
10. **Redis keys move to new namespaces** (S3a). 0.3.0 wrote `oidf:challenge:*` and `oidf:jti:*`; 0.4.0 writes
   `oidf:as:*`, `oidf:cas:*` and `oidf:fed:endpoint:*` (and reserves `oidf:admin:dpop:*`) and reads nothing
   under the old prefixes. The old keys are orphaned until their own TTL expires them: 300 s for a challenge,
   360 s for an attestation proof's `jti` (maximum age plus skew), up to 660 s for a federation endpoint's
   client assertion, and as long as its own `exp` allows, at most 86400 s, for the request object or client
   assertion of an automatic registration. What that means for replay: a credential spent against 0.3.0 is
   unknown to 0.4.0, so it can be presented once more to a 0.4.0 node until it expires - during a rolling
   upgrade, and after a stop-the-world one too, because 0.4.0 never reads the old keys. The window runs the
   other way as well during a rolling upgrade: a credential spent at a 0.4.0 node is recorded only under the
   new prefixes, which the 0.3.0 nodes never read, so it can be presented once more to a 0.3.0 node until the
   last of them stops. A proof or an assertion lives minutes; a registration request object lives as long as
   its `exp`. Where a challenge is required the proof carries it, and a challenge issued by one version is unknown to the other (400
   `use_attestation_challenge`, and the client fetches another), so those proofs cannot cross. To close the
   rest, stop every 0.3.0 node and wait out the longest window your clients' credentials allow before starting
   0.4.0; otherwise accept it, knowing that a replay needs a spent credential someone intercepted. Nothing needs
   flushing - the old keys expire on their own - and `FLUSHDB` would drop 0.4.0's live challenges and spent
   `jti`s with them.
11. **A store outage is now 503, not a refusal** (S3a). When Redis cannot answer, the token endpoint, the
   challenge endpoint and the attester answer 503 `temporarily_unavailable`. 0.3.0 answered with a refusal
   instead: at the token endpoint 401 for a "replay" or 400 `use_attestation_challenge`, at the attester 401
   `invalid_instance_proof`, and at the challenge endpoint 500, because its store threw. The code is RFC 6749's (§4.1.2.1, defined there for the authorization endpoint); the
   federation endpoints' 503 is OpenID Federation 1.0 §8.9's. Anything that alerts on a rise in 401s from
   attested clients should alert on 503s too. A client should retry later with a fresh proof, and fetch a new
   challenge only if the retry answers `use_attestation_challenge`: the challenge survives an outage of the
   challenge store, but not one that came after it was consumed. Two callers do not answer 503: the
   automatic-registration filter answers 500 `server_error`, and an OGNL issuance criterion built on
   `ClientAttestationUtils` fails, as it does for any refusal, so a deployment whose only gate is that
   criterion sees an ordinary authentication failure.
12. **Attestations no longer carry the evidence; read the digest** (S3b). `workload.svid` (every SPIFFE-shaped
   evidence type) and `workload.instance_attestation` (the wallet WIA) are gone from minted attestations and
   from everything downstream of them: the PDP request's `attestation.workload` and any token attribute
   mapped from the verified attestation. In their place, `workload.instance_attestation_sha256`,
   `workload.instance_attestation_type` (the evidence type id) and `workload.instance_attestation_exp`. The
   digest is the SHA-256, lower-case hex, of the evidence's first two segments, header and payload, which is
   its JWS Signing Input and what its signature covers: `printf %s "${token%.*}" | sha256sum` computes it
   from a captured token. It is not the SHA-256 of the whole token, because one signed token verifies in many
   encodings. Attestations minted before the upgrade, or by an attester still on 0.3.0, keep carrying
   `workload.svid` into the PDP and into tokens until they expire (`attestation_issued_ttl`, 300 s by
   default). Consumers this repository cannot edit, from what their names say they hold (none of them could be
   opened from here, so check each; U-0071 records it):
   - **pf-oidf-modules**: the harness text and the explainers that print or describe `workload.svid` must
     print the digest and say what it is; a harness that asserts the SVID is in the attestation now fails,
     and one that re-verifies the SVID from the attestation has nothing to re-verify - compare
     `instance_attestation_sha256` with the digest of the token it presented instead, computed as above
     (header and payload only). Its terraform's access-token mappings and PAZ policies that name
     `workload.svid` get nothing; map or match the three new members.
   - **domain-authority**: traces that show `workload.svid` in the minted attestation show the digest now;
     any trace that expected the raw token to reach the PDP is out of date.
   - **the connector**: its copy of `InstanceIdentity` must take the nine- or ten-argument shape (evidence
     type, digest, audiences, and the evidence's `iat`), with the digest from `InstanceIdentity.evidenceDigest`,
     or keep the six-argument one and accept that its attestations carry `instance_attestation_exp` alone and
     are not bound; either way it must stop putting the token in `workloadClaims`.
13. **Evidence binds to its first presenter** (S3b). Once the key proof and every other check have passed, just
   before minting, the evidence's digest is bound to the instance key's thumbprint and the client for as long
   as the evidence lives. A request refused by any of those checks never takes the binding; one that fails
   after it, at the signer say, keeps it, having passed them all. Presenting evidence already bound to another
   key or client is 401 `instance_attestation_bound` and an `attestation.evidence.conflict` audit event, which
   names the key refused (`presented_jkt`) and the key and client that hold the binding (`bound_jkt`,
   `bound_client`). The digest covers only header and payload, so the same token re-encoded - trailing
   whitespace, another encoding of its signature - meets the same binding. Two things change for a workload.
   First, one that regenerates its instance key while its evidence is still live meets its own binding. The
   SPIRE agent caches a JWT-SVID per SPIFFE ID and audience and returns the cached one until less than half
   its lifetime is left (spiffe/spire main, fetched 2026-09-27: `FetchJWTSVID` in
   `pkg/agent/manager/manager.go`, `JWTSVIDExpiresSoon` in `pkg/common/rotationutil/rotationutil.go`), and a
   projected cloud token is the same file until it rotates. So keep the instance key for the evidence's life,
   persisting it across restarts; or wait for the cached evidence to rotate; or, on a SPIRE that has it,
   register the entry with a `jti` claim, which makes the agent bypass its cache and mint a fresh SVID for
   every fetch. A conflict right after a restart is most likely this, not a theft. Second, a deployment that
   shares one piece of evidence between several instances or clients cannot any more, and replicas that
   share a SPIFFE ID share the agent's cached SVID. With no Redis the binding is per node, so a thief can
   still win on a node that has not seen the rightful holder: a clustered deployment needs the shared store.
14. **Evidence may live at most a day, and the attestation never outlives it** (S3b). Evidence issued to live
   longer than `OIDF_ATTESTER_MAX_EVIDENCE_LIFETIME_SECONDS` (86400), measured `exp - iat` when it has an
   `iat`, or with more than that of life left, measured `exp - now` with 60 s allowed for a clock behind the
   issuer's, is refused with `invalid_svid` / `invalid_instance_attestation` naming the variable. A token
   issued for exactly a day is accepted, even from an issuer whose clock is a little ahead; a year-long one
   is refused on its last day too. Production may set the value lower, never higher
   (a higher value is a 500 `server_error` naming the variable from the first request), a rig may with
   `OIDF_DEPLOYMENT_PROFILE=development`. The minted attestation's `exp` and the `expires_in` in the response
   are capped at the evidence's `exp`: a client whose `attestation_issued_ttl` exceeds its evidence's
   remaining life gets a shorter attestation than it asked for. `OIDF_ATTESTER_REQUIRE_SINGLE_AUDIENCE_EVIDENCE=true`
   additionally refuses evidence whose `aud` names more than one party; the default is `false`.
15. **`OIDF_ATTESTER_CIMD_URL` does nothing outside development** (M-1). Unless `OIDF_DEPLOYMENT_PROFILE=development`,
   the attester leaves the CIMD source out with an ERROR naming the variable, the discovery document's
   `resolver_plugins_active` omits `cimd` (and the CAS document's `client_metadata_sources_supported` no longer
   lists it for `OIDF_CIMD_TRUST_BUNDLES`), and clients only that document describes cannot be issued
   attestations; clients from the federation and PingFederate sources are unaffected. A deployment that
   relied on CIMD for production clients has no supported path until X-B02 (Phase 5) lands; move those
   clients to PingFederate's client store or to a federation entity.
16. **Code that implements or calls the client-attestation stores must change** (S3a, S3b). The library's store
   interfaces answer in three states. `AttestationReplayCache.record` and
   `AttestationChallengeService.consumeChallenge` are now the abstract methods; `firstSeen` and `consume` are
   defaults over them that throw `StoreUnavailableException` (an `IllegalStateException`) for an outage, where
   0.3.0's answered `false`. An implementation of 0.3.0's interfaces no longer compiles, and a caller of the
   boolean views that caught nothing now sees an exception for an outage. `EvidenceBindingStore.bind` is new,
   and returns a `Result`: the outcome and, on a conflict, the key and client that hold the binding.

17. **Every RAR field is compared, and undeclared fields are refused** (S-1, blocker B1: S1a, S1b, S1c). The
   token gate, the attester and the RAR plugin all ask [libs/rar-model](../../libs/rar-model/README.md); the
   items from **Token and PAR requests are compared field by field with the attestation's
   `authorization_details`** on, and from **Deploy the plugin and the attestation filter from one release** on,
   say what each surface does. In short:
   - A token request whose `authorization_details` relied on a scalar going unexamined - an amount above the
     attestation's, a different creditor account, a later `validUntil` - is refused with
     `invalid_authorization_details` where 0.3.0 granted it.
   - A field the type's model does not declare is refused, so a type with fields of its own needs a models
     document (`OIDF_RAR_MODELS_FILE` or `OIDF_RAR_MODELS`, one for the whole PingFederate process, read by the
     attestation filter, the attester and the plugin alike) that `extends` the built-in.
   - Values are typed: `identifier`, `purpose`, `creditorName`, `remittanceInformationUnstructured` and the flat
     `currency` are non-blank strings, `limit` and `amount` values are non-negative decimals of at most 64
     digits, and `validUntil` is RFC 3339 with seconds, or a full date, which means the last instant of that day
     in UTC. Anything else is malformed.
   - A `payment_initiation` detail says its amount one way, `instructedAmount` or the flat `amount` and
     `currency`; a detail with both is refused, and a request must use the spelling of the ceiling that
     constrains it, so an attester's ceilings and its clients' requests need to agree.
   - `account_information` has no `access` object: RFC 9396 §7.1-shaped requests, Figure 16 included, are
     refused until a models document swaps `access` in for `accounts` (the module README has the document).
   - At the attester, a constrained field the request omits is filled from the ceiling for every rule, so
     attestations carry, say, `max_txn_eur` and `currency` explicitly. At the token endpoint nothing is filled
     in: see **A token request restates every field its attestation constrains**.
   - The plugin refuses a request whose attestation context carries another model fingerprint or lacks one (a
     request with no attestation context is decided without the comparison), and `OIDF_RAR_EXTRA_TYPES` no
     longer makes a type acceptable on its own: a type of your own needs a model as well as a name there.

   The payment fields the RAR plugin reads and its tests send (`amount`, `currency`, `debtorAccount`, `purpose`)
   and the RFC 9396 Figure 2 fields are in the built-in model; what idp-agentic-demo sends beyond them, and the
   types of what it sends, is [U-0057](../findings/U-0057.yaml). Check your clients' requests against the
   built-in tables before upgrading. One grant is not covered: on the JWT-bearer grant the requested details
   reach the token without the model or the PDP ([F-0108](../findings/F-0108.yaml); "Known gaps" says how to
   avoid it).

18. **Give the RAR plugin an `https` PDP URL, or say the deployment is `development`** (S2a). The plugin refuses
   a plaintext PDP URL unless `OIDF_DEPLOYMENT_PROFILE=development` (item 1's reading: unset is production).
   The admin console and the admin API reject the field. An instance imported from an archive with an
   `http://` URL fails to configure, and the plugin refuses every request that reaches it with
   `invalid_authorization_details` (U-0068 is what PingFederate itself makes of such an instance). A rig or a
   demo sets `development`.
19. **Give the PDP a certificate PingFederate's JVM trusts** (S2a). "Skip TLS verification (dev only)" now means
    what its name says: outside `development` it is inert, the PDP's certificate is checked, and configure logs
    a WARNING naming the switch. A deployment that reached a self-signed PDP through it now gets a TLS failure,
    which denies. The JDK client checks the hostname either way; the plugin README says why the JVM-wide
    property that turns that off must not be set.
20. **Expect a client-credentials caller to be refused for payments and account queries** (S2b). The new field
    "Types requiring an authenticated principal" (default `payment_initiation,account_information`) refuses those
    types before any PDP call when the principal is nobody or is the client - and under client credentials
    PingFederate passes the client id as the user key, so the principal is the client. A machine-to-machine
    caller that used to get a `payment_initiation` detail decided about itself now gets 400
    `invalid_authorization_details`. Give it a flow with a person in it (CIBA, the code flow, a refresh of
    either), or take the type off the list where a deployment has decided a client may hold it; a single `-`
    empties the list.
21. **Save every RAR plugin instance again after upgrading** (S2a). "Shared Secret" is an encrypted field now,
    under the same name. A value an older jar stored in the clear keeps working. Rehearsed on the rig on
    2026-09-27 (13.1.3.0): an instance created under v0.3.0 was imported under this version, PingFederate
    logged one ERROR (`There was a problem deobfuscating the value for the field: Shared Secret`) and handed the
    plugin the value as stored, and the PDP received the same secret. Until the instance is saved again the
    secret stays in the clear on disk and in every archive exported from it. Saving it - Save in the console, or
    a `PUT` of the instance through the admin API - stores it encrypted, which the rehearsal saw on disk.
22. **Fail-open means unreachable, and nothing else** (S2a). "Fail open on engine error" grants through a
    connection refused or reset, an unresolved name, a deadline, or HTTP 429, 502, 503 or 504. It refuses a 401
    or 403 from a wrong secret, every other status, a body that is not a JSON object, a non-JSON content type,
    an AuthZEN answer without a boolean `decision`, a status line or header the client cannot parse, and a TLS
    failure. A deployment that relied on the switch to paper over a wrong secret or a certificate that does not
    match now sees denials: fix the secret or the certificate. Both dialects also refuse a body with content
    after the JSON object or a member named twice, and the governance engine's answer is refused when
    `decision` is not a string or `authorised` is not a JSON boolean (`"true"` and `1` used to read as a
    permit). A PDP that answers in the shape the plugin has always documented, a string and a boolean, is not
    affected.
23. **"Deny unless PERMIT" is gone** (S2a). The decision is always deny-unless-PERMIT. An instance saved with the
    switch off now refuses a DENY. The stored field is never read, and it does not stop the instance loading:
    an archive exported under 0.3.0 carries it, and the rehearsal in item 21 imported that archive, and the
    instance configured and decided. Saving the instance again drops the field.
24. **Point policy at the new PDP request shape** (S2a, S2b). `principal_source` is one of `authenticated`,
    `client`, `identity_hint`, `subject_token`, `client_asserted` (development only) or `none`. The AuthZEN
    `subject.type` is `client` for a client principal. The attester's `iss` arrives as `context.actor.iss` and
    `context.attestation.iss` (AuthZEN), or as `actor_iss` and `attestation.iss` (governance engine). The
    request attribute `com.pingidentity.ps.oidf.rar.resource_owner_sub` is no longer read: the principal comes
    from PingFederate's user key. In the governance-engine dialect the server's attributes are written last,
    and a requested field whose attribute name is one of them is refused: `UserID`, `principal_source`,
    `actor`, `actor_iss`, `client_id`, `attestation.entitlement`, `attestation.workload`,
    `attestation.cnf_thumbprint`, `attestation.iss`, and the `req_` and `att_` mirror of every set-valued field
    (`actions`, `locations`, `datatypes`, `privileges`, `sales_regions`). Only an empty "Attribute Prefix" with
    "Prefix Attributes with Type" off can produce those names (F-0073).
25. **`login_hint` and `_principal_sub` need `OIDF_DEPLOYMENT_PROFILE=development` as well as the switch**
    (S2b). "Trust a client-asserted principal" is inert in production, with a WARNING at configure time. Both
    go at 1.0 (plan decision 9).
26. **Give the authentication contract behind the authorization endpoint a `subject` attribute** (S2b).
    PingFederate 13.1.3 asks the plugin once in the code flow, at the resume after authentication
    (`OAuthResumableRequestHandlerBase`, path `/as/<id>/resume/as/authorization.ping`), and the user key it
    passes is the authentication result's `subject` attribute. The rig's HTML-form adapter has no such
    attribute. Without it the plugin knows nobody and refuses `payment_initiation` and `account_information` with
    `invalid_authorization_details` after the user has signed in. With `subject` mapped on the adapter (by
    expression from `username`) the same flow is decided about `suite-user`, and the token is issued for them.
    Both were driven by `conformance/verify-rar-principal.sh` on 2026-09-27 (13.1.3.0). The mapped attributes
    also reach the plugin under the SDK's `IN_PARAMETER_AUTH_DETAILS_USER_INFO` parameter, which it does not read:
    the deployment says who the principal is by mapping `subject`. Seen with the mapping on the adapter only; on
    an authentication policy contract it is U-0067.
27. **Token exchange is decided about nobody** (S2b). PingFederate passes no user key for the token-exchange
    grant, and skips the plugin when the requested token type is `id-jag`. The token-endpoint filter does not
    publish a verified subject-token subject yet (F-0074, with S4c), so `principal_source` is `none`: the payment
    and account types are refused, and other types reach the PDP with the client as subject.

28. **`POST /compliance` is gone from device-enrolment** (M-2, the B4 mitigation). Anything that called it
   gets 404. Nothing in any known environment did: the service has never been deployed. Read
   [services/device-enrolment/README.md](../../services/device-enrolment/README.md#not-production-usable-until-phase-6)
   before deploying it anywhere: a device enrols `UNKNOWN`, re-minting needs `COMPLIANT`, and until Phase 6
   nothing in this repository can make it so. `REQUIRE_COMPLIANT_DEVICE=false` is the development switch,
   and it removes the compliance control rather than satisfying it.
29. **SSF push delivery changes behaviour at boot, and nothing needs configuring** (S10-0, the B5 stopgap;
    [servlets/ssf/README.md](../../servlets/ssf/README.md#upgrading-to-040)). The push loop starts with
    PingFederate rather than with a receiver's first management request. A data store that is down when
    PingFederate boots no longer stops `pf-runtime.war` from starting (until now every runtime endpoint
    answered 503): the SSF endpoints answer 500 and the log says `SSF transmitter NOT started` until a
    retry, every 30 s, opens it. A push receiver that takes more than 10 s to answer, or 2 s to accept a
    connection, is now a retryable failure - its stream dead-letters when its oldest SET has failed
    `pushRetryMaxAttempts` times, about 100 s at the defaults - where before the loop waited for it. A stream
    whose delivery fails sends nothing more until that SET is due again, and then sends it first; SETs issued
    in the same second go in `jti` order, not the order they were generated in (F-0095). Held SETs on a paused
    or disabled stream are no longer read for push; they never delivered before either. The events
    PingFederate raises while the store is down, or while a stream is paused, are not queued (F-0017).
30. **device-enrolment reads `IDM_DATABASE_URL`, whatever its README said.** (HYG) The README's configuration table
    named `DATABASE_URL`. `Main` requires `IDM_DATABASE_URL` - the Identity Object Model directory, as a JDBC URL
    or a `postgresql://` DSN - and refuses to start when only `DATABASE_URL` is set, naming the rename. The code
    did not change here; if you configured the service from the README, rename the variable. The table now lists
    every variable `Main` reads, `REGISTRY` and the connector path's twelve included.
31. **Delete a `pf.plugins.ciba-sim.jar` that v0.3.0's assets left behind.** (HYG) v0.3.0's release assets carry the
    CIBA simulator (checked 2026-09-27), and there it runs on `OIDF_CIBA_SIM_ENABLED` alone. From 0.4.0 the
    release stages the production profile and its assets leave the simulator out, so copying the new assets over
    the old ones keeps the old jar. In `modules/` the assembler refuses it, because 0.4.0's `MANIFEST` does not
    name it; a jar you copied into `server/default/deploy` yourself stays loaded until you delete it.
32. **Token and PAR requests are compared field by field with the attestation's `authorization_details`.** (S1B) The
    attestation filter, and the issuance criterion where the filter does not run, compare a request's
    `authorization_details` (or `oidf_requested_access`) with the verified Client Attestation's using
    [libs/rar-model](../../libs/rar-model/README.md): every field by its type's rule. 0.3.0 compared `type` and
    five array fields, so an amount above the attestation's, another creditor account or a later `validUntil` was
    granted; it is now refused. A field the type's model does not declare, a type no model names and a value of the
    wrong shape are refused too. idp-agentic-demo's payment fields in the built-in tables pass; what it sends beyond
    them is [U-0057](../findings/U-0057.yaml). A type with fields of its own needs a models document that
    `extends` the built-in: see **Give every PingFederate node the same models document, or none**.
33. **A token request restates every field its attestation constrains.** (S1B) The token gate compares strictly: a field
    the attestation's details constrain and the request leaves out is not within them, and the request is refused.
    0.3.0 granted it, and PingFederate issued the detail without the field, which reads as unconstrained - wider
    than the attestation. The filter forwards the request's own details, so the gate cannot fill a field in: a
    constrained field the request omits is filled from the ceiling at the attester, at issuance, never at the token
    endpoint. What to change: for every field an attestation's detail
    carries, send that value or a narrower one. An attestation of
    `[{"type":"sales_agent","sales_regions":["EMEA"],"max_txn_eur":5000}]` needs a request that names
    `sales_regions` and `max_txn_eur`. How to tell: 400 with `authorization_details exceeds what the client
    attestation allows`.
34. **A refused request is 400 `invalid_authorization_details`, not 401 `access_denied`.** (S1B) CAS §7.1: an
    authorization server "MUST reject requests exceeding it with `invalid_authorization_details`". The filter
    answers 400, the status RFC 6749 §5.2 gives the token endpoint's errors, with a fixed description:
    `authorization_details is malformed`, `authorization_details exceeds a size limit`, `authorization_details
    carries a field its type does not define`, `authorization_details names a type this server does not support`,
    or `authorization_details exceeds what the client attestation allows`. An attestation whose own details this
    server's model refuses - a type it has no model for, say - is 401 `invalid_client`, `the client attestation's
    authorization_details cannot be evaluated by this server`. The log line names the detail and the field; no
    response carries a value. On the criterion path PingFederate answers a refusal with the Error Result configured
    on the criterion (400 `invalid_grant`). What to change: a client that read 401 `access_denied` as "outside my
    attestation" reads 400 `invalid_authorization_details`.
35. **A repeated `authorization_details` is refused where the criterion verifies.** (S1B) Where no filter verified the
    request, the issuance criterion refuses a token request carrying `authorization_details` or
    `oidf_requested_access` more than once: it checks the first value, and nothing there decides which one
    PingFederate goes on to read. RFC 6749 §3.2: "Request and response parameters MUST NOT be included more than
    once." The filter path is unchanged - it forwards only the value it checked. What to change: send each parameter
    once. How to tell: `server.log` says `Multiple 'authorization_details' parameters present`.
36. **Give every PingFederate node the same models document, or none.** (S1B) `OIDF_RAR_MODELS_FILE` (a path) or
    `OIDF_RAR_MODELS` (the document inline), environment variables only, not both. It is read once per classloader:
    when the attestation filter or the attester starts, and on the criterion's first call. Its fingerprint is logged
    (`RAR containment models loaded: fingerprint=...`) and published in the attestation context as
    `rar_models_fingerprint`, which the RAR plugin compares with its own from S1c, so the plugin must see the same
    variables. A document the library refuses, an unreadable file, or both set: with attestation authentication
    configured the filter refuses to start, which takes `pf-runtime.war` and PingFederate's runtime down with it, as
    a broken bridge configuration does (plan item S-9 changes that in Phase 3); the attester fails from its first
    request; the criterion refuses every attested token. How to tell: `server.log` says `RAR containment models
    could not be loaded`, naming the reason.
37. **Stage `rar-model-<version>.jar` beside the other modules.** (S1B) `build/pingfederate/stage-modules.sh` stages it:
    nine jars in production, ten in conformance. A deployment that copies jars by hand puts it in both
    `pf-runtime.war`'s `WEB-INF/lib` and `server/default/deploy`: without it the attestation filter does not start,
    and the criterion and the attester fail with `NoClassDefFoundError`. `oidf.war` and
    `services/device-enrolment` take it as a dependency.
38. **The attester holds configured ceilings to the model, and an instance ceiling keeps what its client's
    constrains.** (S1B) `attestation_entitlement` and each instance's `entitlement` must be details the model accepts. A
    client whose ceiling it refuses is skipped by the PingFederate client store, with a warning naming it; a CIMD or
    federation source refuses its whole mapping list, as it does for any invalid entry. An instance ceiling under a
    client ceiling is now `authorize(instance, client, INHERIT)`, kept: an instance that left out a field its client
    constrains gets the client's value (F-0034). Its attestations carry that field, so **A token request restates
    every field its attestation constrains** applies to them. How to tell: `server.log` says `Skipping attestation
    client with invalid config`. Both properties, and the whole `attestation_instances` value with its metadata, are
    now read by a strict RFC 8259 reader, not jose4j: a trailing comma or other input 0.3.0 tolerated makes the
    client's configuration invalid, with the same warning. CIMD and federation sources are not affected.
39. **The attester mints the fitted grant, and narrows an asserted context to the overlap.** (S1B) A requested detail is
    minted with every field its ceiling entry constrains and the request leaves out, for every rule; an empty
    request still gets the full ceiling. A request outside the ceiling is 403 `access_denied`; one the model cannot
    compare is 400 `invalid_request`, naming the detail and the field; `_principal_sub` and `_agent_id` in an
    issuance request are refused. An asserted-context ceiling narrows with the model's meet: an evidenced
    EMEA-and-APAC entry under an asserted EMEA one is minted as EMEA, where 0.3.0 dropped it - more than before,
    never more than both allow.
40. **Code that builds a `ClientAttestationVerifier` or reads its result has new members.** (S1B)
    `ClientAttestationVerifier.withRarModels(...)` takes a model set; the public constructor takes the
    classloader's and throws `IllegalStateException` when it could not be loaded. `ClientAttestationResult` gains
    `rarModelsFingerprint()` and a ten-argument constructor, and `grantedAuthorizationDetails()` is the request's own
    details without the two markers, no longer filled from the attestation. `RarEntitlement` is deprecated for
    removal (F-0100), and `rar-model` is a new dependency of `client-attestation`.
41. **Deploy the plugin and the attestation filter from one release.** (S1C) The filter publishes its model set's
    fingerprint in the attestation context from 0.4.0 (S1b), and the plugin refuses a request whose context lacks
    it or carries another. With a 0.4.0 plugin beside a 0.3.0 `pf-integration`, the requests the plugin decides at
    the token endpoint for a client the filter verified - client credentials or token exchange with
    `authorization_details`, and a refresh that restates them - are refused before the PDP is asked, with
    `invalid_authorization_details`. A request with no attestation context is decided without the comparison: a
    client the filter did not verify, the authorization endpoint's resume, CIBA's backchannel request, and
    PingFederate's consent and grant-reuse checks, which pass no request.
42. **Give the whole PingFederate process one models document.** (S1C) The plugin reads `OIDF_RAR_MODELS_FILE` or
    `OIDF_RAR_MODELS` itself, once, as the filter and the attester do; a plugin GUI field would let the two drift,
    which the fingerprint exists to catch. Unset, the model is the three built-in types. A document the library
    refuses leaves the plugin with no model: it logs a SEVERE line saying why and refuses every request until the
    document is fixed and PingFederate restarted. The start-up line `RAR models loaded: fingerprint=...` and each
    instance's `rarModels=` say which model set a node runs.
43. **A detail the model cannot read is refused before the PDP.** (S1C) Every field is compared now, so a field the
    type's model does not declare, a type no model names (outside `OIDF_DEPLOYMENT_PROFILE=development`) and a
    value of the wrong shape - a flat `amount` without `currency`, a negative limit, an empty array, a blank
    string - answer `invalid_authorization_details`, and the PDP is not asked. idp-agentic-demo's payment fields
    pass; what else it sends is not visible from here (U-0057). A field of your own needs a models document with
    `extends`, and a type of your own needs a model and a name in `OIDF_RAR_EXTRA_TYPES`, which still decides what
    PingFederate may bind to the processor.
44. **A PDP's statements may narrow a request and never widen it.** (S1C) After a PERMIT the plugin merges the statements
    into a copy of the request and refuses the result unless the model finds it within the request: a lower
    amount, a region fewer or a limit the request left open is granted; a higher amount, another currency, another
    payee, an added region, a changed type or a field the type does not declare is `invalid_authorization_details`.
    Every AuthZEN response `context` member other than `id`, `reason_admin` and `reason_user` is a statement, so a
    PDP that returns, say, a trace id in its context now denies. The policies under `plugins/rar-paz-plugin/paz`
    return no statements; check what yours return before you upgrade.
45. **A refresh that restates `authorization_details` must stay within its grant.** (S1C) It is compared with the
    model's strict `contains`: more than the grant, another payee or another currency, or a constrained field left
    out, is `invalid_authorization_details` where 0.3.0 compared five array fields and issued the rest. A grant
    issued before 0.4.0 whose stored details the model cannot read - a statement's field no model declares, say -
    can no longer be refreshed with `authorization_details`. A refresh without the parameter still reissues the
    stored details without asking the PDP (F-0105), and the plugin is asked about it only where approved consent is
    reused (**Consent and grant reuse follow the stricter answer.**). So a grant issued before 0.4.0, whose details
    were compared on five array fields only, keeps them for its lifetime: until plan item S4d, revoke or re-issue
    the grants issued before 0.4.0 that carry `payment_initiation` or `account_information`, and keep refresh-token
    lifetimes short for those types.
46. **Consent and grant reuse follow the stricter answer.** (S1C) PingFederate 13.1.3 also asks `isEqualOrSubset`
    whether approved consent covers a request, which stored grant a request may reuse, and which consent records a
    changed consent deletes (read with `javap`, not driven: U-0115). Expect a consent prompt where 0.3.0 reused a
    consent for a larger amount. With "bypass authorization for approved consents" on, and for a client that does
    not bypass the approval page, a grant issued before 0.4.0 whose details exceed its consent, or cannot be read
    by the model, is revoked at its next refresh (`invalid_scope`, "revoked, or expired consent"), bare refreshes
    included. Revoke or re-issue such grants on your own schedule before the upgrade if that matters. These checks
    pass no request, so no attestation context and no fingerprint comparison.
47. **A client attestation PoP must be addressed to PingFederate's issuer, and to nothing else.** (S4A) The token
    endpoint URL, another server's identifier, or an `aud` array with a second member is refused with 401
    `invalid_client` and the description "Client Attestation PoP 'aud' must be this server's issuer identifier
    and nothing else". The issuer as a string, or as the one member of an array, is accepted.
    draft-ietf-oauth-attestation-based-client-auth-10 §5.1 asks for exactly this: "When the JWT is presented to
    an Authorization Server, the [RFC8414] issuer identifier URL of the Authorization Server MUST be used. [...] A
    Client Attestation PoP JWT is intended for a single audience". How to tell: the token or PAR response carries
    that description, and PingFederate's `server.log` has `attest_jwt_client_auth: rejected [invalid_client]` with
    it (on the OGNL criterion route, where there is no filter, the client gets 400 `invalid_grant` and the log line
    is `Attestation-based client authentication failed [invalid_client]`). What to change: address the PoP to the
    `issuer` of PingFederate's `/.well-known/openid-configuration`, which the attester also publishes as
    `pop_audience` in `/.well-known/client-attester`. The workloads in pf-oidf-modules already do (read on
    2026-09-27: `bootstrap.py` sends `OP_ISSUER`, `agent-workload/app.py` sends PF's base URL).
48. **A combined-mode DPoP proof must name the endpoint URL PingFederate advertises.** (S4A) The `htu` is compared with
    `token_endpoint` at the token endpoint (PingFederate's token endpoint base URL when one is set, otherwise the
    issuer, then `/as/token.oauth2`) and with `pushed_authorization_request_endpoint` at PAR (the issuer, then
    `/as/par.oauth2`), after RFC 3986 normalisation. The `Host` header, `X-Forwarded-*` and the request URL no
    longer count. A client that reaches PingFederate by a name other than its base URL - a compose service name, or
    a proxy whose public name PingFederate does not have as its base URL or a virtual host name - is refused with
    401 `invalid_client` and "DPoP proof verification failed: DPoP 'htu' mismatch: got '<the proof's htu>',
    expected '<the configured URL>'" (on the OGNL route, 400 `invalid_grant` and that text in `server.log`). What
    to change: make PingFederate's base URL (Server Settings > Federation Info) the URL clients use, which the
    issuer in its tokens and discovery needs anyway. Adding the client's name to PingFederate's virtual host names
    also works, but it moves the issuer: for a request that names a virtual host, PingFederate answers with that
    name and the request's port as its issuer (`BaseUrlUtil.getCurrentBaseUrl`, 13.1.3, javap), so the PoP `aud`
    the server expects under **A client attestation PoP must be addressed to PingFederate's issuer, and to nothing
    else** and the `iss` of the tokens it issues change for those requests too. A PoP-mode client that reaches
    PingFederate by that name but addresses its PoP to the base URL is then refused. On the OGNL route only,
    `extproperties.attestation_expected_htu` still pins one client's `htu`, if the deployment declares that
    extended property. In idp-agentic-demo (9eee704, read on 2026-09-27) the concierge (`agent/auth.py`) sends its
    `PF_TOKEN_URL` as the `htu`, so it is affected when it runs with `TOKEN_MODE=pingfederate` and a `PF_TOKEN_URL`
    whose host is neither PingFederate's base URL nor one of its virtual host names; its compose file defaults
    `TOKEN_MODE` to `local` and sets no `PF_TOKEN_URL`. Its Entra bridge authenticates in PoP mode with `aud`
    `PF_ISSUER` and sends no DPoP header, so this item does not touch it; its virtual-host caveat above does.
49. **`ClientAttestationConfig` takes one expected audience.** (S4A) For code that builds the verifier from
    libs/client-attestation: `Builder.acceptedAudiences(Set)` and `Builder.addAcceptedAudience(String)` are
    replaced by `Builder.expectedAudience(String)`, and `acceptedAudiences()` by `expectedAudience()`. Code that
    calls the old methods no longer compiles; the one such caller found on 2026-09-27 is pf-oidf-modules'
    `demo/spiffe-bootstrap/harness/BootstrapHttpHarness.java`, which calls `addAcceptedAudience(OP_ISSUER)` and
    becomes `expectedAudience(OP_ISSUER)`. Pass the one identifier the verifying server answers to: an
    authorization server's issuer, or a resource server's resource identifier. DPoP combined mode is refused
    ("Server misconfigured: no expected DPoP htu") when neither `expectedHtu` nor the `requestUri` argument names
    the endpoint.
50. **`DpopProofValidator` compares the `htu` after normalisation, and refuses more.** (S4A) For code that uses the
    validator directly, as `services/demo-rs` does: the scheme and host are compared in lower case, a default or
    empty port is dropped, percent-encoded unreserved characters are decoded and dot-segments removed, and the
    query and fragment are ignored (RFC 9449 §4.3 and the RFC 3986 sections it names). An `htu` carrying user
    information is now refused, where it used to be matched on its host and path alone, and one that is not an
    absolute http or https URI is refused outright. How to tell: "DPoP 'htu' mismatch" in the refusal, which repeats
    at most 256 characters of the proof's `htu`. What to change: send the endpoint's URL as the endpoint advertises
    it.
51. **An attester client fetches its challenge from the attester's own endpoint.** (S4B) A client that put a challenge
    from `POST /federation/attestation-challenge` into its instance-key proof must fetch it with
    `GET /federation/attestation/challenge` instead - the URL `/.well-known/client-attestation-service` and
    `/.well-known/client-attester` now give as `challenge_endpoint`. Until it moves, `/federation/attestation`
    answers 401 `{"error":"invalid_instance_proof","error_description":"challenge is unknown, expired, or already
    used"}`. The refused challenge is not spent: it stays good at the token endpoint for its 300 s. A client that
    follows `challenge_endpoint` but still `POST`s gets 405 with `Allow: GET` and
    `{"error":"invalid_request","error_description":"this challenge endpoint takes GET, not POST"}`. Proofs without
    a challenge are unaffected while `challengeRequired` is `false`, the default. Move clients once every node runs
    this release: a 0.3.0 node has no `GET /federation/attestation/challenge` (404), and its attester reads only
    `oidf:challenge:*`. Both documents are publicly cacheable - `/.well-known/client-attestation-service` for an
    hour, `/.well-known/client-attester` for five minutes - so a client or proxy holding a copy from before the
    upgrade names the old path until the copy expires; a client that reads `challenge_endpoint` should fetch the
    documents again after the upgrade, and one that keeps its copy in memory has to be restarted. Nothing in this
    repository fetches the attester's challenge; `AttestationFlowHarness` and the idp-agentic-demo bridge fetch the
    authorization server's, for the PoP at the token endpoint, and are right as they are. The clients that fetch
    the attester's are in other repositories: see **The client SDK and domain-authority's agents lose the
    attester's challenge until they change**.
52. **The client SDK and domain-authority's agents lose the attester's challenge until they change.** (S4B)
    client-attestation-sdk-polyglot's `ClientAttestation` (Python, Go, TypeScript and Java alike; read on
    2026-09-27) takes `challenge_endpoint` from `/.well-known/client-attester`, `POST`s to it, goes on without a
    challenge after any error, and keeps the document for the life of the object. pf-agentic-identity-domain-authority
    uses that SDK in its demo workloads and its agent-runtime gateway, and its hand-written agents (aws-bedrock-demo,
    cross-cloud-chain, gke-spiffe-demo) and its AKS and EKS lab capture adapters `POST` to the same member; the GKE
    adapter labels its challenge step with the old path. After the upgrade:
    - A client with the new document gets 405, and mints with no challenge. The mint succeeds while the attester's
      `challengeRequired` is `false`, the default, so the proof loses its freshness without a sign. Where it is
      `true`, every mint answers 401 `invalid_instance_proof`, "a server-issued challenge is required".
    - An SDK object made before the upgrade still `POST`s to `/federation/attestation-challenge` and puts the
      authorization server's challenge in its proof. Every mint then answers 401 `invalid_instance_proof`,
      "challenge is unknown, expired, or already used", until the object is made again: its copy of the document
      is not an HTTP cache and does not expire. The agent-runtime gateway holds one such object for the life of
      the process.
    - Once the SDK `GET`s the attester's challenge, its default of putting the same value in the token-endpoint
      PoP or DPoP `nonce` (always in Go, TypeScript and Java; in Python unless `challenge_at_token=False`) answers
      400 `use_attestation_challenge`. It did before this release as well, because the attester had spent the
      value; now the value is also from the wrong namespace.

    What to change: `GET` the attester's `challenge_endpoint` for the instance-key proof, and for the PoP either
    `POST` to `/federation/attestation-challenge` for a second challenge, which the Entity Configuration's
    `openid_provider` metadata names, or send none. Restart long-running workloads once every node runs this
    release. Leave the attester's `challengeRequired` at `false` until these clients have moved.
    `/.well-known/client-attester` does not name the authorization server's challenge endpoint (F-0118).
53. **The token endpoint refuses the attester's challenges.** (S4B) A challenge from
    `GET /federation/attestation/challenge` presented in a Client Attestation PoP or a DPoP `nonce` answers 400
    `use_attestation_challenge`; fetch the token endpoint's from `POST /federation/attestation-challenge`, which the
    Entity Configuration's `openid_provider` metadata names. A client that put one challenge in both its proof and
    its PoP was refused before this release too, because the attester had spent it by the time the PoP arrived.
    The SDK does this by default: see **The client SDK and domain-authority's agents lose the attester's challenge
    until they change**.
54. **A wrong method at a challenge endpoint answers JSON with an `Allow` header.** (S4B) Any method but `POST` at
    `/federation/attestation-challenge`, and any but `GET` at `/federation/attestation/challenge`, is 405 with
    `Allow` naming the one it takes, `Cache-Control: no-store` and a JSON `invalid_request` body, and issues no
    challenge - `HEAD` included. Before, a `GET`, `HEAD`, `PUT` or `DELETE` on the authorization server's endpoint
    fell to the servlet API's defaults, `sendError` with 405 (400 over HTTP/1.0) and no `Allow` (javap of
    jakarta.servlet-api 5.0.0, 2026-09-27). Over HTTP/1.1 only the body and the header change; over HTTP/1.0 the
    status changes too, from 400 to 405. PingFederate answers every `OPTIONS` 403 itself, before either servlet.
55. **Each endpoint's settings reach only its own challenges.** (S4B) `challengeCacheMaxEntries`, `challengeTtlSeconds` and
    the three `challengeRateLimit*` init-params on `ClientAttestationChallengeServlet` now size only the
    authorization server's challenges and cap only its callers; the same names on
    `AttestationIssuanceChallengeServlet` do the same for the attester's. Before, the one endpoint's TTL and size
    were the attester's too. No shipped descriptor sets any of them, so the defaults (300 s, 8192 entries, 60
    requests a minute per caller) apply to both unless you override `web.xml`; if you did, set the attester's
    servlet as well.
56. **Attester challenges have a key prefix of their own in Redis.** (S4B) With `OIDF_REDIS_URL` set, the attester's
    challenges are `oidf:cas:challenge:<value>` (300 s TTL), beside `oidf:as:challenge:*`. Anything that counts,
    evicts or alerts on key prefixes should know the new one. Nothing needs flushing.

## What changes for readers of the repository

- **The coverage dashboard is generated, not tracked.** `docs/coverage-dashboard.md` and `.html` left git on
  2026-09-27 (plan decision 18): a file that every test change regenerated reactor-wide conflicted in Phase 0's
  parallel merges and turned `main` red once (the Build on `e067a87`, which the 0.3.0 notes record). To read it,
  download the `coverage-dashboard` artefact of any Build run whose reactor build completed (a run that fails
  in `mvn verify` publishes none), or run `mvn verify` then `python3 tools/coverage-report.py`, which writes
  both files to the same paths, git-ignored. The generator's `--check` is gone. It is strict by default: it
  exits 1 when a module that has tests left no surefire report, a module that configures jacoco left no
  `jacoco.xml`, or a jacoco check includes no method, and the page it writes says so first - so a build that
  skipped tests cannot produce a clean-looking dashboard. `--no-strict` writes the same pages and exits 0.
- **The showcase's documents are built, not inlined.** `showcase/index.html` no longer carries the rendered
  documents. `node tools/build-showcase-docs.mjs` (after `npm ci --prefix tools`) writes them to
  `showcase/docs.js`, git-ignored, which the page loads; the dashboard is rendered with them when the last
  build left one. Without `docs.js` every other view works and the Documentation view says how to build it.
  CI uploads the built `showcase/` as the `showcase` artefact of every Build run that gets past the generator.
  `--check` is gone here too.
  `tools/check-showcase-links.py` reads the documents from `docs.js`, so build it first.
- **CI runs the Postgres suite every time.** The Build's `java` job has a `postgres:16-alpine` service
  container and sets `IDM_TEST_JDBC_URL`, `IDM_TEST_JDBC_USER` and `IDM_TEST_JDBC_PASSWORD` for the reactor
  build, so device-instance's IOM registry suite runs against it on every run rather than when Testcontainers
  happens to find Docker.
- **The release waits for the Build on its commit.** `release.yml`'s green-Build gate, the second after the
  tag-version check, judges the Build workflow's own run on the tagged commit - the newest run a push to `main`
  or a dispatch started, and the latest attempt of each required job in it - where it used to read every check
  run on the commit, whatever had made it, and judge the oldest of two. A pull request's Build no longer counts:
  it tested the pull request's merge with its base, and its check runs could decide the gate. The gate waits,
  reading every 30 seconds for up to 20 minutes, while that run is queued, pending or in progress, instead of
  failing on it. It fails when the run or a required job concludes anything but success, after two minutes when
  there is no such run, after three refused reads in a row, and at 20 minutes, each time with nothing
  published. A `required-checks.txt` that names no job now fails the gate; before 0.4.0 it passed. The job's
  token permission `checks: read` is now `actions: read`. v0.3.0's release failed on a `java` job still running
  and was re-run by hand (run 36278709651, F-0069). How a release is cut, and what to do when the gate fails,
  is in [CONTRIBUTING.md](../../CONTRIBUTING.md#releasing). Nothing changes for a consumer. It was not
  dispatched: the next tag is its first live run.

  is a Swift package for iOS 17 (and macOS 14, where its tests run) with no dependencies. It speaks the device
  side of [services/device-enrolment](../../services/device-enrolment/README.md): enrolment with an App Attest
  attestation, a Secure Enclave instance key and a PingOne sign-in; re-minting with an ES256 key proof and an App
  Attest assertion; the user-verification refresh; and the recoveries the protocol implies (the time-box refusal,
  a lost App Attest counter race and a spent challenge, each once). It follows
  [docs/device/ios-client-contract.md](../device/ios-client-contract.md), which says every request, value and
  refusal as the Java has them at this release. A [sample app](../../clients/ios/SampleApp/README.md) drives it on
  an iPhone and captures App Attest vectors, and [.github/workflows/ios.yml](../../.github/workflows/ios.yml)
  builds and tests both on macOS.

  It is a skeleton until X-I01b (Phase 6). It speaks the protocol as it stands here, which Phase 6 changes: a nonce
  the service checks (F-0084, X-A05), key proofs with required claims (X-A06), assertions on every renewal and on
  the refresh (X-A08), and `/v1` (X-A11). It has not run on a physical iPhone or against a PingOne tenant (U-0063,
  U-0081), the Entra device token is a seam that throws (U-0064, U-0065), and the device path as a whole is not
  production-usable until Phase 6 (M-2). Verified 2026-09-27: 73 unit tests; the kit's commitments reproduce
  what the server's own classes print and what real macOS 27.2 App Attest objects signed; and the kit enrolled,
  re-minted and recovered from both refusals against the service's own classes over HTTP
  ([clients/ios/tools/interop](../../clients/ios/tools/interop/README.md)).

  Nothing a deployment runs changes, so "Before you deploy" has no item for it. Writing the contract found two
  service defects, both for Phase 6: [F-0084](../findings/F-0084.yaml) (an iOS enrolment's ID token is bound to
  nothing) and [F-0085](../findings/F-0085.yaml) (refusals carry registry text, the device id among it, to the
  caller).

## Package EVIDENCE: the store, the digest and the binding

Plan items S3a, S3b and M-1. Verified 2026-09-27 on PingFederate 13.1.3's libraries; the stores against
`redis:7-alpine`, plaintext and TLS; and on a booted 13.1.3 rig, where a challenge sent over verified TLS
landed as `oidf:as:challenge:<value>`, and the same Redis reached by an address its certificate does not name
made the challenge endpoint answer 503 `temporarily_unavailable`, with the hostname mismatch in `server.log`.
The conflict event in `audit.log` and the token and federation endpoints' 503 were not driven on a boot
(U-0072).

- **The store** (S3a). `MiniRedisClient` sets the HTTPS endpoint identification algorithm and the SNI name on
  every `rediss://` socket, runs `startHandshake()` before the first byte of `AUTH`, and builds its trust
  from `OIDF_REDIS_CA_FILE` when set. Against a Redis with a self-signed certificate for `localhost`: the
  handshake completes with the CA file; a URL by `127.0.0.1` fails endpoint identification before `AUTH`;
  without the CA file the JVM's CAs refuse the certificate. `MiniRedisClientTlsTest` repeats the first two
  inside the JVM, against a TLS server whose certificate `keytool` makes for the run, so the build catches
  the loss of the name check without a TLS Redis: removing `setSSLParameters` from `connect()` fails it.
  `redis://` is refused under the production profile (`transportRefusal`), read directly from
  `OIDF_DEPLOYMENT_PROFILE` until PR-1 (Phase 2) centralises it, and no message quotes a URL's userinfo. The three
  stores answer in three states; `RedisAttestationStore` is one view per `StoreNamespace` over one shared
  client, and `AttestationSupport` hands out the view each surface asks for. The verifier, the token-endpoint
  filter (`statusFor`), the challenge endpoint and `OpenIdFederationServlet`'s jti guard map
  `STORE_UNAVAILABLE` to 503. `bind` is `SET NX PX` until the evidence expires, then `GET` and compare; a key
  that can twice be neither taken nor read is `STORE_UNAVAILABLE`, not a conflict. The live tests
  (`RedisLiveTest`) skip without `OIDF_TEST_REDIS_URL`; CI's Build runs both halves, plain and TLS, and fails if
  either skipped (package HYG, below).
- **The digest and the binding** (S3b). `InstanceIdentity` carries `evidenceType`, `evidenceDigest`,
  `audiences` and the evidence's `iat`; the seven SPIFFE-shaped validators and the wallet validator fill them
  and no longer put the token in `workloadClaims`; `AttestationMinter` writes the three
  `instance_attestation_*` members and caps `exp` at the evidence's. The digest is `evidenceDigest`: the
  SHA-256 of the JWS Signing Input, never of the whole token, because jose4j 0.9.6 verifies one signed token
  with trailing whitespace, with stray characters or padding in its signature, with non-canonical trailing
  bits and, for ECDSA, as the `(r, n-s)` twin; the adversarial review drove each of those past a digest of
  the whole string. `AttestationIssuanceServletTest` presents each of them with a thief's key, for a
  JWT-SVID and a GKE token, and expects `instance_attestation_bound`. `AttestationIssuanceServlet` applies
  `EvidencePolicy`, binds through `EvidenceBindingStore`, refuses a conflict with `instance_attestation_bound`
  and emits `attestation.evidence.conflict`, naming both keys, through `FederationEvents` (installing
  `PfAuditEventSink` at init so it reaches `audit.log`). Its proof jtis, bindings and, from S4b, challenges live
  under `oidf:cas:*`. Residual risk, as the
  plan states it: a thief who uses the evidence first wins; detectable, not preventable, without key-bound
  evidence.
- **CIMD** (M-1). `AttesterResolvers.fromEnvironment` takes the environment as a function and honours
  `OIDF_ATTESTER_CIMD_URL` only in development, and `ClientAttestationServiceMetadataServlet` lists `cimd` in
  `client_metadata_sources_supported` only there. Refusing the one source rather than the attester keeps the
  blast radius to the clients that source describes, and a source silently dropped is what the ERROR line
  and the discovery document are there to make visible.

## Package RAR: the containment model, as a library

Plan item S1a, the first of three for design S-1 (blocker B1). Verified 2026-09-27 by the module's build:
350 tests, the 100% METHOD gate on 55 decision and reader methods and the 95%/92% floor, on the merged tree.

- **`libs/rar-model`**, JDK only, so the plugin can shade it and the servlets borrow nothing for it. Nine rules
  (`set`, `set_of_values`, `limit` with a paired unit, `amount`, `instant_limit`, `equal`, `string`, `object`,
  `forbidden`); a field the ceiling omits is unconstrained, a field it carries and the candidate omits is not
  contained, `null`, `[]`, a blank string, a negative limit or amount and a wrong type are malformed, undeclared
  fields are refused, a candidate fits one same-type entry; a thing a type can say two ways is held to one
  spelling (alternatives); 16 details, depth 8, 256 members, 2048 characters, and numbers of at most 64 digits
  written out, measured without writing them.
- **Three operations.** `contains` (strict), `authorize(INHERIT | STRICT)` whose result is checked against the
  ceiling before it is returned, and `intersect`, the meet - within both arguments, commutative, the greatest
  lower bound, monotone, idempotent and associative under a seeded property test of 1,500 iterations each, and
  refused as too large past 16 entries.
- **Built-in models** for `sales_agent`, `payment_initiation` (RFC 9396 Figure 2 plus the flat `amount` and
  `currency` the plugin reads, the two spellings of the amount as alternatives) and `account_information`
  (`accounts`, `validUntil`, `recurringIndicator`; not the §7.1 `access` object), each on the §2.2 common fields;
  more from a models document (`OIDF_RAR_MODELS_FILE` / `OIDF_RAR_MODELS`, schema in the README) that may
  `extends` a built-in and may not replace one; a SHA-256 fingerprint of the effective model and the library's
  semantics version; the common-fields fallback for unmodelled types only when
  `OIDF_DEPLOYMENT_PROFILE=development`.
- **A strict reader.** Duplicate member names, non-ASCII hex in a Unicode escape and half a surrogate pair are
  refused; nesting past 32, a number literal past 128 characters and text past 262,144 characters are refused
  as too large before they cost anything.
- **One vector file**, 244 named cases in the module's test-jar with the runner the wave-2 modules reuse, and
  `@Requirement` tags quoting CAS §7 rules 1 to 3 and §7.1, RFC 9396 §2.2 and §6.1, and PROFILE §7 items 1 and 2.
- **Wired by S1b and S1c.** The token gate and the attester (package S1B) and the RAR plugin (package S1C) ask
  this library; `RarContainment` is deleted and `RarEntitlement` is unused, kept until its deletion
  ([F-0100](../findings/F-0100.yaml)). F-0001 is closed. "Before you deploy" has what they bring, starting at
  **Every RAR field is compared, and undeclared fields are refused**.

## Package PLUGIN: fail-open, the principal, and the rig script

Plan items S2a and S2b. Closes blocker B3 (F-0003), the "fail-open catches everything" high (F-0016) and
F-0030. Verified 2026-09-27 on PingFederate 13.1.3.0.

- **Fail-open is for an unreachable PDP** (S2a). `PdpUnavailableException` is the one failure "Fail open on
  engine error" grants through: `JdkHttpTransport.classify` sorts a refused or reset connection, an unresolved
  name and a deadline into it, and `PdpResponses.bodyOf` adds HTTP 429, 502, 503 and 504. An `SSLException`
  or a `ProtocolException` anywhere in the cause chain, every other status, a non-JSON content type, a body that
  is not a single JSON object with each member once, an AuthZEN answer without a boolean `decision`
  (AUTHZEN-1.0 §5.5) and a governance answer whose `decision` is not a string or `authorised` not a boolean
  refuse. A reset is read from the exception's class, or from a message that starts with the JDK's own
  "Connection reset": the review of this package found that searching the message let a DENY carrying a header
  named `connection reset` fail open, because the JDK client copies wire text into its protocol errors
  (F-0093, closed here with a loopback test through the real client). Each class has a test, and each of those
  methods is in the plugin's 100% METHOD gate.
- **Always deny unless PERMIT** (S2a). The switch is gone from the descriptor. PingFederate 13.1.3 hands an
  instance its stored configuration as it is and raises no error for an undeclared field (`javap` of
  `ConfigurationUtil` and the admin API's `PluginConfigTranslator`), so the field was dropped rather than kept
  read-only; the rehearsal below imported a 0.3.0 archive holding it, and the instance configured and decided.
- **The shared secret is encrypted** (S2a), as `TextFieldDescriptor(name, label, true)` under the same name (the
  three-argument constructor, `javap` on the 13.1.3 SDK). A `SecretReferenceFieldDescriptor` names a secret in
  a configured secret manager, which neither the rig nor any consumer runs; the encrypted field gives the
  archive what PingFederate gives its own client secrets. The upgrade was rehearsed on the rig from the v0.3.0
  release jar (Before you deploy, item 21; U-0022).
- **https, and TLS that is checked** (S2a). The PDP URL is https unless `OIDF_DEPLOYMENT_PROFILE=development`,
  on the field's validator and again at configure; "Skip TLS verification" is inert outside development. The
  profile is read from the environment until PR-1 centralises it.
- **The server's attributes last** (S2a). The governance-engine request writes the requested fields first and
  its own attributes after them, and refuses a requested field whose name is one of them - including every
  `req_` and `att_` mirror, which closes F-0073, found on the way.
- **The principal, per flow** (S2b). `PrincipalResolver` labels PingFederate's user key: `client` under client
  credentials, `authenticated` for a refresh and at the resume after authentication, `identity_hint` at
  `/as/bc-auth.ciba` (the request URI read as the container maps it, so path parameters and escapes do not hide
  the endpoint; U-0094), `subject_token` only from a subject the token-endpoint filter verified and published,
  else `none`; `login_hint` and `_principal_sub` are `client_asserted`, in development only. "Types requiring
  an authenticated principal" refuses before any PDP call. The PDP receives the attester's `iss` beside the
  agent, and `RESOURCE_OWNER_ATTRIBUTE` is deleted. `PrincipalPerFlowTest` drives each flow through `enrich`
  with the context built as `AuthorizationDetailsUtil` builds it.
- **Logs** (S2a). The plugin's lines carry the principal and the user key as `sha256:` and 16 hex characters.

  failure travels as text with the principal hashed and no PDP exception is chained.
- **The rig script** (S2b). `conformance/verify-rar-principal.sh` lends the rig this jar through

  upgrade rehearsal. Its run of 2026-09-27T03:40Z is the evidence in
  [the plugin README](../../plugins/rar-paz-plugin/README.md#who-the-decision-is-about).
- **Not verified, and opened.** Not driven on the rig: the device flow (U-0066), the JWT-bearer grant (U-0017;

## Package STOPGAPS: the B5 push stopgap, the B4 route removed, the IOM schema v2 proposed

Plan items S10-0, M-2 and X-A03. Verified 2026-09-27 on PingFederate 13.1.3.

- **SSF push is no longer starved by paused, disabled or poll backlogs, and no single POST holds it past
  10 s** (S10-0). `SsfStore.dueForPush` joins the stream's state in all three stores, so only enabled push
  streams' SETs are read for push (SSF 1.0 §8.1.2.1 quoted in the tests). A stream whose delivery fails waits
  out its first SET's backoff as a whole: nothing else of it is posted until that SET is due again, so a
  receiver that is down costs one attempt per backoff step, and when it is back the SET that failed goes first
  and the rest follow by `issuedAt`. SETs issued in the same second go in `jti` order in all three stores, for
  both reads of the queue; ordered by `issuedAt` alone, Postgres returned a burst in whatever order its rows
  lay, the retry moved from SET to SET, and five SETs of one second took 130 s rather than 75 s to
  dead-letter. The `jti` is random, so within a second this is not the order the SETs were generated in
  (F-0095). The POST has a 2 s connect deadline and a 10 s deadline on the whole exchange, body
  included, read to 4 KiB, and the connection is closed at the deadline (tested against loopback receivers
  that never answer, answer and stall, and answer 100 kB). The loop starts from `SsfSupport.start`, which every
  servlet's bootstrap runs, and a store that cannot be opened at boot is one ERROR, with the `jdbcUrl` replaced,
  and a retry every 30 s rather than an exception out of the load-on-startup servlet. What S-10 (Phase 4) still
  owes: fairness between enabled streams (one with 500 due SETs older than another's fills the batch, and a
  slow receiver holds the thread for up to 10 s a SET), leases, more than one thread, the order within a
  second, and holding the events raised while a stream is paused or the store is down (F-0017). Push delivery
  has still not been run against the conformance suite.
- **The stores' SQL runs.** `SsfStoresOnPostgresTest` runs the `tables` and `ldm` stores' push selection,
  three ticks of the loop over each, and a burst of one second's SETs - held and retried from one SET, and
  dead-lettered at 75 s - against Postgres (16.14 here; CI's Postgres service in the Build), the
  `ldm` store on the model repo's `0000` and `0001` migrations, vendored with their checksums. The `tables`
  selection and the same ticks were also run once on the HSQLDB 2.7.1 the PingFederate 13.1.3 image ships.
- **On the rig** (`conformance/up.sh` in its own slot, PingFederate 13.1.3, the branch's jars at `e858f9e`).
  Boot order, in-memory store: `SSF push delivery executor started` at 03:41:43,415 UTC, the runtime listener
  on 9031 at 03:41:45,160, `PingFederate started` at 03:41:45,742, and nothing in `audit.log` - the loop was
  running before any request could start it, and the annotation's `loadOnStartup` is honoured in the merged
  `pf-runtime.war`. A `tables` store whose database was not up at boot: the ERROR at 03:42:28,675, PingFederate
  up and serving discovery, the heartbeat and federation while SSF answered 500, and at 03:42:58,677, once the
  database was up, the retry opened the store and started the loop. And what 0.3.0 did instead: with
  `OpenIdFederationServlet`'s init made to throw, Jetty failed the whole `pf-runtime.war` and every runtime
  endpoint answered 503 (U-0076, U-0023).
- **`POST /compliance` removed** (M-2). The route, its handler and `EnrolmentService.applyComplianceChange`
  are gone; `CaepSignalApplier`, called from PingFederate's SSF receiver, is the one mapping left, and the
  tests keep the property (a suspended instance cannot re-mint over HTTP) through it. `CaepEventHandler`
  stays, unwired, for X-A18. The device-enrolment README states the deadlock and that the device path is not
  production-usable until Phase 6. Verified with `mvn -o -B clean verify` against Postgres (the 22
  `IomInstanceRegistryTest` cases included).
- **IOM schema v2 proposed** (X-A03): [docs/device/iom-schema-v2-proposal.md](../device/iom-schema-v2-proposal.md),
  a diff against the model as `libs/device-instance` and `servlets/ssf` write it and as migrations `0000`,
  `0001`, `002` and `006` declare it, for David to raise in `idp-scim-service`. F-0004 and F-0005 are
  `mitigated` in the register; their full fixes are Phase 6 and Phase 4. U-0076, U-0077 and U-0078, the three
  things S10-0 first assumed, are closed with the evidence above.

## Package S4B: separate challenges for the authorization server and the attester

What changed. `ChallengeEndpointServlet` (client-attestation) holds what both endpoints share: the one method it
issues for, the namespace it issues into, its own per-caller cap, and its init-params, which configure only that
namespace (`AttestationSupport.configureChallengeService(StoreNamespace, ...)`; the old overload is the
authorization server's). `ClientAttestationChallengeServlet` is the authorization server's (`StoreNamespace.AS`,
`POST`, and `replayCacheMaxEntries` as before); `AttestationIssuanceChallengeServlet` (attestation-issuer) is the
attester's (`StoreNamespace.CAS`, `GET`). `AttestationIssuanceServlet` consumes from `oidf:cas:challenge:*`. The
CAS document and the attester configuration name the attester's endpoint; the Entity Configuration's
`openid_provider` block names the authorization server's, as before. A setting the store refuses (a TTL that is not
positive) now fails that endpoint's start and leaves the store it had, where before it could leave a zero TTL
behind for every store made after it. The issuance criterion (`ClientAttestationUtils`) learns the OP issuer
through a test seam now, as the token-endpoint filter already did, so a test can drive it; in PingFederate it asks
`OAuthIssuerUtils` as before.

The texts, read on 2026-09-27. ABCA-10 §6.1 (draft-ietf-oauth-attestation-based-client-auth-10 at ietf.org, and -11,
which says the same): a challenge is fetched with an HTTP POST to the `challenge_endpoint` URL, the response carries
`attestation_challenge` and is made uncacheable with `Cache-Control: no-store`, and "If the Authorization Server
offers a challenge endpoint, the Client MUST retrieve a challenge and MUST use this challenge in the Client
Attestation PoP JWT or DPoP Proof". CAS §4.1 (docs/openid-client-attestation-service-1_0.md): `GET
/attestation-challenge`, and "a challenge issued by one party MUST NOT be accepted by the other". The paths are this
deployment's; clients discover them from `challenge_endpoint` (CAS §5.1, ABCA-10 §6.1).

Replay and lifetime, unchanged. A challenge lives 300 s and is spent by its first use, on either surface; in memory
each namespace holds at most 8192. The token endpoint's proof `jti`s are held in `oidf:as:jti:*` for the proof's
maximum age plus the clock skew, 360 s by default; the attester's in `oidf:cas:jti:*` for 300 s. A store that cannot
answer is 503 `temporarily_unavailable` at both endpoints, as PR #31 made it.

Verification. Unit tests on 2026-09-27, JDK 20.0.2 and JDK 17.0.11, every coverage gate met: the refusal in both
directions through the real servlets, leaving the refused challenge unspent (`AttestationIssuanceServletTest`); the
token-endpoint direction through the real `ClientAttestationAuthFilter` and the real issuance criterion, each of
which refuses a challenge from `oidf:cas:challenge:*` with the challenge left unspent and takes one from
`oidf:as:challenge:*` once (`TokenEndpointChallengeSurfaceTest`); the same on the RESP fake
(`RedisAttestationStoreTest`); each method and response (`ChallengeEndpointMethodTest`,
`AttestationIssuanceChallengeServletTest`); each endpoint's settings (`ChallengeEndpointSettingsTest`,
`AttestationSupportTest`); each advertisement against the servlet mapping it names
(`ChallengeEndpointAdvertisementTest`). With the attester pointed back at `oidf:as:challenge:*`, three of the
issuance tests fail; with the filter or the criterion pointed at `oidf:cas:challenge:*`, two of
`TokenEndpointChallengeSurfaceTest`'s fail each. On a booted PingFederate 13.1.3 (`conformance/up.sh` as
`PF_RIG_NAME=pfai-s4b`, the deployed client-attestation and attestation-issuer jars byte-identical to the branch's
build): both endpoints answered their own method 200 and every other 405 with the right `Allow`; `OPTIONS` was 403
from PingFederate; the two attester documents named `/federation/attestation/challenge` and the Entity Configuration
named `/federation/attestation-challenge` only; with Redis, one challenge from each endpoint landed in its own
namespace with a 300 s TTL. PingFederate's own `/.well-known/openid-configuration` and
`/.well-known/oauth-authorization-server` named neither endpoint (F-0115). The client SDK and domain-authority were
read, not run: the symptoms in **The client SDK and domain-authority's agents lose the attester's challenge until
they change** follow from their code on 2026-09-27 and this release's answers.

Residual risk. The cross-surface refusal is proven by unit tests, not on a booted PingFederate: the rig runs
attestation inert (U-0125). Behind a proxy PingFederate does not see through, every caller shares one allowance per
endpoint - 61 requests with 61 `X-Forwarded-For` values were counted as one caller on the rig (F-0116). The
federation's `oauth_client_attester` block names neither of the attester's endpoints (F-0117). A client that
discovers from `/.well-known/client-attester` alone finds no challenge the token endpoint accepts (F-0118), and one
that discovers from PingFederate's own documents finds no challenge endpoint at all (F-0115). Until the SDK changes,
its challenge fetch fails quietly and the attester's proofs carry no challenge.
