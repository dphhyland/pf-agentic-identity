# 0.4.0 - Phase 1: the blockers closed or mitigated, the guard rails up

In progress: 0.4.0 is the version the poms have carried since 2026-09-27, and this page is written as its
pull requests land. Phase 1 of the production programme closes the 2026-09-26 review's first three blockers,
mitigates two more, seeds the findings register, and puts the CI and documentation guard rails in place.
Nothing here is released until David tags it; [CHANGELOG.md](../../CHANGELOG.md) carries the one-line
entries meanwhile.

**Read "Before you deploy" first.**

## Before you deploy

Every pull request that changes what a consumer must do - a setting that becomes strict, a default that
changes, a route that goes - adds its item here as it merges, naming its commit or pull request, so this list
is never assembled from memory at the end.

1. **`POST /compliance` is gone from device-enrolment** (M-2, the B4 mitigation). Anything that called it
   gets 404. Nothing in any known environment did: the service has never been deployed. Read
   [services/device-enrolment/README.md](../../services/device-enrolment/README.md#not-production-usable-until-phase-6)
   before deploying it anywhere: a device enrols `UNKNOWN`, re-minting needs `COMPLIANT`, and until Phase 6
   nothing in this repository can make it so. `REQUIRE_COMPLIANT_DEVICE=false` is the development switch,
   and it removes the compliance control rather than satisfying it.
2. **SSF push delivery changes behaviour at boot, and nothing needs configuring** (S10-0, the B5 stopgap;
   [servlets/ssf/README.md](../../servlets/ssf/README.md#upgrading-to-040)). The push loop starts with
   PingFederate rather than with a receiver's first management request. A data store that is down when
   PingFederate boots no longer stops `pf-runtime.war` from starting: the SSF endpoints answer 500 and the
   log says `SSF transmitter NOT started` until a retry, every 30 s, opens it. A push receiver that takes more
   than 10 s to answer, or 2 s to accept a connection, is now a retryable failure - its stream dead-letters
   after `pushRetryMaxAttempts` such ticks - where before the loop waited for it. Held SETs on a paused or
   disabled stream are no longer read for push; they never delivered before either.
