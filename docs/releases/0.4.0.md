# 0.4.0 - Phase 1: blockers closed or mitigated, guard rails up

0.4.0 is Phase 1 of the production programme, in progress. Each package adds its own section here as it
lands; the "Before you deploy" list is the union of what they ask of a consumer.

**Read "Before you deploy" first.** Several changes stop things working until something is done.

## Before you deploy

1. **Decide the deployment profile, because unset now means production** (R-I4, X-D02). `OIDF_DEPLOYMENT_PROFILE`
   is read by the image's entrypoint and by the CIBA simulator: `development` means a rig or a demo, and unset,
   `production` or any other value means production. Two things change with it: a plaintext `data.zip` no
   longer boots in production (next item), and the CIBA simulator never runs there. Set
   `OIDF_DEPLOYMENT_PROFILE=development` on a rig - the conformance rig's `vars.env` does - and nothing on a
   production deployment. Plan item PR-1 (Phase 2) centralises the profile; until then this is the whole
   definition.
2. **Ship `data.zip.age`, or say the deployment is `development`** (R-I4). `pf-entrypoint.sh` refuses a plaintext
   archive - baked in or named by `PF_ARCHIVE_FILE` - with `FATAL: a plaintext archive (...) is refused when
   OIDF_DEPLOYMENT_PROFILE is production`, and PingFederate does not start. Every deployment that still boots
   from a plaintext `data.zip` and does not set the profile stops at the next restart on this version. The
   encrypted path is unchanged in what it needs: the archive and one identity
   ([the image build](../../build/pingfederate/README.md#the-archive-at-boot)).
3. **Move the age identity to a file** (R-I4). `PF_ARCHIVE_AGE_KEY_FILE` is preferred over `PF_ARCHIVE_AGE_KEY`:
   when both are set the file is used, and a file that is named but missing is a refusal, not a fall-through to
   the variable. Both are removed from the environment before PingFederate starts, so nothing that reads the
   PingFederate process's environment - a diagnostic, a plugin, a shell in the container - sees the identity
   from this version. The inline variable remains visible in the container's metadata (`docker inspect`), which
   is why the file is preferred. An identity file the entrypoint was given is no longer deleted after use
   (0.3.0's entrypoint removed it when it could, which on a writable mount was the operator's file).
4. **Optionally pin the archive** (R-I4). `PF_ARCHIVE_SHA256=<hex>` makes the boot check the archive - the
   ciphertext, for an encrypted one - before it is decrypted or imported, and stop on a mismatch.
   `PF_ARCHIVE_FILE=<path>` selects a mounted archive over the one baked into the image.
5. **The plaintext path now takes its keys from the archive** (R-I4). On the plaintext path `pf.jwk` and
   `pingfederate-system-keys.xml` are extracted from inside `data.zip`, as the encrypted path always did, and
   overwrite the `overlay/` copies the Dockerfile still stages. For an archive exported the way the rig's
   `export.sh` does they are the same files. A plaintext archive that lacks them is refused
   (`FATAL: pf.jwk is not in the archive`), where 0.3.0 booted with the overlay copies.
6. **Re-stage `modules/` with the new `stage-modules.sh`, choosing a profile** (R-I1). `MANIFEST` is version 2 -
   a header naming the format, the profile, the build time and the commit; a section per module group; a
   sha256 per jar - and `assemble-pf-runtime-war.sh` refuses a v1 `MANIFEST` (bare filenames), a `modules/`
   staged for a profile other than the one the image is built for (`STAGING_PROFILE`, default `production`),
   and a jar whose digest is not the one staged. `stage-modules.sh` with no argument stages the production
   profile: **eight jars**. `--profile conformance` stages nine, the CIBA simulator among them, and is what the
   rig uses. Anything of yours that counted the module set by counting `MANIFEST` lines now counts the header
   and sections too; count the digest lines, `grep -cE '^[0-9a-f]{64}  ' MANIFEST`. From this version a
   release's module set is the production profile, so `pf.plugins.ciba-sim.jar` is not among a release's
   assets - a rig builds it from source, as `conformance/up.sh` does.
7. **The CIBA simulator needs three settings, and a directory that already exists** (X-D02). The decision
   endpoint answers 404 and the authenticator fails every backchannel request unless `OIDF_CIBA_SIM_ENABLED=true`,
   `OIDF_DEPLOYMENT_PROFILE=development` and `OIDF_CIBA_SIM_DIR` names an absolute path to an existing directory
   that is not a symbolic link, is owned by the user PingFederate runs as and is `0700`, on a POSIX filesystem.
   The plugin no longer creates the directory or falls back to the JVM's temp directory; the conformance image
   makes `/opt/ciba-sim` to this shape, and the rig's `vars.env` names it
   ([plugins/ciba-sim](../../plugins/ciba-sim/README.md)). Both halves check before every request and log the
   reason for a refusal at WARN.
8. **An image built from `conformance/compose-context.sh`'s output needs the build arg** (R-I1). `.context/modules`
   is staged for the conformance profile from this version - `up.sh` stages it so, and `compose-context.sh` accepts
   nothing else - so a plain `docker build .context`, which builds for the default profile, stops at the assembler:
   `modules/ was staged for the conformance profile, and this image is being built for production`. Pass
   `--build-arg STAGING_PROFILE=conformance`, or your platform's equivalent, and know what comes out: a conformance
   image, the CIBA simulator in it, gated by item 7's three settings, which `.context/vars.env` carries. For a
   production image, stage again with `stage-modules.sh --profile production` and build without the arg.
9. **Give the RAR plugin an `https` PDP URL, or say the deployment is development.** From 0.4.0 the plugin
   refuses a plaintext PDP URL unless `OIDF_DEPLOYMENT_PROFILE=development` (read straight from the environment
   until PR-1 centralises the profile; unset means production): the admin console and the admin API reject the
   field, and an instance imported from an archive with an `http://` URL fails to configure and denies every
   request that reaches it. A rig or a demo sets `development`.
10. **Expect a client-credentials caller to be refused for payments and account queries.** The new field "Types
    requiring an authenticated principal" (default `payment_initiation,account_information`) refuses those types
    before any PDP call when the principal is nobody or is the client - which is what a client-credentials grant
    is, since PingFederate passes the client id as its user key. A machine-to-machine caller that used to get a
    `payment_initiation` detail decided about itself now gets `invalid_authorization_details`; give it a flow with
    a person in it (CIBA, code, a refresh of one of those), or take the type off the list for a deployment that
    has decided a client may hold it.
11. **Re-save every RAR plugin instance's shared secret.** "Shared Secret" is an encrypted field now, under the
    same name. A stored plaintext value survives the upgrade - verified on the rig (2026-09-27, 13.1.3): the
    archive imports, PingFederate logs one `PluginConfigUtil` ERROR ("There was a problem deobfuscating the value
    for the field: Shared Secret") and hands the plugin the value as stored, and the PDP receives the right header
    - but the archive still holds it in the clear until the instance is saved again, which stores it obfuscated
    under the master key and stops the error.
12. **Fail-open means unreachable now, and nothing else.** "Fail open on engine error" grants through a
    connection refused or reset, an unresolved name, a deadline, or HTTP 429/502/503/504 - and refuses a 401 or
    403 from a wrong secret, any other status, a body that is not JSON, a non-JSON content type and a TLS
    failure. A deployment that relied on the old switch to paper over a wrong secret or a certificate that does
    not match will see denials; fix the secret or the certificate.
13. **"Deny unless PERMIT" is gone.** The decision is always deny-unless-PERMIT. A stored value under that name is
    carried by PingFederate and never read (13.1.3 hands a no-parent instance its stored configuration as it
    is, and the admin API raises no error for an undeclared field - both read with `javap`, 2026-09-27; seen on
    the rig on import). An instance saved with it off now refuses a DENY.
14. **Point policy at the new PDP request shape.** `principal_source` is one of `authenticated`, `client`,
    `identity_hint`, `subject_token`, `client_asserted` (development only) or `none`, and the AuthZEN
    `subject.type` is `client` for a client principal; the attester's `iss` arrives as `context.actor.iss` and
    `context.attestation.iss` (AuthZEN) or `actor_iss` and `attestation.iss` (governance engine). The
    `com.pingidentity.ps.oidf.rar.resource_owner_sub` request attribute is no longer read - the principal comes
    from PingFederate's user key. In the governance-engine dialect the server's attributes are written last and a
    detail field that maps onto one of them (`UserID`, `principal_source`, `actor`, `actor_iss`, `client_id`,
    `attestation.*`, a `req_*` or `att_*` mirror) is refused.
15. **`login_hint` and `_principal_sub` need `OIDF_DEPLOYMENT_PROFILE=development` as well as the switch.**
    "Trust a client-asserted principal" is inert in production, with a warning at configure time; both go at 1.0
    (plan decision 9).
16. **Give the authentication contract behind the authorization endpoint a `subject` attribute.** PingFederate
    13.1.3 asks the plugin once in the code flow, at the resume after authentication
    (`OAuthResumableRequestHandlerBase`, path `/as/<id>/resume/as/authorization.ping`), and the user key it passes
    is the authentication result's `subject` attribute - nothing else. The rig's HTML-form adapter has no such
    attribute, and without it the plugin knows nobody and refuses `payment_initiation` and `account_information`
    with `invalid_authorization_details` after the user has signed in; with `subject` mapped on the adapter (by
    expression from `username`) the same flow is decided about `suite-user` and the token is issued for them.
    Both driven by `conformance/verify-rar-principal.sh` (2026-09-27, 13.1.3.0). The mapped authentication
    attributes also reach the plugin under the SDK's `IN_PARAMETER_AUTH_DETAILS_USER_INFO` parameter, which it does
    not read: the deployment says who the principal is by naming `subject`, not the plugin by guessing an
    attribute.
17. **Token exchange is decided about nobody.** PingFederate passes no user key for the token-exchange grant (and
    skips the plugin for a requested token type of `id-jag`); the token-endpoint filter does not yet publish a
    verified subject-token subject under `verified_subject_token_sub`, so `principal_source` is `none`, the
    payment and account types are refused, and other types reach the PDP with the client as subject and
    `principal_source: none`.

## What changes for readers of the repository

- **The coverage dashboard is generated, not tracked.** `docs/coverage-dashboard.md` and `.html` left git on
  2026-09-27 (plan decision 18): a file that every test change regenerated reactor-wide conflicted in Phase 0's
  parallel merges and turned `main` red once (the Build on `e067a87`, which the 0.3.0 notes record). To read it,
  download the `coverage-dashboard` artefact of any Build run whose reactor build completed (a run that fails
  in `mvn verify` publishes none), or run `mvn verify` then `python3 tools/coverage-report.py`, which writes
  both files to the same paths, git-ignored. The generator's `--check` is gone. It is strict by default: it
  exits 1 when a module that has tests left no surefire report, a module that configures jacoco left no
  `jacoco.xml`, or a jacoco check includes no method, and the page it writes says so first - so a build that
  skipped tests cannot produce a clean-looking dashboard. `--no-strict` writes the same pages and exits 0.
- **The showcase's documents are built, not inlined.** `showcase/index.html` no longer carries the rendered
  documents. `node tools/build-showcase-docs.mjs` (after `npm ci --prefix tools`) writes them to
  `showcase/docs.js`, git-ignored, which the page loads; the dashboard is rendered with them when the last
  build left one. Without `docs.js` every other view works and the Documentation view says how to build it.
  CI uploads the built `showcase/` as the `showcase` artefact of every Build run that gets past the generator.
  `--check` is gone here too.
  `tools/check-showcase-links.py` reads the documents from `docs.js`, so build it first.
- **CI runs the Postgres suite every time.** The Build's `java` job has a `postgres:16-alpine` service
  container and sets `IDM_TEST_JDBC_URL`, `IDM_TEST_JDBC_USER` and `IDM_TEST_JDBC_PASSWORD` for the reactor
  build, so device-instance's IOM registry suite runs against it on every run rather than when Testcontainers
  happens to find Docker.

## Package IMAGE: staging profiles, the entrypoint, and a conformance-only simulator

Plan items R-I1, R-I4 and X-D02. Verified 2026-09-27 on PingFederate 13.1.3.

- **Staging profiles** (R-I1). `stage-modules.sh --profile production|conformance`; `MANIFEST` v2 with the
  profile, sections and digests; the assembler refuses a profile mismatch, a v1 file, a tampered, stray or
  missing jar (each tried against the 13.1.3 stock war, no output war left behind); the Dockerfile takes
  `STAGING_PROFILE`, records it as the label `io.github.dphhyland.pf-agentic-identity.staging-profile`,
  refuses a third value at its first `RUN`, and makes `/opt/ciba-sim` under conformance only. Both profiles
  built: production has eight jars and no simulator directory, conformance nine and the directory as
  `drwx------ ping`. `conformance/docker-compose.yml` builds with `STAGING_PROFILE=conformance`, `up.sh`
  stages for it, `compose-context.sh` refuses any other stage.
- **Entrypoint** (R-I4). `umask 077` first; `PF_ARCHIVE_AGE_KEY_FILE` before `PF_ARCHIVE_AGE_KEY`, the inline
  identity piped to `age` rather than written to a temporary file, and both variables unset before the
  hand-over; `PF_ARCHIVE_SHA256`; `PF_ARCHIVE_FILE`; a plaintext archive refused unless the profile is
  `development`; the keys extracted from the archive on both paths; an encrypted archive recognised by content
  in either age format, binary or `age -a` armored; the "tmpfs-backed path" claim replaced with what the base
  image does and a paragraph on mounting one. `test-entrypoint.sh` runs 42 checks against the script with the
  bootstrap stubbed, here or inside a built image (`--image`); 42 of 42 passed inside the 13.1.3 image as the
  `ping` user, with the image's busybox grep and again with GNU grep - the check that the inline identity
  reached no file is proved live by two that plant it and find it. On a real boot of the rig's image from an
  encrypted archive on a read-only mount, with the identity as a file and the digest set, under the production
  profile, PingFederate came up with neither identity variable in its JVM's environment and `Umask: 0077` - on
  the writable layer and again with `/opt/out` on a tmpfs (`exec` in the mount options, or `run.sh` cannot
  start). Every script under
  `build/pingfederate` and `conformance/compose-context.sh` is shellcheck-clean (0.11.0).
- **ciba-sim conformance-only** (X-D02). `SimulatorGate` holds the three checks as decision methods in the
  plugin's 100% METHOD gate, with a test per refusal, including the ownership branch (a principal that is not
  the test's user) and the non-POSIX branch (a zip filesystem opened without POSIX attributes). The servlet
  answers 404 rather than 503 because that is what the same URL answers on an image without the jar, and
  nothing about a refusal changes with time. `DecisionStore` no longer reads the environment or creates its
  directory.

## Findings closed in 0.4.0

The findings register ([docs/findings](../findings/README.md)) is the record: one file per finding, each with
the pull requests that closed it and dated verification text. The findings this release is expected to close
are the ones targeted at it:

```sh
python3 tools/findings.py list --status closed          # closed, with the release that closed each in its file
python3 tools/findings.py --gate 0.4.0                  # what still stands in the way of this release
```

The register itself is new in 0.4.0 (plan item D-2), seeded from the review, the reviewer reports, the
plan's "Found while designing" list, and the assumptions `docs/unverified.md` had been carrying (now `U-`
entries, cross-referenced from that file).
