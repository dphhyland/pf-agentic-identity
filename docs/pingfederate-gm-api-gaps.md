# Implementing the Grant Management API on PingFederate: what fits, and what cannot

An implementer's report against **PingFederate 13.0.3**, testing the OIDF
[Grant Management API](https://openid.net/specs/oauth-v2-grant-management-1_0.html) draft
plus the proposed Grant Evaluation extension (`docs/GMAPI-Extension.md`).

The short version: **§6 and §7.1 can be added from outside the product. §5 cannot.** That
line is not about effort — it is where the spec stops describing endpoints and starts
describing authorization server behaviour, and no extension point reaches behaviour.

## What PingFederate supports natively

Nothing. Verified, not assumed:

| Spec | Test | Result |
|---|---|---|
| §7.1 `grant_management_endpoint` | `GET /.well-known/openid-configuration` | absent |
| §7.1 `grant_management_actions_supported` | same | absent |
| §7.1 `grant_management_action_required` | same | absent |
| §5 `grant_management_action` | `?grant_management_action=create` | **ignored** |
| §5 invalid action rejected | `?grant_management_action=nonsense_value` | **HTTP 200** |
| §5 `grant_id` in token response | authorization code exchange | absent — response is `access_token, refresh_token, token_type, expires_in` |
| §6.2 / §6.3 endpoints | — | no such endpoint |

The invalid-action result is the telling one. PF does not merely fail to honour
`grant_management_action`; it does not parse it. A client cannot distinguish an AS that
rejects the action from one that never read it, which means **a client cannot detect the
absence of support** — it just gets a grant with whatever semantics PF chose.

What PF *does* have is a proprietary Persistent Grant Management API at
`/pf-ws/rest/oauth/...`: Basic-authenticated, admin-shaped, different contract. It is a
grant store, not the spec.

> A caution for anyone reading a PF discovery document in this repo: the
> `grant_management_*` **scopes are there because we created them** in
> `deploy/pingfederate/terraform`. They are strings. PF attaches no meaning to them, and
> their presence is not evidence of support.

## What we added, and how

`servlet/` deploys a WAR into `server/default/deploy`, which PF's `PFWebAppProvider`
serves at `/gm-api`. It reads grants in-process through the supported SDK
(`AccessGrantManagerAccessor`), so it is the same grant store PF itself uses.

| Spec | Endpoint | Status |
|---|---|---|
| §6.2 query | `GET /gm-api/grants/{id}` | ✅ |
| §6.3 revoke | `DELETE /gm-api/grants/{id}` | ✅ 204 |
| §6.7 evaluate *(proposed)* | `POST /gm-api/grants/{id}/evaluate` | ✅ |
| §7.1 metadata | `GET /gm-api/.well-known/grant-management-configuration` | ⚠️ wrong location — see below |
| §5 lifecycle | — | ❌ not implementable |

Two deviations, both forced:

**The query response omits `claims`.** §6.2 shows a `claims` array. PF's
`com.pingidentity.sdk.accessgrant.AccessGrant` models no claims — there is no accessor
and no field. The array has no source, so it is omitted rather than invented.

**The metadata is at the wrong URL.** §7.1 adds its fields to the AS's own metadata.
That document is PF's: generated by the server, with no `PF-INF` plugin type for
extending it and no SDK surface that touches it. We serve the same fields at
`/gm-api/.well-known/grant-management-configuration`, which **no conformant client will
look for**. The response carries an `x_note` saying so. This is a demonstration of the
shape, not working discovery.

## §5 is the wall

Section 5 asks the authorization server to:

1. accept `grant_management_action` = `create` | `replace` | `merge` on the
   authorization request, and reject unknown values;
2. accept a `grant_id` parameter for `replace` and `merge`;
3. return `grant_id` in the **token response**;
4. honour `grant_management_action_required`.

None of that is an endpoint. It is behaviour at `/as/authorization.oauth2` and
`/as/token.oauth2`, both of which are PF's own servlets. A WAR in `server/default/deploy`
gets its own context path; it cannot intercept another. PF's plugin types
(`PF-INF/idp-authn-adapters`, `token-processors`, `authorization-detail-processors`, …)
extend points *within* those flows — none of them can add a request parameter, change how
one is validated, or add a field to the token response.

An access token manager can add **claims**, and PF already does: the `agid` claim carries
the grant's id, which is how clients in this repo name their grant. But a claim inside the
token is not `grant_id` beside it in the response. A client reading the spec will look for
the field, not decode the JWT.

So on this evidence §5 needs product support. There is no plugin-shaped answer, and a
convincing fake would be worse than the gap: it would let a client believe `replace` and
`merge` work when the grant lifecycle underneath is whatever PF decided.

## For the spec

Three things this exercise suggests, offered as implementer feedback rather than
conclusions:

**The §6 / §5 split is load-bearing for adoption.** §6 is an API and rode onto an
unmodified AS in a day. §5 is AS behaviour and cannot be retrofitted at all. An AS vendor
can therefore ship "Grant Management API support" meaning only §6 — and a client has no
way to tell, because §7.1 metadata is also AS-owned and unreachable. The evaluation
extension inherits this: `grant_evaluation_supported` will be undiscoverable on any AS
that has not adopted it natively, however good the endpoint is.

**Silent parameter ignoring is a real interop hazard.** PF returning 200 for
`grant_management_action=nonsense_value` is arguably fine per OAuth's tolerance of unknown
parameters, but it means a spec-aware client gets a grant with no idea the action was
dropped. §5 may be worth an explicit statement that an AS advertising
`grant_management_actions_supported` MUST reject unknown actions — giving clients
something to probe.

**§6.2's `claims` array needs a stated source.** It is unimplementable on an AS whose
grant model has no claims, and PF's does not. Either the array is optional and should say
so, or the spec assumes a grant model it should describe.

## Reproducing

```bash
# native support: none of these appear
curl -sk https://localhost:9131/.well-known/openid-configuration \
  | jq '{grant_management_endpoint, grant_management_actions_supported}'

# an invalid action is not rejected
curl -sk -o /dev/null -w '%{http_code}\n' \
  "https://localhost:9131/as/authorization.oauth2?client_id=acme-budgeting&response_type=code\
&scope=accounts.read&redirect_uri=http%3A%2F%2Flocalhost%3A8081%2Fcallback\
&grant_management_action=nonsense_value&state=x"          # -> 200

# no grant_id on the token response
python3 scripts/authcode.py <tpp-secret>                   # -> access_token, refresh_token, token_type, expires_in

# what we added does work
curl -sk https://localhost:9131/gm-api/.well-known/grant-management-configuration
curl -sk -H "Authorization: Bearer $TOKEN" https://localhost:9131/gm-api/grants/$AGID
curl -sk -X DELETE -H "Authorization: Bearer $TOKEN" https://localhost:9131/gm-api/grants/$AGID  # -> 204
```
