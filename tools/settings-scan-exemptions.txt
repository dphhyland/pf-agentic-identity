# Modules tools/settings-scan.py does not hold to "every setting read is catalogued" yet (plan item ST-3).
#
# One module path per line, under the `# group` line of the package that will catalogue it; that package deletes
# its own group and nothing else. A line in the "not shipped" group gives, after a colon, why the module never
# reaches a deployment. The scan refuses a line for a module that is not in the reactor, that has a catalogue
# already or that reads nothing, and a "not shipped" line naming a module the image stages. A missing file means
# no exemptions.
#
# While the flag below is `no`, any group may exempt a module. ST-4 sets it to `yes` once the ST3B and ST3C
# groups are gone; from then on only the "not shipped" group may.
refuse-shipped-exemptions: yes

# group not shipped
libs/testkit: DB1's Postgres test support, a test-scoped dependency of the modules whose stores it tests; it is never staged into the image or deployed, and its OIDF_TEST_JDBC_URL, OIDF_TEST_JDBC_USER and OIDF_TEST_JDBC_PASSWORD (and CI) are for the build, described in CONTRIBUTING.md
services/harness: verification CLIs run by hand with mvn exec:java, and pinned by their smoke tests under mvn test; nothing in build/ or .github/ stages or releases it and its pom skips deploy, so its OIDF_CLIENT_SECRET, OIDF_POP_AUDIENCE and the rest are a developer's, described in services/harness/README.md, and a catalogue would put them in the operators' reference
