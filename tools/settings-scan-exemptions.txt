# Modules tools/settings-scan.py does not hold to "every setting read is catalogued" (plan item ST-3): only modules
# that never reach a deployment.
#
# One module path per line, under a `# group` line. A line in the "not shipped" group gives, after a colon, why the
# module never reaches a deployment. The scan refuses a line for a module that is not in the reactor, that has a
# catalogue already or that reads nothing, and a "not shipped" line naming a module the image stages. A missing
# file means no exemptions.
#
# With the flag below at `yes` the scan refuses an exemption in any group but "not shipped", so every shipped
# module is held to its catalogues, and the scan says so. ST-4 set it on 2026-09-28, once ST3B and ST3C had
# catalogued the last shipped modules and deleted their groups; while it was `no`, any group could exempt a module
# its package had not catalogued yet.
refuse-shipped-exemptions: yes

# group not shipped
libs/testkit: DB1's Postgres test support, a test-scoped dependency of the modules whose stores it tests; it is never staged into the image or deployed, and its OIDF_TEST_JDBC_URL, OIDF_TEST_JDBC_USER and OIDF_TEST_JDBC_PASSWORD (and CI) are for the build, described in CONTRIBUTING.md
services/harness: verification CLIs run by hand with mvn exec:java, and pinned by their smoke tests under mvn test; nothing in build/ or .github/ stages or releases it and its pom skips deploy, so its OIDF_CLIENT_SECRET, OIDF_POP_AUDIENCE and the rest are a developer's, described in services/harness/README.md, and a catalogue would put them in the operators' reference
